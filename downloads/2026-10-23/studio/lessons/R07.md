# R07. 시퀀스·상태·정지와 실패 복구

시퀀스는 순서를 가진 명령 목록입니다. 요리의 준비→가열→불 끄기처럼 로봇도 앞으로 이동→정지→방향 전환→정지의 순서가 필요합니다. 상태는 지금 프로그램이 어느 단계에 있는지 나타내는 이름표입니다. 오늘 상태에는 ready, 각 action, completed가 있습니다. completed는 검사와 호출을 끝낸 프로그램 상태이고 센서로 목표 도달을 확인한 상태가 아닙니다. 상태의 의미를 문서로 정하면 10/29 대시보드에서도 실제 관찰과 명령 완료를 섞지 않을 수 있습니다.

PC의 my-sequence.json에 앞으로·뒤로·정지 세 명령을 만듭니다. 각 명령의 예상 실행 순서와 최종 completed 값을 종이에 적은 뒤 실행합니다. 실행기는 목록 전체를 먼저 검사하고, 명령을 하나 수행한 뒤 유지 시간을 기다리고, 다음 명령 전에 정지를 요청합니다. 마지막에 잘못된 명령이 있으면 앞부분까지 실행해 버리지 않도록 전체 검사를 앞에 둡니다. 빈 목록·너무 긴 목록·누적 시간이 긴 목록도 거절합니다. 학습자가 만든 입력의 일부만 보고 안전하다고 판단하지 않습니다.

```python
try:
    adapter.execute(command)  # 선택한 어댑터에게 명령을 넘깁니다.
finally:
    adapter.stop()            # 중간에 오류가 나도 정지를 요청합니다.
```

이 예는 finally의 핵심을 보여 주는 축약 예입니다. 실제 제공 파일은 runner.py이며 반복과 close까지 포함합니다. `try`는 실행을 시도할 범위, 들여쓰기는 그 범위에 속하는 줄, `finally`는 정상·오류 여부와 관계없이 정리할 범위입니다. Ctrl+C는 KeyboardInterrupt를 일으켜 이 정리 경로로 들어갑니다. SIGTERM도 중단 예외로 바꿉니다. 그러나 프로세스 강제 제거, 전원 상실, OS 정지, 이미 고장 난 보드까지 소프트웨어가 통제할 수는 없습니다. 전원 분리 담당과 접근 방법은 현장 운영에서 별도 준비합니다.

강사는 대기 함수에서 일부러 KeyboardInterrupt를 발생시키는 시험을 보여 줍니다. 학생은 왜 마지막 이벤트가 stop인지 확인합니다. 단순 출력 예를 보여 주는 것보다 명령이 중간에 끊긴 실제 경로를 시험하는 것이 중요합니다. 다음에는 잘못된 마지막 명령을 넣고 앞의 forward 이벤트가 전혀 생기지 않았는지 봅니다. 학생 개별 수행은 성공 시퀀스, 입력 거절 시퀀스, 실행 중 중단 세 조건의 결과를 비교하는 것입니다. 모의 시험에서는 실제 바퀴가 멈췄다는 표현을 사용하지 않습니다.

상태 기록에는 mode, status, completed, feedback을 구분합니다. mode는 dryrun 또는 hardware, completed는 처리한 명령 개수, feedback은 현재 command-only입니다. 장치 실행에서 오류가 나면 성공 JSON을 출력하지 않습니다. 출력 파일을 저장할 때는 실행 날짜, 입력 파일명, 관찰 조건도 적습니다. 시간값을 늘려서 출력이 바뀌었는지뿐 아니라 어떤 조건에서 실패하고 어떻게 복구했는지 남깁니다. 실물 관찰이 있다면 그 기록을 별도 열로 두어 프로그램 상태와 비교합니다.

필수 활동의 완성 예는 forward 0.3초, backward 0.2초, stop이며 총 유지 시간은 0.5초입니다. 이 합계는 실제 벽시계 수행 시간과 다릅니다. 초기화·처리·정리 시간이 더해지기 때문입니다. 추가 도전은 반복 동작을 무한 while로 만들기보다 유한한 목록으로 만들고 최대 시간 규칙을 적용하는 것입니다. 오류 복구에서는 JSON을 복구한 후 다시 전체 검사하고, 실물에서 이상 움직임을 본 경우에는 전원을 분리한 상태에서 원인을 확인한 다음 재시작합니다.
