# Git/GitHub 확인과 평가

**18활동의 작성·예상·실제 확인을 분리해 봅니다. 속도나 설치 성공만 평가하지 않습니다.**

| 기준 | 확인할 증거 | 보완이 필요한 경우 |
| --- | --- | --- |
| 개념 | 입력·처리·출력 또는 변경 단계의 역할 설명 | 결과 이름만 외우고 근거를 말하지 못함 |
| 수정 | 지정한 위치와 변경 전후를 연결 | 여러 곳을 바꾸어 원인을 설명하지 못함 |
| 확인 | 정상·경계·오류 사례의 예상과 실제 구별 | 실행 성공을 내용 정확성으로 단정 |
| 전달 | 파일·명령·결과·남은 질문을 재현 가능하게 기록 | 어느 파일을 사용했는지 불명확 |

각 기준은 ‘독립 설명 가능 / 힌트 후 가능 / 다시 연습’으로 기록합니다. 개인 실행 여부는 별도 체크하며 미실행을 실패한 개념 이해로 간주하지 않습니다.

## 구간별 확인 질문

1. status를 열 번 실행하면 커밋이 생기나요?
2. 커밋 해시가 교안과 달라지면 실패인가요?
3. .gitignore가 과거 커밋의 파일을 지우나요?
4. 브랜치를 만들면 GitHub PR도 자동으로 생기나요?
5. PR 본문에 ‘모든 테스트 통과’라고 쓰면 그대로 믿어도 되나요?
6. clean 상태이면 원격도 최신이라고 단정할 수 있나요?

## 제출

work의 활동 노트와 수정 파일, 마지막 종합 작업, 확인한 명령·출력 또는 수동 추적 기록을 제출합니다. 제출 위치는 강사 안내를 따릅니다. 정답 폴더를 학생 결과에 복사하지 않습니다.


## 다른 상황에 적용해 보기 · 추가 복습

교시별 필수 설명을 다른 상황에 적용하는 추가 복습입니다. 수업 시간에 모두 풀기 어려우면 남은 문제는 복습으로 풉니다. 답안은 먼저 학생이 작성하고 이후 아래 해설을 대조합니다. 설치나 로그인이 됐는지와 문제를 이해했는지는 따로 확인합니다.

### 전이 1 · 저장과 기록의 구별

**문제:** 새 안내.md를 저장하고 status만 세 번 실행했습니다. 파일은 어느 상태이며 다음 이력에 남기려면 어떤 행동이 필요한가요? 인터넷이 없는 경우도 판단하세요.

**해설·확인 기준:** 새 파일은 아직 추적되지 않은 상태이며 add로 내용을 선택하고 commit으로 기록합니다. status는 조회입니다. 인터넷 없이도 가능합니다. 저장과 이력과 공유를 셋으로 구별하면 충족입니다.

### 전이 2 · 세 상태의 값

**문제:** 커밋=28, 스테이징=30, 작업 파일=29입니다. 기본 diff와 staged diff의 변화 및 지금 커밋할 값을 쓰세요. 업무 요구 29를 기록할 다음 행동은 무엇인가요?

**해설·확인 기준:** 기본 diff는 30→29, staged diff는 28→30이며 커밋에는 30이 들어갑니다. 29를 다시 add하고 staged diff를 읽습니다. 마지막 저장값이 무조건 커밋된다는 답은 재학습입니다.

### 전이 3 · ignore의 시간 범위

**문제:** 이미 기록한 가짜 secret.txt를 .gitignore에 적었습니다. 과거 커밋과 추적 여부가 어떻게 되나요? 앞으로 실제 비밀을 다룰 때 보고에 무엇을 남기나요?

**해설·확인 기준:** 과거 내용과 이미 추적한 상태는 자동 삭제되지 않습니다. 실제 비밀을 연습 자료로 쓰지 않고 노출 발견 시 담당 절차와 자격 증명 교체를 확인합니다. ignore를 이력 삭제라고 말하면 오답입니다.

### 전이 4 · 복구 대상 선택

**문제:** README의 좋은 새 문장을 유지하면서 이번 커밋에서만 빼려 합니다. 어떤 restore 옵션을 쓰나요? 마지막 기록 문장으로 작업 파일까지 돌리는 요청과 어떻게 다르나요?

**해설·확인 기준:** git restore --staged README.md는 선택을 취소하고 작업 문장을 유지합니다. git restore --source=HEAD --worktree README.md는 작업 문장을 이전 기록으로 바꾸므로 편집 내용을 보관하고 사용합니다. 대상·기준·사라지는 내용 설명이 필요합니다.

### 전이 5 · 공유 시차

**문제:** 내 로컬은 clean이고 새 커밋도 있습니다. 동료 README는 옛 문장입니다. 공유 장소에 보내기와 동료가 받아 적용하기를 구분하여 가능한 원인 두 개와 확인 방법을 쓰세요.

**해설·확인 기준:** push 전이거나 동료가 아직 fetch/적용하지 않았을 수 있습니다. remote 주소, 로컬/원격 기록 차이, 동료 작업 상태를 확인합니다. fetch는 곧바로 작업 파일 변경을 보장하지 않습니다. clean으로 공유 상태를 단정하지 않으면 충족입니다.

### 전이 6 · 충돌의 업무 판단

**문제:** 양쪽 브랜치가 경계값을 28과 30으로 수정했고 승인된 요구는 28 이상 주의입니다. 최종 값과 검사 세 개, 해결 절차를 쓰세요.

**해설·확인 기준:** 28을 유지하고 27.9→정상,28→주의,28.1→주의를 확인합니다. 표식을 제거해 최종 문장을 작성하고 add→staged diff 검토→commit으로 기록합니다. 양쪽 평균이나 위쪽 자동 선택은 요구 근거가 없습니다.
