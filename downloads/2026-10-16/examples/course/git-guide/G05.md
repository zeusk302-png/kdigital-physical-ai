# G05 · 바뀐 줄을 읽고, 무엇을 기록할지 고르기

G04에서 만든 **같은 git-class-lab 저장소**를 이어서 씁니다. Git Bash에서 현재 폴더가 맞는지 `pwd`로 확인하고 `git status`를 실행하세요. README.md가 있고 첫 커밋이 있어야 합니다. 작업 중인 다른 변경이 있으면 이번 예제로 덮어쓰지 말고 먼저 강사와 상태를 확인합니다. 네트워크와 GitHub 로그인은 필요하지 않습니다.

**필수 활동**은 diff로 변경 읽기→add→다시 수정→두 비교 결과 예측→목적에 맞게 다시 선택→커밋과 log 확인입니다. 추가 활동은 서로 다른 커밋 두 개를 비교하는 것입니다. 모든 명령을 외우기보다 지금 어떤 두 상태를 비교하는지 말하는 것이 목표입니다.

## 1. 개념 정의 · 비교는 두 대상이 있어야 합니다

diff는 difference, 즉 차이를 뜻합니다. Git의 diff는 파일 전체를 다시 보여 주는 대신 **어느 줄이 없어지고 어느 줄이 추가되었는지** 보여 줍니다. 문장을 고치면 이전 문장을 삭제하고 새 문장을 추가한 것으로 표시될 수 있습니다. 빨강과 초록은 비교를 읽기 위한 색이며 오류·성공 점수가 아닙니다. 색을 볼 수 없는 환경에서도 `-`와 `+` 기호로 읽을 수 있습니다.

여기서 가장 중요한 점은 비교 대상입니다. 옵션 없는 `git diff`는 작업 폴더와 스테이징 영역을 비교합니다. `git diff --staged`는 스테이징 영역과 현재 마지막 커밋을 비교합니다. `git diff HEAD`는 현재 마지막 커밋과 작업 폴더의 전체 차이를 볼 때 씁니다. `HEAD`는 지금 체크아웃한 기록을 가리키는 Git의 이름이며, 보통 현재 브랜치가 가리키는 마지막 커밋을 뜻합니다.

## 2. 일상 비유 · 제출 봉투를 고른 뒤 원고를 또 고쳤다면

보고서 1판을 제출할 봉투에 넣었다고 생각해 보세요. 그 뒤 책상 위 원고를 2판으로 고쳐도 봉투 안 내용이 저절로 바뀌지는 않습니다. add는 그 시점의 내용을 고르는 행동입니다. add 뒤에 파일을 다시 저장하면 **선택된 내용과 현재 작업 파일 내용이 다를 수 있습니다**.

따라서 커밋 직전에는 파일을 저장했는지만 보지 않고 선택된 내용이 내가 남기려는 내용인지 봐야 합니다. 이 비유도 파일을 진짜 봉투 폴더로 복사하라는 뜻은 아닙니다. Git이 내부에서 세 시점의 내용을 구별하여 관리한다는 설명입니다.

## 3. 구성요소 · diff 화면 읽기

```text
diff --git a/README.md b/README.md
--- a/README.md
+++ b/README.md
@@ -1,2 +1,2 @@
 # My Git Practice
-First record.
+Second record.
```

`a/`와 `b/`는 비교의 이전 쪽과 이후 쪽을 구별하는 표기입니다. 실제로 a와 b라는 폴더를 만들 필요가 없습니다. `---`와 `+++`는 파일 쪽 설명이고, 내용 줄 앞의 `-`는 이전 줄, `+`는 새 줄입니다. 공백으로 시작한 줄은 주변 문맥으로 제시한 바뀌지 않은 줄입니다. `@@` 사이 숫자는 바뀐 구간의 줄 위치를 설명하며 직접 코드에 입력하지 않습니다.

예시는 첫 단원의 실제 문장과 다를 수 있습니다. 파일에 문장을 더 추가했다면 비교 결과 줄 수가 더 많아집니다. 출력 화면을 외우는 대신 어떤 문장이 이전에 있었고 지금 무엇으로 바뀌었는지 읽습니다. 줄바꿈 경고가 보이면 문장 차이와 구별해 강사에게 확인합니다.

## 4. 준비 · 기준 상태를 먼저 확인하기

```bash
# 이 창의 현재 폴더를 확인합니다.
pwd
# main에서 기록할 변경이 없는 상태인지 확인합니다.
git status
# 현재 문서 내용을 읽어 기준을 확인합니다.
cat README.md
# 최근 기록 세 개를 한 줄씩 보여 줍니다.
git log --oneline -3
```

`--oneline`은 커밋을 짧은 한 줄로 보라는 옵션이고 `-3`은 최근 세 개까지만 보라는 뜻입니다. 기록이 한 개나 두 개뿐이면 그 개수만 보입니다. 예시의 숫자와 다른 ID가 나오는 것이 정상입니다. 변경 내용과 시간 등이 다르면 커밋 ID도 달라질 수 있습니다.

긴 비교나 이력 화면 아래에 `(END)` 또는 `:`가 보이면 내용을 넘겨 보는 화면일 수 있습니다. 이때 `q`를 눌러 명령 입력으로 돌아옵니다. `q`를 파일에 쓰는 활동이 아닙니다. 창을 강제로 닫기 전에 화면이 입력 대기인지 내용 보기인지 구별하세요.

## 5. 복사 명령 · add 뒤 다시 고친 내용 비교

아래는 README의 기존 내용을 보존하고 끝에 줄을 추가합니다. `>>`는 기존 파일 뒤에 덧붙이라는 기호입니다. G04의 `>`와 다릅니다. 같은 명령을 여러 번 실행하면 같은 문장이 여러 번 붙으므로 단계마다 한 번만 수행합니다.

```bash
# 첫 번째 설명 줄을 작업 파일 끝에 추가합니다.
printf '\nPractice topic: files.\n' >> README.md
# 아직 선택하지 않은 작업 변경을 봅니다.
git diff
# 지금 README 내용을 다음 기록 대상으로 고릅니다.
git add README.md
# 선택된 내용과 마지막 기록 사이의 차이를 봅니다.
git diff --staged
# 선택한 뒤에 작업 파일을 한 번 더 고칩니다.
printf 'Practice topic: history.\n' >> README.md
# 선택된 내용 뒤에 추가로 생긴 작업 변경을 봅니다.
git diff
# 다음 커밋에 들어갈 내용은 무엇인지 따로 봅니다.
git diff --staged
# README가 선택 상태와 추가 수정 상태 양쪽에 있는지 확인합니다.
git status
```

이 시점에서 잠시 멈추세요. `git diff`에는 보통 나중에 붙인 `Practice topic: history.`가 보입니다. `git diff --staged`에는 먼저 추가하고 선택한 `Practice topic: files.`가 보입니다. 같은 README 이름이 status의 **커밋 준비됨**과 **아직 준비 안 됨** 부분 양쪽에 나올 수 있습니다. 파일이 두 개 생긴 것이 아니라 같은 파일의 두 상태가 다른 것입니다.

## 6. 예상 결과를 비교하고 기록하기

다음 표의 예상 결과를 먼저 말한 뒤 직접 확인합니다.

| 시점 | 일반 diff | staged diff | 지금 commit한다면 |
|---|---|---|---|
| 첫 줄 추가, add 전 | 첫 줄 추가가 보임 | 비어 있음 | 선택한 내용이 없어서 새 기록 없음 |
| 첫 줄 추가, add 후 | 비어 있음 | 첫 줄 추가가 보임 | 첫 줄이 포함됨 |
| 둘째 줄 추가, 다시 add 전 | 둘째 줄 추가가 보임 | 첫 줄 추가가 보임 | 둘째 줄은 포함되지 않음 |
| 다시 add 후 | 비어 있음 | 두 줄 추가가 보임 | 두 줄이 포함됨 |

두 줄 모두 이번 기록에 담는 것을 이번 실습의 목표로 정합니다. 비교 결과를 확인한 뒤 아래를 수행합니다.

```bash
# 마지막에 추가한 줄까지 포함하도록 현재 내용을 다시 선택합니다.
git add README.md
# 다음 기록에 두 설명 줄이 모두 들어가는지 확인합니다.
git diff --staged
# 목적을 설명하는 문구와 함께 선택 내용을 기록합니다.
git commit -m "Add two practice topics"
# 아직 기록하지 않은 변경이 없는지 확인합니다.
git status
# 방금 만든 기록의 제목과 ID를 확인합니다.
git log --oneline -3
```

커밋 후 작업 파일이 그대로인 것은 정상입니다. 커밋이 문서를 원래대로 되돌리는 행동은 아닙니다. Git은 기록에 담을 내용을 보관하며 현재 README에도 두 설명 줄이 남습니다. 출력이 영어·한국어·중국어 등으로 달라도 **선택 내용과 작업 내용이 같은가, 마지막 기록 이후 변경이 남았는가**를 기준으로 읽습니다.

## 7. 변경 실습 · 이유가 다른 두 기록

먼저 README 마지막에 `Next step: branches.`를 추가하고 저장하세요. diff로 줄을 읽고 add→staged diff→commit 순서로 진행합니다. 이번 메시지는 `Describe next learning step`처럼 실제 변경 이유가 보이게 정합니다. 그 다음 기존 문장의 단어 하나를 편집기로 바꾸고, 앞 기록과 다른 목적인 메시지로 두 번째 커밋을 만듭니다.

완료 후 log에서 두 기록을 찾고 **제목만 보고 변경 의도를 구별할 수 있는지** 짝이 확인합니다. 의미 없는 `수정`, `최종`, `진짜최종`만 반복하기보다 무엇을 위한 기록인지 적습니다. 메시지는 한국어로 적어도 됩니다. 한국어가 깨지면 PC의 문자 표시 문제와 커밋 성공 여부를 나누어 확인합니다.

추가 도전은 직전 두 커밋 사이를 비교하는 것입니다. 현재 저장소에 최소 두 커밋이 있는지 먼저 확인합니다.

```bash
# 마지막 커밋과 그 바로 전 커밋에서 README가 어떻게 달라졌는지 봅니다.
git diff HEAD~1 HEAD -- README.md
```

`HEAD~1`은 현재 기록의 첫 번째 부모, 즉 이 단순한 연속 실습에서는 바로 앞 기록입니다. `--`는 뒤에 파일 이름이 온다는 구분 표시입니다. 이 명령은 조회이며 파일 내용을 바꾸지 않습니다. 복잡한 병합 이력까지 설명하는 약속으로 확대하지 않습니다.

## 8. 오류 해결과 안전한 선택 해제

일반 diff가 비어 있다고 변경이 전혀 없는 것은 아닙니다. 이미 add한 내용은 staged diff에서 확인합니다. staged diff가 비어 있다면 아직 add하지 않았거나 이미 커밋을 마쳤을 수 있습니다. status와 log를 함께 읽습니다. 새 파일은 add하기 전 일반 diff에 내용이 나타나지 않을 수 있으므로 status의 Untracked를 확인하고 편집기로 직접 읽습니다.

선택을 잘못했다면 **파일 내용을 지우지 않고 선택만 해제**할 수 있습니다. 첫 커밋이 이미 있는 이번 저장소에서 다음처럼 파일 이름을 지정합니다.

```bash
# README의 커밋 대상 선택만 해제합니다. 현재 작업 문장은 남습니다.
git restore --staged README.md
# 선택이 풀렸고 작업 변경은 남아 있는지 확인합니다.
git status
```

선택 해제는 G06의 `git restore README.md`와 다릅니다. 뒤 명령은 작업 내용이 덮어써질 수 있습니다. 단어가 비슷하다고 옵션을 빼고 실행하지 않습니다. 파일에 변경이 남아 있는 상태에서 G06으로 넘어가려면 필요한 내용을 다시 선택하고 커밋하세요. 버릴 변경이라면 먼저 별도 보존한 뒤 G06의 파일 단위 복구 설명을 읽습니다.

## 9. 확인 질문과 풀이

1. add 뒤에 다시 저장한 문장은 커밋에 자동 포함되나요? → 아닙니다. 다시 비교한 뒤 필요한 내용을 add해야 합니다.
2. status에서 같은 README가 두 부분에 나오면 파일 두 개가 있나요? → 같은 파일에 선택된 변경과 아직 선택되지 않은 변경이 함께 있습니다.
3. 일반 diff가 빈 화면이면 바로 커밋해도 될까요? → staged diff로 실제 기록 대상부터 읽어야 합니다.
4. log의 첫 글자·숫자가 예시와 다르면 실패인가요? → ID는 달라질 수 있습니다. 내 기록 제목과 순서를 확인합니다.
5. 선택을 풀면 편집 문장도 없어져야 하나요? → `restore --staged`는 선택만 해제하므로 작업 문장은 남습니다.
6. 변경된 파일 이름만 보면 충분할까요? → 같은 파일 안에 원치 않는 문장도 있을 수 있으므로 바뀐 줄까지 읽어야 합니다.

## 10. 공식 문서와 확인 범위

[차이 보기 git diff](https://git-scm.com/docs/git-diff) · [기록 보기 git log](https://git-scm.com/docs/git-log) · [다음 기록 선택 git add](https://git-scm.com/docs/git-add) · [선택과 작업 복구 git restore](https://git-scm.com/docs/git-restore)

예상 출력은 설명용 예시이며 설치 버전·출력 언어·실제 이전 문장에 따라 달라집니다. **G06으로 넘어가기 전에 반드시 `git status`에서 작업 변경이 없는 깨끗한 상태인지 확인하세요.** 마지막 선택 해제 연습으로 문장이 남았다면 필요한 문장을 다시 add·commit하고, 버릴 문장이라면 먼저 별도 보존한 뒤 G06의 파일 한 개 복구 절차를 읽습니다. 미기록 변경을 남긴 채 브랜치·병합 실습을 시작하지 않습니다.
