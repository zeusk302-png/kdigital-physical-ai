# G08 · GitHub Desktop의 화면을 하나씩 읽기

## 버튼으로 하는 Git

Git Bash에서는 `git status` 같은 명령을 직접 씁니다. GitHub Desktop에서는 같은 저장소를 열고 버튼과 목록으로 작업합니다. 저장소를 Desktop에 추가한다고 해서 별도의 Git 이력이 하나 더 생기지는 않습니다. G04에서 만든 폴더의 기록을 두 도구로 보는 것입니다.

Desktop은 Python 편집기나 실행기가 아닙니다. 파일 내용은 메모장이나 VS Code에서 고치고 저장합니다. Desktop에서는 바뀐 줄을 확인하고 어떤 변경을 기록할지 고릅니다. GitHub 웹은 인터넷에 공유된 상태를 확인하는 곳입니다.

## 먼저 같은 폴더를 엽니다

1. GitHub Desktop을 실행합니다. 시작 메뉴에서 `GitHub Desktop`을 찾습니다.
2. 메뉴 `File → Add local repository`를 선택합니다. 이름이 비슷한 `New repository`와 구별하세요. 이번에는 G04에서 만든 저장소를 열어야 합니다.
3. `Choose…`로 `GitPractice/git-class-lab` 폴더를 선택하고 `Add repository`를 누릅니다.
4. 위쪽 `Current repository`가 `git-class-lab`인지 확인합니다.
5. `Repository → Show in Explorer`로 폴더를 엽니다. G04에서 수정한 README.md가 있어야 합니다.

**예상 결과:** History에 G04·G05에서 만든 기록이 나옵니다. 기록이 없다면 다른 폴더를 열었는지 확인합니다. 바탕화면의 같은 이름 폴더를 다시 만드는 것으로 해결하지 않습니다.

## 위쪽부터 차례로 읽기

| 화면 요소 | 쉬운 뜻 | 여기서 확인할 것 |
|---|---|---|
| Current repository | 지금 보고 있는 저장소 | 같은 이름이어도 실제 폴더가 맞는지 확인 |
| Current branch | 지금 작업하는 변경 흐름 | main인지 연습 브랜치인지 확인 |
| Changes | 아직 커밋하지 않은 변경 | 파일 목록과 바뀐 줄 |
| History | 이미 커밋한 기록 | 메시지·작성자·시각·변경 내용 |
| Summary | 이번 기록의 제목 | 무엇을 왜 바꿨는지 짧게 작성 |
| Commit to … | 선택한 변경을 PC 이력에 기록 | 어느 브랜치에 기록하는지 확인 |
| Publish repository | 처음으로 호스팅 서비스에 게시 | 공개 범위·저장소 이름을 먼저 확인 |
| Fetch origin | 공유 저장소의 새 기록 확인 | 받아와야 할 변경이 있는지 확인 |
| Pull origin | 공유 기록을 내 브랜치에 반영 | 작업 중 변경이 남아 있는지 확인 |
| Push origin | 내 커밋을 공유 저장소에 보내기 | 보낼 커밋과 대상 저장소 확인 |

버튼은 현재 상태에 따라 바뀝니다. 화면에 항상 Fetch·Pull·Push가 동시에 있지는 않습니다. 로그인한 계정에 따라 접근할 수 있는 저장소도 달라집니다.

## 같은 작업을 명령과 연결하기

| 하고 싶은 일 | Git Bash | Desktop에서 볼 곳 |
|---|---|---|
| 현재 상태 읽기 | `git status` | Current branch + Changes + 위쪽 동기화 버튼 |
| 바뀐 내용 읽기 | `git diff` | Changes에서 파일 선택 |
| 이번 기록에 넣을 변경 고르기 | `git add README.md` | Changes의 파일·줄 선택 |
| PC에 기록 남기기 | `git commit -m "Update introduction"` | Summary 작성 → Commit |
| 과거 기록 보기 | `git log --oneline` | History |
| 다른 흐름에서 작업하기 | `git switch -c docs-improve` | Current branch → New branch |
| 웹의 새 기록 확인 | `git fetch origin` | Fetch origin |
| 내 PC로 반영 | `git pull --ff-only` | Pull origin — 명령의 세부 옵션과 앱의 병합 방식은 구별 |
| 공유 저장소로 보내기 | `git push` | Push origin |

Desktop의 변경 선택과 명령줄의 스테이징은 화면 동작이 완전히 같은 것은 아닙니다. 특히 Git Bash의 `git add`는 **그 시점의 내용**을 스테이징합니다. Desktop에서 고른 파일과 줄을 확인하고, 다른 창에서 파일을 더 수정했다면 커밋 전에 diff를 다시 읽으세요.

## 직접 해보기 · 두 창의 기록을 비교합니다

1. README.md 마지막에 `다음 목표: 파일 저장 기능 만들기`를 한 줄 추가하고 저장합니다.
2. Desktop의 Changes에서 README.md를 선택합니다. 추가한 줄이 초록색 `+`로 보이는지 확인합니다.
3. Git Bash에서도 같은 폴더에서 아래 명령을 한 줄씩 입력합니다.

```bash
# 현재 저장소 위치와 상태를 확인합니다. 조회만 하는 명령입니다.
pwd
git status

# 아직 커밋하지 않은 변경을 읽습니다.
git diff
```

4. Desktop에서 이번 변경을 선택하고 Summary에 `Describe next goal`을 씁니다. Commit 버튼에 표시된 브랜치가 맞는지 확인하고 커밋합니다.
5. Git Bash에서 다음을 입력합니다.

```bash
# 두 도구가 같은 저장소를 보고 있다면 방금 만든 제목이 나옵니다.
git --no-pager log --oneline -3

# 다른 변경이 없다면 working tree clean이 나옵니다.
git status
```

**확인:** Changes가 비었고 History에는 기록이 늘어납니다. 이 단계만으로 GitHub에 게시된 것은 아닙니다. 아직 원격 저장소가 없는 로컬 연습이라면 Publish repository가 보일 수 있습니다. 게시 실습은 G07·G11의 주소와 공개 범위를 확인한 뒤 진행합니다.

## 막혔을 때

- **파일을 고쳤는데 Changes가 비어 있어요:** 편집기 저장 여부 → Show in Explorer의 위치 → 실제 파일 확장자 순서로 확인합니다.
- **다른 계정의 저장소가 보여요:** `File → Options → Accounts`에서 연결 계정을 확인합니다. 다른 사람 계정을 이어서 사용하지 않습니다.
- **main으로 돌아가려는데 변경을 어떻게 할지 물어요:** 남은 변경이 어느 브랜치 작업인지 먼저 확인합니다. 버리기 버튼을 누르지 말고 현재 브랜치에서 기록할지 강사와 판단합니다.
- **같은 폴더의 버전이 서로 달라 보여요:** 두 도구의 현재 브랜치와 실제 경로를 비교합니다. 폴더명이 같다는 사실만으로 같은 저장소는 아닙니다.

## 스스로 설명하기

**질문:** Desktop의 Commit을 누른 뒤 웹을 새로고침했는데 글이 그대로입니다. 무엇을 확인해야 할까요?

**풀이:** 먼저 로컬 History에 커밋이 있는지, 원격 저장소가 연결됐는지, Push origin으로 보냈는지, 웹에서 같은 브랜치를 보고 있는지 확인합니다. 저장·커밋·push는 각각 다른 단계입니다.
