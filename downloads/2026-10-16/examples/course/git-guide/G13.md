# G13 · GitLab에서도 이어지는 Git 개념

**학습 경로: 둘러보기.** GitLab 공식 문서의 화면과 용어를 읽습니다. 별도 가입·로그인·프로젝트 생성·원격 연결은 요구하지 않습니다. 회사의 비공개 GitLab 주소나 계정이 없어도 공통 개념을 익힐 수 있습니다.

## Git과 저장소 호스팅을 다시 구별하기

Git은 파일 변경을 기록하고 브랜치를 다루는 도구입니다. GitHub와 GitLab은 Git 저장소를 서버에서 제공하고 사람들이 검토·소통하도록 돕는 서비스입니다. 메모를 쓰는 방식은 같아도 메모를 보관하고 팀원이 방문하는 사무실이 다를 수 있다고 생각해 보세요.

회사에서 GitLab을 쓴다는 말을 들었다고 `commit`, `branch`, `clone`의 의미가 사라지는 것은 아닙니다. 어느 서버에 접속하는지, 누구에게 접근 권한을 받는지, 웹에서 검토를 어느 메뉴로 하는지가 달라집니다. 서버 주소가 바뀌면 로그인과 인증 방식도 확인해야 합니다. Git 작성자 이름·이메일은 기록에 남을 정보이며 접속 권한을 주는 로그인 자체가 아닙니다.

## 같은 목적을 다른 메뉴에서 찾기

| 하려는 일 | GitHub에서 배우는 이름 | GitLab에서 만나는 이름 |
|---|---|---|
| 수정안을 검토하고 합치기 제안 | Pull request, PR | Merge request, MR |
| 오류·해야 할 일 기록 | Issues | Issues |
| 정해 둔 검사나 배포 작업 실행 | Actions의 workflow | CI/CD의 pipeline |
| 정적 웹사이트 제공 | GitHub Pages | GitLab Pages |

같은 줄의 기능은 목적을 이해하기 위한 대응입니다. 버튼·설정 파일·요금제·권한이 똑같다는 뜻은 아닙니다. GitHub Actions의 설정 파일을 이름만 바꿔 GitLab에 넣으면 그대로 동작한다고 생각하지 않습니다. 이번 수업에서는 두 서비스의 자동화 문법을 동시에 작성하지 않습니다.

GitLab의 project는 저장소와 협업 기능을 묶는 프로젝트 단위로 쓰입니다. GitHub에서 업무 진행판을 뜻하는 Projects 메뉴와 같은 의미라고 외우면 혼동합니다. “파일 프로젝트를 여는가, 여러 할 일을 보드에서 보는가”라는 실제 목적을 먼저 생각합니다.

## PR과 MR을 방향으로 읽기

GitHub에서 `readme-guide`의 변경을 `main`에 합치자고 제안했다면 GitLab에서는 같은 목적을 Merge request로 표현할 수 있습니다. GitLab의 source branch는 변경을 가져올 출발, target branch는 받아들일 대상입니다. 이름을 외우는 것보다 변경이 어느 방향으로 들어가는지 말하는 연습이 먼저입니다.

진입 위치: GitLab 프로젝트의 탐색 메뉴에서 Code → Merge requests를 찾습니다. 현재 버전과 화면 구성에 따라 위치가 달라 보일 수 있으니 메뉴 이름으로 찾습니다. 목록에서 항목을 열면 설명과 대화, 변경 내용, 커밋 등을 확인하는 화면으로 이어집니다. 비공개 프로젝트는 권한이 필요합니다. 공개 예시도 댓글이나 승인을 하려면 계정과 권한 조건을 확인해야 합니다.

가벼운 따라가기: 공식 MR 문서의 예시를 보고 종이나 메모장에 `출발: readme-guide`, `대상: main`, `이유: 실행 위치 안내 추가`, `검토: 실제 파일명과 일치하는가`를 씁니다. 이어서 GitHub의 base와 compare 중 각각 무엇에 대응하는지 말합니다. 실제 MR은 만들지 않습니다.

예상 결과: “MR은 다른 종류의 파일을 올리는 버튼”이 아니라 변경을 검토하고 합치는 제안임을 설명합니다. merge 권한과 승인 조건은 팀 정책에 따라 달라집니다. 다른 사람의 변경이 보인다고 곧바로 합칠 수 있는 것은 아닙니다.

## GitLab CI/CD와 Pages는 위치만 살펴보기

CI/CD는 코드가 바뀔 때 검사나 전달 과정을 이어 실행하는 작업 체계입니다. GitLab 문서에서 pipeline과 job이라는 단어를 보면 “전체 작업 흐름”과 “그 안의 작업 묶음”으로 먼저 이해합니다. 준비된 예시에서 성공·실패를 읽는 데 집중하고 runner 설치나 비밀키 입력을 하지 않습니다.

Pages는 정적 웹사이트를 제공하는 기능입니다. GitLab도 소스 파일을 저장했다는 사실과 사이트 배포가 성공했다는 사실은 구별해야 합니다. 서비스의 실행 자원·사용량·접근 제한 등 조건은 GitLab.com인지 회사가 운영하는 서버인지, 요금제와 관리자 정책에 따라서도 확인해야 합니다. GitHub에서 확인한 무료 범위를 GitLab에 그대로 적용하지 않습니다.

## Desktop을 사용할 때의 주의

GitHub Desktop의 “GitHub.com에 로그인”은 GitHub 계정 연결입니다. 그 버튼으로 GitLab 계정에도 로그인했다고 생각하면 안 됩니다. Git 저장소의 원격 연결과 서비스별 계정 기능은 구별해야 합니다. 회사가 지정한 도구와 인증 절차를 확인하기 전에는 기존 remote 주소를 임의로 바꾸지 않습니다.

마무리 확인: “학교에서 GitHub로 배웠는데 회사에서 GitLab을 쓰면 무엇을 이어 쓸 수 있나요?”에 답해 보세요. `저장·commit·branch·diff라는 개념은 이어 쓸 수 있고, 서버 주소·인증·웹 검토 메뉴와 팀 규칙은 새로 확인한다`가 완성 답의 예입니다.
