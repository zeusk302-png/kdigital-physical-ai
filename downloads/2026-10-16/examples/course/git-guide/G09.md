# G09 · GitHub Code에서 파일과 기록 찾기

**학습 경로: 연습.** 내 작품 저장소 또는 강사가 안내한 공개 연습 저장소를 브라우저에서 엽니다. 여기서는 파일을 읽고 주소를 확인합니다. 남의 저장소에 변경을 보내는 활동은 하지 않습니다. 공개 저장소의 기본 파일 탐색은 로그인 없이도 가능한 경우가 많지만, 비공개 저장소는 접근 권한이 필요합니다. 코드 검색은 로그인을 요구할 수 있습니다.

## 먼저 알아둘 것

웹 주소의 `github.com/소유자/저장소이름`을 봅니다. 소유자는 개인 또는 조직이고 저장소는 한 프로젝트의 파일과 기록을 담는 곳입니다. 내 계정으로 로그인해도 현재 보고 있는 저장소가 자동으로 내 것이 되지는 않습니다. 화면 위 소유자와 저장소 이름을 먼저 읽는 습관을 만듭니다.

Code 탭은 프로젝트의 파일 선반입니다. 파일 이름을 누르면 내용을 읽고, 폴더 이름을 누르면 그 안으로 들어갑니다. `.py`는 Python 코드, `.md`는 Markdown 문서, `.png`는 이미지처럼 확장자가 형식을 알려 줍니다. 파일을 웹에서 열었다고 내 PC에 저장되거나 실행된 것은 아닙니다.

## 1. README부터 읽기

README는 처음 온 사람을 위한 안내문입니다. Code 화면의 파일 목록 아래에서 보거나 `README.md` 파일을 눌러 엽니다. “무슨 작품인가, 어떻게 실행하는가, 어떤 파일이 필요한가”를 찾습니다. 설명이 없는 저장소도 있으므로 빈 부분을 내 추측으로 채우지 않습니다.

따라 하기: 내 작품의 README에서 실행 명령 한 줄을 찾습니다. `python main.py`라면 `python`은 실행 도구, `main.py`는 실행할 파일 이름입니다. 파일 목록에 실제로 `main.py`가 있는지 대조합니다. README가 `app.py`라고 쓰고 실제 파일이 `main.py`면 안내가 맞지 않습니다. 지금은 차이를 메모하고 수정은 별도 작업 단계에서 합니다.

예상 결과: 작품 소개와 실행할 파일을 내 말로 짧게 설명합니다. README에 실행 방법이 없으면 “확인할 수 없음”이라고 쓰는 것이 올바른 관찰입니다.

## 2. 브랜치와 파일 찾기

파일 목록 위의 브랜치 선택에서 현재 이름을 확인합니다. `main`이 자주 쓰이지만 모든 저장소의 기본 이름이 main인 것은 아닙니다. 브랜치를 바꾸면 같은 주소의 프로젝트에서도 보이는 파일과 문장이 달라질 수 있습니다. “없어졌다”라고 판단하기 전에 브랜치를 확인합니다.

파일명 찾기 칸이나 Go to file이 보이면 `README`를 입력해 봅니다. 이는 파일 이름을 찾는 일입니다. 코드의 내용에서 단어를 찾는 검색과 구별합니다. 상단 검색에서 저장소 범위를 선택해 `print` 같은 내용을 찾을 수도 있습니다. 로그인 안내가 나오면 코드 검색은 강사 시연으로 보고, 내 화면에서는 README를 열어 브라우저의 Ctrl+F로 한 단어를 찾습니다. Ctrl+F는 현재 화면에 있는 내용만 찾으며 저장소 전체 검색과 다릅니다.

예상 결과: “파일명은 찾았지만 내용은 아직 안 읽었다”, “현재 파일에서만 찾았다”처럼 검색 범위를 구별합니다. 검색 결과가 없다는 사실만으로 프로젝트 전체에 코드가 없다고 결론 내리지 않습니다.

## 3. History와 Blame으로 기록 읽기

History는 파일이나 저장소가 바뀐 기록을 보는 입구입니다. 파일을 연 뒤 History가 보이면 눌러 커밋 설명과 시점을 읽습니다. 기록을 선택하면 어떤 줄이 추가·삭제됐는지 비교할 수 있습니다. 초록과 빨강은 줄의 변화를 표시하는 단서이며 내용이 옳거나 틀렸다는 평가가 아닙니다.

![커밋 기록 예시](../git-starter/assets/live/06-commit-history.jpg)

Blame은 각 줄의 최근 변경과 관련 커밋을 찾는 화면입니다. 이름의 일상 뜻처럼 사람을 탓하는 버튼으로 이해하지 마세요. “이 안내 문장은 언제 바뀌었나”를 조사하는 도구입니다. 한 줄을 마지막으로 바꾼 사람이 그 기능 전체의 최초 작성자라고 단정할 수 없습니다.

따라 하기: README의 문장 하나를 고릅니다. History에서 최근 설명을 읽고, Blame이 제공되면 그 문장 옆의 기록을 살펴봅니다. 커밋이 하나뿐이면 처음 만든 기록만 보일 수 있습니다. 없는 기록을 만들려고 파일을 일부러 바꾸지 않습니다.

예상 결과: 현재 내용과 변경 기록이 별개라는 점을 설명합니다. “파일을 보기만 했는데 커밋이 생겼다”는 일은 없습니다.

## 4. Raw·ZIP·clone 구별하기

Raw는 파일의 원래 내용을 보는 기능입니다. README를 열고 Raw를 누르면 제목 꾸밈 대신 `#` 같은 Markdown 기호가 보입니다. 예쁜 안내 화면과 저장된 원문이 어떻게 연결되는지 비교해 보세요. Raw 버튼과 다운로드 아이콘은 파일 종류와 화면에 따라 다르게 보일 수 있습니다.

초록색 Code 메뉴의 Download ZIP은 선택한 버전의 파일 묶음을 받는 방법입니다. clone은 파일과 Git 이력을 작업용 저장소로 가져옵니다. ZIP을 풀어 놓은 폴더를 Desktop에서 열기만 한다고 원래 저장소의 이력이 따라오지 않습니다. 오늘 커밋·push 연습에 사용할 폴더는 clone으로 준비합니다.

![Code 메뉴에서 clone 위치 확인](../git-starter/assets/live/01-code-clone.jpg)

## 5. Tags는 특정 기록에 붙인 이름

브랜치 선택 근처의 Tags나 태그 목록을 열면 `v1.0` 같은 이름이 있을 수 있습니다. 태그는 특정 기록을 가리키는 이름으로, “이때의 버전”을 찾는 데 씁니다. 태그가 없다고 저장소가 고장 난 것은 아닙니다. 태그와 배포 안내인 Release도 같은 뜻은 아닙니다.

마무리 확인: 현재 브랜치, 실행할 파일, README의 실행 방법, 최근 기록 하나를 메모합니다. 그다음 “이 코드를 읽기만 할 때”와 “내 PC에서 수정하고 기록할 때” 각각 어디에서 무엇을 해야 하는지 설명합니다.
