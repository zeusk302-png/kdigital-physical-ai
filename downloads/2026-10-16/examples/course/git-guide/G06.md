# G06 · 브랜치로 나누어 고치고, 충돌을 읽고 복구하기

G04·G05의 **git-class-lab**을 이어서 사용합니다. Git Bash에서 `pwd`, `git status`, `git branch --show-current`를 확인하세요. 현재 브랜치가 main이고 기록할 변경이 없는 상태에서 시작합니다. README.md에 보존할 작업이 남아 있으면 먼저 정상적으로 기록하거나 별도 파일로 복사합니다. **필수 활동**은 브랜치 구별→작업 브랜치에서 수정→main으로 돌아와 차이 확인→병합입니다. **추가 활동**은 아래 충돌 재현과 중단·해결입니다. 충돌 표식을 알아보고 멈춰 상태를 읽는 일은 모두 확인합니다.

별도 파일로 복사하는 것은 보존만 하는 행동입니다. 원래 작업 폴더의 변경이 정리되어 `git status`에 `working tree clean`이 나오는 것을 확인한 뒤 아래 연습을 시작하세요.

## 1. 개념 정의 · 브랜치는 별도 작업 흐름입니다

브랜치는 저장된 커밋을 가리키는 이름이며, 기존 기록에서 갈라진 작업을 따로 이어갈 수 있게 합니다. 브랜치마다 프로젝트 폴더를 하나씩 복사하는 방식이 아닙니다. 같은 폴더에서 브랜치를 바꾸면 Git이 그 흐름에 맞는 파일 내용을 작업 폴더에 보여 줍니다. 그래서 switch 전후에 파일 내용이 달라질 수 있습니다.

`main`이라는 이름은 특별한 실행 명령이 아니라 이 실습의 기준 브랜치 이름입니다. 새 브랜치 이름은 작업 목적을 알아볼 수 있게 정합니다. 이번에는 문서 설명을 보강하는 `docs-practice`를 씁니다. 영어 소문자와 하이픈을 사용하고 공백을 넣지 않습니다.

병합, merge는 다른 브랜치의 변경을 현재 브랜치에 통합하는 행동입니다. 현재 main에서 `git merge docs-practice`를 실행하면 docs-practice의 변경을 main에 합칩니다. 어느 쪽에서 실행했는지가 중요합니다. PR은 온라인에서 변경을 비교하고 검토하는 제안 절차이며 브랜치 생성이나 로컬 merge와 같은 말이 아닙니다. 여기서는 인터넷 없이 로컬 작업 흐름부터 배웁니다.

## 2. 일상 비유 · 원본 문서와 제안 문서

모둠이 안내문을 고친다고 생각해 보세요. 기준 원고에서 한 사람은 소개 문장을 보강하고 다른 사람은 준비물을 고칩니다. 서로 다른 부분이면 비교해 함께 반영할 수 있습니다. 같은 문장을 서로 다르게 고쳤다면 기계가 어떤 뜻이 맞는지 결정하기 어렵습니다. 두 의견을 읽고 최종 문장을 정해야 합니다. 이것이 충돌을 이해하는 출발점입니다.

Git의 충돌은 컴퓨터 고장이나 누군가의 잘못을 뜻하지 않습니다. 자동 통합이 멈추고 사람이 판단해야 하는 상태입니다. 한쪽을 무조건 지우면 통과할 수는 있어도 필요한 뜻을 잃을 수 있으므로 **양쪽이 왜 고쳤는지 읽고 완성 문장을 정하는 일**이 중요합니다.

## 3. 구성요소 · 현재 위치와 통합 대상

| 항목 | 역할 | 확인 방법 |
|---|---|---|
| main | 이번 실습의 기준 기록 흐름 | branch에서 이름과 현재 표시 확인 |
| docs-practice | 문서 보강용 작업 흐름 | 이 브랜치에서만 먼저 커밋 |
| switch | 작업할 브랜치를 바꾸는 행동 | --show-current로 결과 조회 |
| merge | 대상 브랜치 변경을 현재 흐름에 통합 | 실행 전 현재 브랜치를 말하기 |
| conflict | 자동으로 합치지 못한 상태 | status와 README의 표식 읽기 |
| abort | 진행 중인 병합을 중단하는 행동 | 병합 전 깨끗한 상태에서 실습 |

main과 작업 브랜치에 커밋이 생기는 순서에 따라 병합은 빠르게 앞으로 이동하는 방식으로 끝나거나 새 병합 커밋을 만들 수 있습니다. 처음부터 모든 그래프 형태를 외우지 않아도 됩니다. 이번 첫 실습은 **main에 다른 변경이 없으므로 빠르게 통합될 수 있는 단순 흐름**입니다.

## 4. 복사 명령 · 분리해서 수정하고 합치기

```bash
# 현재 상태가 깨끗한지 먼저 봅니다.
git status
# 현재 브랜치 이름만 보여 줍니다. main이어야 합니다.
git branch --show-current
# docs-practice를 만들고 그 브랜치로 이동합니다.
git switch -c docs-practice
# 이동한 결과를 이름으로 확인합니다.
git branch --show-current
# 작업 브랜치에서 README 끝에 설명을 추가합니다.
printf '\nBranch practice: add a clear guide.\n' >> README.md
# 이번 수정 줄을 확인합니다.
git diff
# 확인한 README를 기록 대상으로 고릅니다.
git add README.md
# 선택한 설명을 작업 브랜치에 기록합니다.
git commit -m "Add branch practice guide"
# 기준 브랜치 main으로 돌아갑니다.
git switch main
# 통합하기 전에는 방금 추가한 문장이 없는지 봅니다.
cat README.md
# docs-practice의 기록을 현재 main에 합칩니다.
git merge --ff-only docs-practice
# 합친 뒤에는 문장이 나타나는지 확인합니다.
cat README.md
# 모든 브랜치의 최근 기록을 간단한 그래프로 확인합니다.
git log --oneline --graph --all -8
```

`-c`는 만들면서 이동하는 옵션입니다. `git branch docs-practice`만 실행하면 브랜치를 만들지만 자동으로 이동하지는 않는다는 차이가 있습니다. `--ff-only`는 현재 기록이 대상 기록의 앞부분으로 이어질 때만 통합하라는 뜻입니다. 이 단순 실습과 달리 양쪽에서 따로 기록을 만들었다면 거절될 수 있으며, 그때 옵션을 지우고 무작정 반복하지 않습니다.

## 5. 예상 결과 · 파일과 기록이 이동하는 모습

새 브랜치로 이동하면 `Switched to a new branch 'docs-practice'`와 비슷한 문장이 보일 수 있습니다. main으로 돌아간 뒤 README의 추가 문장이 사라져 보여도 삭제 사고라고 단정하지 않습니다. 작업 브랜치에 기록한 내용이며 main은 아직 그 기록을 포함하지 않기 때문입니다. 병합 후에는 main에서도 문장이 보입니다.

첫 병합에서는 `Fast-forward`가 나타날 수 있습니다. main이 작업 브랜치의 새 기록까지 따라갔다는 뜻입니다. 마지막 그래프에서 main과 docs-practice가 같은 커밋에 붙어 있어도 정상입니다. 그래프의 별표와 선은 커밋의 연결을 나타내며, 문서에 그대로 입력하는 기호가 아닙니다. 영어·한국어·중국어 출력이 달라도 브랜치 이름, 통합 완료 여부, status를 기준으로 확인합니다.

## 6. 추가 활동 · 같은 줄 충돌을 일부러 만들기

이 활동은 **연습 저장소에서만** 수행합니다. README를 덮어쓰는 대신 새 연습용 한 줄을 먼저 추가합니다. 이후 편집기로 그 줄만 바꿉니다. 지금 main이 깨끗한지 확인하세요. 내용이 남아 있거나 이미 다른 병합을 진행 중이라면 이 단계로 들어가지 않습니다.

```bash
# 모두가 함께 출발할 연습용 줄을 README 끝에 만듭니다.
printf '\nMeeting place: room A.\n' >> README.md
# 출발 문서를 선택합니다.
git add README.md
# 충돌 전 기준 상태를 기록합니다.
git commit -m "Add meeting place baseline"
# 같은 기준에서 제안을 만들 브랜치로 이동합니다.
git switch -c meeting-change
```

편집기에서 README의 `Meeting place: room A.`만 `Meeting place: room B.`로 바꾸고 저장합니다. 다른 줄은 유지합니다. 파일을 잘못 열지 않도록 전체 경로를 확인합니다.

```bash
# B로 바꾼 줄만 있는지 비교합니다.
git diff
# 제안 문장을 선택합니다.
git add README.md
# 작업 브랜치의 제안을 기록합니다.
git commit -m "Suggest room B"
# main으로 돌아가 같은 기준 문장을 확인합니다.
git switch main
```

이제 main의 README에는 아직 room A가 있습니다. 그 줄만 `Meeting place: room C.`로 바꾸고 저장합니다. **서로 다른 브랜치에서 같은 원문 줄을 다른 값으로 고치는 것**입니다.

```bash
# main에서 C로 바뀐 줄을 확인합니다.
git diff
# main의 제안을 선택합니다.
git add README.md
# main의 별도 기록을 만듭니다.
git commit -m "Suggest room C"
# 양쪽 기록을 합치려 시도합니다. 이번에는 충돌을 관찰하는 추가 활동입니다.
git merge meeting-change
# 자동 병합이 멈췄다면 어떤 파일인지 읽습니다.
git status
# 문서 안의 충돌 표식을 직접 읽습니다.
cat README.md
```

표식은 다음과 비슷합니다. 설정에 따라 원래 기준 내용이 추가되거나 표식 길이·레이블이 달라질 수 있습니다.

```text
<<<<<<< HEAD
Meeting place: room C.
=======
Meeting place: room B.
>>>>>>> meeting-change
```

`<<<<<<< HEAD` 아래는 지금 main 쪽 문장, `=======`는 구분선, 아래쪽은 합치려는 meeting-change 쪽 문장입니다. `>>>>>>>`는 그쪽 표시가 끝나는 곳입니다. **표식 자체를 최종 문서에 남기지 않습니다.** C와 B 중 하나를 자동 정답으로 고르지 말고 서로의 의도를 먼저 읽습니다.

## 7. 복구 연습 · 먼저 중단한 뒤 다시 판단하기

첫 번째 충돌에서는 해결하지 않고 병합을 중단합니다. 이 실습은 병합 시작 전 작업 변경이 없도록 준비했기 때문에 이전 main 상태로 돌아오는 것을 확인할 수 있습니다.

```bash
# 진행 중인 병합을 중단합니다. 평소의 파일 수정 취소 명령과 다릅니다.
git merge --abort
# 병합 중이라는 표시가 사라졌는지 확인합니다.
git status
# main의 room C 문장이 돌아왔는지 확인합니다.
cat README.md
```

`--abort`가 언제나 모든 작업을 완벽하게 복원한다는 뜻은 아닙니다. 병합 전에 미기록 변경이 있으면 재구성이 어려울 수 있으므로 시작 전에 깨끗한 상태를 확인했습니다. 오류가 나면 다른 취소 명령을 잇달아 실행하지 말고 status와 오류를 강사에게 보여 줍니다. `.git` 폴더를 삭제하는 방식으로 해결하지 않습니다.

이제 다시 `git merge meeting-change`를 실행합니다. 같은 충돌이 나타나는 것이 정상입니다. 편집기로 표식과 두 문장을 읽고, 이번 연습에서는 양쪽 제안이 남는 다음 한 줄로 바꿉니다.

```text
Meeting place: room C; room B is the backup.
```

실제 업무에서 어느 방이 맞는지는 관계자에게 확인해야 합니다. 위 문장은 실습에서 합의했다고 정한 완성 예입니다. 꺾쇠 표식 세 줄과 중복 문장을 모두 없애고 완성 문장 한 줄만 남깁니다.

```bash
# 해결한 문장과 불필요한 표식이 없는지 먼저 읽습니다.
cat README.md
# 해결 완료한 파일 내용을 고릅니다.
git add README.md
# 충돌이 해결되었으며 병합 커밋을 기다리는지 확인합니다.
git status
# 합의한 문장을 병합 기록으로 남깁니다.
git commit -m "Resolve meeting place suggestions"
# 최종 상태와 두 작업 흐름의 연결을 확인합니다.
git log --oneline --graph --all -8
```

add는 파일을 올바르게 고쳐 주는 명령이 아닙니다. **내가 고친 결과를 해결된 내용으로 선택**하는 행동입니다. 표식을 남긴 채 add해도 잘못된 문서가 기록될 수 있으므로 직접 읽는 확인이 필요합니다.

## 8. 파일 한 개의 선택 취소와 내용 복구

이 절은 서로 다른 취소를 비교하는 참고입니다. 병합 중이 아닌 깨끗한 main에서 시작하고, 먼저 편집기로 README에 `Temporary practice line.`을 추가해 저장합니다. 필요하면 저장소 밖의 별도 보존 폴더에 복사합니다. 복사본에 같은 이름을 사용하더라도 원본을 덮어쓰지 않게 구별하세요.

```bash
# 어떤 문장을 취소하려는지 먼저 읽습니다.
git diff -- README.md
# 실습 문장을 일단 선택합니다.
git add README.md
# 선택만 취소합니다. 편집한 문장은 작업 파일에 남습니다.
git restore --staged README.md
# 문장이 아직 남았는지 확인합니다.
git diff -- README.md
```

여기서 멈춰 어떤 문장을 없앨지 말하세요. **다음 명령은 미기록 작업 내용을 덮어쓸 수 있습니다.** 별도 보존을 확인했고 이 연습 문장을 버리기로 한 경우에만 파일 이름을 지정하여 실행합니다.

```bash
# 현재 스테이징 내용으로 README 작업 파일을 되돌립니다. 위에서 선택을 풀어 현재 기준과 같게 했습니다.
git restore README.md
# 연습 문장만 없어졌는지 파일을 읽습니다.
cat README.md
# 남은 변경이 없는지 확인합니다.
git status
```

옵션 없는 restore는 기본적으로 스테이징 영역 내용을 작업 파일로 가져옵니다. 따라서 항상 마지막 커밋으로 돌아간다고 외우면 틀릴 수 있습니다. 이번에는 먼저 선택을 해제해 스테이징을 마지막 커밋과 맞췄습니다. 새 파일이나 다른 파일까지 일괄 지우는 `.` 범위 취소는 사용하지 않습니다. 커밋하지 않은 내용을 지운 뒤 Git이 언제나 복구해 줄 것이라고 생각하지 않습니다. 이미 커밋한 이력을 취소하는 작업은 별도 개념이므로 여기서는 이력 삭제 명령을 다루지 않습니다.

## 9. 오류와 확인 질문 풀이

- 브랜치가 이미 있다는 오류: 같은 이름을 반복 생성했을 수 있습니다. branch 목록을 읽고 이미 있는 연습을 이어갈지 강사와 결정합니다. 삭제부터 하지 않습니다.
- switch가 파일 덮어쓰기를 경고: 미기록 변경이 있습니다. 필요한 내용을 보존하거나 커밋한 뒤 이동합니다. 강제로 이동하는 옵션으로 우회하지 않습니다.
- `Not possible to fast-forward`: 양쪽에서 기록이 갈라졌을 수 있습니다. 현재 브랜치와 log를 읽습니다. 곧바로 강제 push나 이력 초기화를 하지 않습니다.
- `There is no merge to abort`: 진행 중인 병합이 아닐 수 있습니다. status로 확인하며 여러 취소를 반복하지 않습니다.

질문 1. branch를 만들면 PR도 생기나요? → 아닙니다. PR은 온라인 검토 제안으로 별도 생성합니다.

질문 2. 충돌이면 파일을 통째로 지워야 하나요? → 아닙니다. 서로 다른 의도를 읽고 최종 내용으로 합치거나 진행 중 병합을 중단합니다.

질문 3. restore --staged와 restore는 같은가요? → 앞은 선택 해제, 뒤는 작업 파일 내용을 복원하므로 미기록 편집이 없어질 수 있습니다.

질문 4. main에서 merge한 뒤 작업 브랜치를 꼭 즉시 지워야 하나요? → 아닙니다. 통합 결과 확인이 먼저이며 이번 실습은 브랜치를 보존해 흐름을 관찰합니다.
