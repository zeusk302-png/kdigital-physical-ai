# G07 · 내 기록을 다른 저장소와 주고받기

이 단원은 두 경로를 분리합니다. **필수 로컬 경로**는 네트워크·계정 없이 컴퓨터 안의 다른 저장소와 clone/fetch/pull/push를 연습합니다. **선택 온라인 경로**는 본인 GitHub 저장소에 연결하고 인증하는 절차를 설명합니다. 온라인에는 인터넷·본인 계정·접근 권한이 필요합니다. 강의 자료에 들어 있는 실제 주소로 임의 push하지 않습니다.

연습 전체는 기존과 같은 **git-class-lab** 폴더 안에서 진행합니다. G04~G06의 README와 .git은 보존하고, 그 안에 새로운 `remote-practice` 폴더를 만들어 원격 모형을 둡니다. 원래 연습 저장소에는 이 하위 연습 묶음을 add하지 않습니다. 마지막의 상태 설명을 읽고 두 종류 저장소를 구별하세요.

## 1. 개념 정의 · clone, 원격, origin

clone은 이미 있는 저장소의 파일과 커밋 이력을 가져와 새 작업 폴더를 만드는 일입니다. ZIP 다운로드는 보통 이력과 연결 설정이 없으므로 같은 연습이 아닙니다. 이미 clone한 폴더 안에서 같은 저장소를 또 clone할 필요는 없습니다. 처음 가져올 때 한 번, 이후 새 기록을 확인할 때 fetch/pull을 사용합니다.

원격 저장소, remote repository는 내 작업 저장소가 기록을 주고받을 대상으로 연결한 다른 저장소입니다. 보통 인터넷 서버에 있지만 같은 컴퓨터의 다른 경로도 대상이 될 수 있습니다. `origin`은 그 연결 주소에 붙이는 별명입니다. clone하면 기본적으로 이 이름이 만들어집니다. origin이라는 이름이 GitHub 자체를 뜻하거나 권한을 주는 것은 아닙니다.

fetch는 연결된 저장소의 새 기록을 가져와 **상대 기록을 가리키는 내 저장소의 정보**를 갱신합니다. 보통 현재 README 작업 내용은 그대로입니다. pull은 가져온 기록을 현재 작업 흐름에 통합하려는 행동입니다. push는 내 커밋을 대상 저장소에 보내는 행동입니다. 파일을 저장하기만 하거나 add하기만 한 내용은 push할 커밋이 아닙니다.

## 2. 일상 비유 · 공용 보관함과 개인 작업대

공용 보관함에 안내문을 보관하고 각자 개인 책상에서 고친다고 생각해 보세요. clone은 공용 보관함의 기록을 가져와 내 작업대를 준비하는 일, fetch는 보관함의 새 기록을 받아 살펴보는 일, pull은 그 새 기록을 내 문서에도 반영하는 일, push는 내 기록을 공용 보관함에 보내는 일입니다.

이 비유에서도 모든 내용이 즉시 자동 동기화되지는 않습니다. 두 사람이 다른 기록을 만들면 확인과 통합이 필요합니다. push가 거절되었을 때 보관함을 내 것만 남기고 덮는 방식은 기본 해결책이 아닙니다. 무엇이 달라졌는지 먼저 확인합니다.

## 3. 구성요소 · 컴퓨터 안에서 세 역할 만들기

| 이름 | 역할 | 사람이 파일을 고치나요? |
|---|---|---|
| shared.git | 공용 보관함 역할의 bare 저장소 | 이 안의 관리 파일은 직접 고치지 않음 |
| learner-one | 첫 번째 사람 작업 폴더 | README.md를 편집하고 커밋 |
| learner-two | 두 번째 사람 작업 폴더 | 받아 온 README를 읽고 비교 |
| origin/main | 상대 main을 마지막으로 확인한 내 쪽 정보 | fetch로 갱신 |
| main | 내가 지금 작업하는 브랜치 | commit이나 pull로 이동 가능 |

bare 저장소는 일반 작업 파일을 펼쳐 놓지 않고 기록을 받도록 만든 저장소입니다. 이 실습에서는 서버 대신 쓰지만 실제 인터넷 서비스가 생기는 것은 아닙니다. `origin/main`은 원격 서버 자체가 아니라 **내가 마지막으로 가져온 원격 main 정보**이므로 서버의 현재 상태와 시차가 있을 수 있습니다.

## 4. 준비 · 하위 연습 공간 만들기

G06의 원래 git-class-lab에서 병합이 끝났고 작업 변경이 없는 상태인지 먼저 확인합니다. 아래 `remote-practice`가 이미 있으면 재사용 여부를 강사와 정하고 삭제나 덮어쓰기를 하지 않습니다. 이 명령들은 Git Bash용이며 `..`는 현재 폴더의 부모 위치를 뜻합니다.

```bash
# 현재 위치가 기존 git-class-lab인지 확인합니다.
pwd
# 기존 연습 저장소가 깨끗한지 확인합니다.
git status
# 원격 실습만 넣을 새 하위 폴더를 만듭니다.
mkdir remote-practice
# 원격 실습 폴더로 이동합니다.
cd remote-practice
# 인터넷 대신 쓸 공용 보관함을 만들고 기준 브랜치를 main으로 지정합니다.
git init --bare -b main shared.git
# 공용 보관함을 첫 작업 폴더로 가져옵니다.
git clone shared.git learner-one
# 첫 번째 작업 폴더로 들어갑니다.
cd learner-one
# 이 작업 저장소에만 작성자 이름을 정합니다.
git config --local user.name "Git Learner One"
# 이 작업 저장소에만 연습용 이메일을 정합니다.
git config --local user.email "learner@example.invalid"
# 공용으로 주고받을 README를 처음 만듭니다.
printf '# Shared Practice\nVersion: one.\n' > README.md
# README를 첫 기록 대상으로 선택합니다.
git add README.md
# 첫 번째 공유 기록을 만듭니다.
git commit -m "Start shared practice"
# 대상 주소의 별명을 조회합니다.
git remote -v
# 내 main 기록을 공용 보관함 main에 보내고 기본 연결을 기억합니다.
git push -u origin main
```

빈 저장소를 clone했을 때 `You appear to have cloned an empty repository`와 비슷한 안내가 나올 수 있습니다. 아직 파일·커밋이 없는 공용 보관함을 가져왔으므로 이 단계에서는 예상된 안내입니다. `-u`는 이후 현재 브랜치가 주고받을 기본 대상 브랜치를 기억하게 하는 옵션입니다. 처음 전송에서 `new branch main -> main`과 비슷한 뜻을 확인합니다.

`git remote -v`의 `-v`는 주소를 자세히 보여 주라는 옵션입니다. 같은 origin이 fetch용과 push용으로 두 줄 보일 수 있습니다. 사용자 이름이나 주소가 예시와 달라도 **현재 저장소의 대상이 shared.git인지** 확인합니다. 암호나 토큰이 포함된 주소를 사용하지 않으며 그런 화면을 공유하지 않습니다.

## 5. 복사 명령 · 다른 작업 폴더에서 받기

```bash
# 원격 실습의 부모 폴더로 올라갑니다.
cd ..
# 같은 공용 보관함을 두 번째 작업 폴더로 가져옵니다.
git clone shared.git learner-two
# 두 번째 작업 폴더로 들어갑니다.
cd learner-two
# 여기에서 사용할 작성자 이름을 저장소에만 정합니다.
git config --local user.name "Git Learner Two"
# 여기에서도 사용자 전체 설정을 바꾸지 않습니다.
git config --local user.email "learner@example.invalid"
# 처음 받은 README에 Version: one이 있는지 읽습니다.
cat README.md
# 현재 브랜치가 main인지 봅니다.
git branch --show-current
# 연결 주소와 방향 표시를 확인합니다.
git remote -v
```

두 작업 폴더의 README는 처음에는 같지만 서로 다른 파일입니다. 한쪽 파일을 편집한다고 다른 쪽 파일이 즉시 바뀌지 않습니다. 이제 첫 번째 작업 폴더에서만 새 줄을 기록해 보냅니다.

```bash
# 원격 실습의 부모 폴더로 이동합니다.
cd ..
# 첫 작업 폴더로 이동합니다.
cd learner-one
# 공용으로 알릴 새 설명을 끝에 붙입니다.
printf 'Notice: bring a notebook.\n' >> README.md
# 변경 줄을 확인합니다.
git diff
# 이번 설명을 선택합니다.
git add README.md
# 첫 작업자의 새 기록을 만듭니다.
git commit -m "Add preparation notice"
# 공용 보관함에 새 기록을 보냅니다.
git push origin main
# 부모 폴더로 이동합니다.
cd ..
# 두 번째 작업 폴더로 돌아옵니다.
cd learner-two
# 아직 새 설명이 없는지 먼저 읽습니다.
cat README.md
```

두 번째 폴더의 README에 아직 공책 안내가 없는 것은 정상입니다. **push한 저장소와 내가 보고 있는 작업 폴더가 다르기 때문**입니다. 두 번째 폴더에서 가져오기와 반영을 따로 비교합니다.

```bash
# 공용 보관함의 새 기록을 가져오되 지금 작업 문서는 그대로 둡니다.
git fetch origin
# fetch만 했으므로 README가 그대로인지 확인합니다.
cat README.md
# 내가 아직 포함하지 않은 원격 쪽 기록을 조회합니다.
git log --oneline main..origin/main
# 상대 기록이 내 기록을 그대로 이어갈 수 있을 때만 main에 반영합니다.
git pull --ff-only origin main
# 이제 공책 안내가 README에 나타났는지 확인합니다.
cat README.md
# 현재 상태와 다음에 주고받을 연결을 확인합니다.
git status
```

`main..origin/main`은 여기서 main에는 없고 origin/main에는 있는 기록을 조회하는 범위입니다. 파일을 고치는 명령이 아닙니다. fetch 후에는 원격 쪽 새 커밋이 조회되지만 현재 README는 아직 그대로일 수 있습니다. pull 후에는 `Fast-forward`와 비슷한 문구와 함께 README에 새 설명이 나타납니다. 이미 최신이라면 `Already up to date`와 같은 뜻으로 끝날 수 있습니다. 영어·한국어·중국어 출력에서도 **기록 가져옴과 작업 파일 반영**을 구별합니다.

## 6. 변경 실습 · 역할을 바꾸어 전송하기

필수 실습입니다. 현재 learner-two에서 README에 `Checked by learner two.` 한 줄을 편집기로 추가하고 저장합니다. diff→add→staged diff→commit을 수행한 뒤 `git push origin main`을 실행하세요. learner-one으로 이동해 **fetch 직후 cat 결과**와 **pull --ff-only 직후 cat 결과**를 비교합니다.

짝에게 다음 세 가지를 설명합니다. 첫째, 어느 폴더가 현재 작업 폴더인가요? 둘째, 공용 보관함에는 기록이 도착했나요? 셋째, 반대쪽 작업 폴더에는 그 기록이 반영되었나요? 단순히 창에서 오류가 없다는 것만으로 세 상태를 모두 같다고 판단하지 않습니다. 이 활동은 로컬 경로를 사용하므로 인터넷 서버의 상태나 GitHub 인증 성공을 증명하지 않습니다.

## 7. 오류 해결 · 거절되었으면 방향부터 확인

- `destination path ... already exists`: 같은 폴더에 이미 clone했을 수 있습니다. 폴더 내용을 확인하고 기존 작업을 이어갈지 결정합니다. 삭제부터 하지 않습니다.
- `does not appear to be a git repository`: 주소나 현재 위치를 확인합니다. shared.git과 learner-one/learner-two의 부모 관계가 달라졌는지 `pwd`와 `ls`로 확인합니다.
- `src refspec main does not match any`: main에 첫 커밋이 없거나 브랜치 이름이 다를 수 있습니다. `git branch --show-current`, `git log --oneline -3`으로 확인합니다.
- `non-fast-forward` 또는 `fetch first`: 상대에 내가 아직 포함하지 않은 기록이 있을 수 있습니다. status→fetch→log로 차이를 읽습니다. 강제 push로 덮어쓰지 않습니다.
- `pull --ff-only`가 거절: 양쪽이 각각 새 커밋을 만들었을 수 있습니다. 이는 안전하게 자동 반영을 멈춘 것입니다. `--ff-only`를 빼고 반복하기 전에 G06의 브랜치 그래프와 통합 개념을 강사와 확인합니다.
- 미기록 파일을 덮어쓴다는 경고: 작업 중 내용을 보존하거나 커밋한 뒤 다시 확인합니다. 옵션을 강하게 바꾸어 경고를 없애는 활동이 아닙니다.

원래 git-class-lab로 돌아와 status를 보면 remote-practice가 새 폴더로 보일 수 있습니다. 이것은 실습용 저장소들을 그 안에 만들었기 때문입니다. **원래 저장소에서 `git add .`로 묶어 기록하지 않습니다.** 작업 위치가 learner-one인지 learner-two인지 원래 git-class-lab인지 매번 확인합니다. 오늘은 하위 실습 폴더를 그대로 보존하며 자동 삭제 명령을 실행하지 않습니다.

## 8. 선택 온라인 경로 · 본인 GitHub에서만

인터넷 사용과 본인 계정 로그인이 끝난 경우에만 진행합니다. 온라인 경로는 앞의 로컬 연습과 별개입니다. 이미 수업의 GitHub Desktop으로 clone한 저장소가 있다면 그 폴더를 사용해도 되며, 같은 저장소를 또 복제할 필요가 없습니다. 새로 clone한다면 git-class-lab의 빈 하위 위치를 선택하고 실제 본인 저장소의 Code 메뉴에서 HTTPS 주소를 복사합니다.

아래 `YOUR-USERNAME`과 `YOUR-REPOSITORY`는 그대로 쓰는 글자가 아닙니다. **본인 주소로 바꾼 다음** 한 줄씩 실행합니다. 강의 저장소 주소나 짝의 주소를 내 것처럼 쓰지 않습니다. 이미 연결된 origin이 있는 폴더에서는 remote add를 다시 하지 않습니다.

```bash
# 본인 주소로 바꾼 저장소를 새 online-work 폴더에 가져옵니다.
git clone https://github.com/YOUR-USERNAME/YOUR-REPOSITORY.git online-work
# 방금 만든 온라인 작업 폴더에 들어갑니다.
cd online-work
# 연결 대상이 본인 저장소인지 확인합니다.
git remote -v
# 온라인으로 새 기록을 만들기 전에 본인 작성자 이름을 이 저장소에 정합니다.
git config --local user.name "Your Name"
```

이메일은 GitHub Settings → Emails에서 확인한 **본인 noreply 주소**로 직접 설정합니다. 복사 예시의 연습용 이메일을 공개용 주소로 착각하지 않습니다. 다음 틀의 큰따옴표 안을 실제 주소로 바꿉니다. 실제 주소를 강사 화면에 공개할 필요는 없습니다.

```bash
# 큰따옴표 안을 본인의 noreply 주소로 바꿔 이 저장소에만 설정합니다.
git config --local user.email "YOUR-NOREPLY-ADDRESS"
# 이 저장소의 새 기록에 사용할 이메일을 본인 화면에서 확인합니다.
git config --local --get user.email
```

이미 로컬에서 시작한 **별도 본인 프로젝트**를 빈 GitHub 저장소에 연결하는 경우에는 clone 대신 remote를 추가하는 경로가 있습니다. 이것은 위 clone 경로의 다음 단계가 아니라 다른 출발 경로입니다. 로컬 공용 보관함 실습의 origin을 바꾸는 명령으로 사용하지 않습니다.

```bash
# 아직 origin이 없는 본인 프로젝트인지 조회합니다.
git remote -v
# 주소를 본인 빈 저장소로 바꾼 뒤 연결 별명을 추가합니다.
git remote add origin https://github.com/YOUR-USERNAME/YOUR-REPOSITORY.git
# 내 로컬 main 기록을 본인 원격 main에 전송합니다.
git push -u origin main
```

위 명령은 주소와 권한이 준비되면 실제 전송을 수행합니다. 학생 본인이 공개 범위를 확인한 자기 자료에만 사용합니다. 저장소를 만드는 과정에서 원격 README도 만들었다면 이미 별도 커밋이 있으므로 위 빈 저장소 경로와 다릅니다. 거절되면 강사와 두 이력을 확인하고 강제 전송하지 않습니다.

HTTPS 인증에서는 설치된 Git Credential Manager 등이 브라우저 로그인을 안내할 수 있습니다. 인증 방법은 학교 환경과 계정 정책에 따라 다릅니다. GitHub 웹 비밀번호를 Git 명령용 비밀번호로 반복 입력하는 방식으로 해결하지 않습니다. 토큰·비밀번호·인증 코드·복구 코드를 README, 명령 예제, 실습지에 적지 않습니다. 인증 실패는 작성자 설정과 다른 문제입니다. 오류의 서비스·계정·권한을 확인하고, 막히면 앞의 네트워크 없는 경로를 계속합니다.

온라인 push 후에는 GitHub에서 **저장소 주소, 브랜치 이름, 최근 커밋, 변경된 README 내용**을 확인합니다. 브라우저 캐시나 다른 브랜치를 보고 있는 경우도 있으므로 주소만 열렸다고 업로드 확인을 마치지 않습니다. 반대로 웹에서 README를 고쳤다면 PC에서는 fetch로 새 기록을 읽고 pull --ff-only로 반영해야 합니다.

## 9. 확인 질문과 풀이

1. clone은 매번 새 기록을 받을 때 쓰나요? → 처음 새 작업 폴더를 만들 때 사용하고, 이후 보통 fetch/pull을 사용합니다.
2. origin이 있으면 GitHub 계정 인증도 된 건가요? → 아닙니다. 주소의 별명이 있다는 뜻이며 인증과 권한은 별도입니다.
3. fetch 직후 README가 안 바뀌면 실패인가요? → 새 원격 기록을 가져왔어도 현재 작업 문서는 그대로일 수 있습니다.
4. push 전에 파일을 저장만 하면 되나요? → 변경 확인과 add·commit이 필요합니다. push는 커밋을 보냅니다.
5. --ff-only 거절을 없애려고 무조건 강제 push하나요? → 아닙니다. 갈라진 이력과 보존할 변경부터 확인합니다.
6. 로컬 shared.git 전송 성공은 GitHub 게시 성공인가요? → 아닙니다. 컴퓨터 안에서 기록을 주고받은 결과이며 온라인 인증·전송·웹 확인은 따로 수행합니다.
