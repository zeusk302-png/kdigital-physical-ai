### A01 · 파일과 브라우저의 관계

<!-- enrichment:2026-10-21:P1 -->

#### 사례로 이해하기 · 문서의 의미와 화면 표시를 분리하기


#### 실무 상황

작업장 안내판의 제목을 바꿨는데 브라우저 탭 이름은 예전대로입니다. 파일 이름도 달라지지 않았습니다. 제목이라는 말이 세 곳에 쓰이지만 파일 이름, 탭 이름, 본문 제목은 각각 다른 정보입니다. 어디를 바꿨고 어떤 결과를 기대했는지 먼저 정해야 합니다.

#### 쉬운 풀이

HTML은 문서 내용과 의미를 표시하는 글입니다. 태그는 내용을 감싸며 역할을 붙이는 표시입니다. h1은 본문의 큰 제목 역할이고 title은 브라우저 탭의 이름입니다. 속성은 태그에 붙이는 추가 정보이며 id는 프로그램이 특정 요소를 찾는 이름입니다. 편집기는 글을 고치는 곳, 브라우저는 문서를 읽어 화면으로 보여 주는 곳입니다. 확장자 .html은 파일 종류를 나타내며 .html.txt와 구별합니다.

#### 완성 예와 단계 풀이

아래 문서를 안내.html로 저장합니다. 꺾쇠와 닫는 태그를 유지하고 한글 내용만 읽습니다.

```html
<!doctype html>
<html lang="ko"><head><meta charset="utf-8"><title>작업장</title></head>
<body><h1>센서 안내</h1><button id="check">값 확인</button></body></html>
```

첫 줄은 HTML 문서 형식, lang은 한국어 정보, charset은 한글을 읽는 문자 규칙입니다. head는 문서 정보, body는 보이는 내용입니다. 브라우저에서 탭은 작업장, 본문은 센서 안내, 버튼은 값 확인으로 보입니다. 버튼은 아직 동작 코드가 없으므로 누른다고 센서 값을 읽지 않습니다. 저장한 같은 파일을 열고 수정 뒤 새로고침합니다.

#### 독립 추가 복습 과제

탭은 “공장 A”, 본문 제목은 “온도 확인”, 버튼은 “기록 조회”로 작성하되 버튼 id는 check를 유지하세요. 이어서 id까지 바꾸면 뒤의 JavaScript 연결에 어떤 확인이 필요한지 설명하세요.

#### 답과 대표 오답

title과 h1과 버튼 사이 글자를 각각 바꾸며 id는 유지합니다. “글자 크기가 같으면 제목 역할도 같다”는 답은 의미와 모양을 혼동합니다. “버튼이 보이면 데이터 연결도 됐다”는 답에는 동작 확인이 빠졌습니다.

#### 확인 질문과 해설

① 저장만 하면 화면이 자동 갱신되나요? 제공 정적 파일은 새로고침이 필요합니다. ② id는 사용자 문구인가요? 내부에서 찾는 이름입니다. ③ 한글이 깨지면 무엇을 확인하나요? 파일 저장 인코딩과 charset, 실제 열린 경로를 확인합니다.


**뜻과 비유.** 브라우저는 HTML 문서를 읽어 화면으로 보여 주는 프로그램입니다. 파일을 편집하는 창과 결과를 보는 창은 역할이 다릅니다.

**왜 필요한가.** 어디에 썼는지와 무엇을 열었는지를 구분해야 저장한 변경을 다시 확인할 수 있습니다.

**예를 따라 읽기.** work/static/index.html을 편집하고 같은 파일을 브라우저로 열면 제공 안내판을 볼 수 있습니다.

**헷갈리는 반례.** 코드 편집기에 글자를 바꾼 것만으로 이미 열린 화면이 자동 갱신되는 것은 아닙니다.

**직접 적용.** course 폴더를 압축 풀기 → work/static/index.html 경로 적기 → 브라우저에서 안내판 열기 → 편집·저장·새로고침 순서를 말하기

**설명할 질문.** 편집 창과 브라우저 화면은 어떻게 다른가요?

**막혔을 때.** 확장자가.txt로 붙었으면 파일 이름과 종류를 확인합니다. ZIP 안의 미리 보기에서 편집하지 않습니다.

### A02 · HTML 태그와 문서 의미

**뜻과 비유.** HTML은 제목·문단·버튼 같은 내용의 의미를 표시하는 문서 형식입니다. 여는 태그와 닫는 태그 사이의 내용이 하나의 요소가 됩니다.

**왜 필요한가.** 보기에 큰 글자를 만드는 것과 문서의 제목이라는 의미를 주는 것을 구별해야 내용 구조를 읽을 수 있습니다.

**예를 따라 읽기.** `<h1>입구 센서 안내판</h1>`에서 h1은 주요 제목, 안의 글자는 화면 내용입니다.

**헷갈리는 반례.** 모든 글자를 h1으로 만들면 크기가 같아질 수 있어도 제목과 설명의 관계가 흐려집니다.

**직접 적용.** 전체 HTML에서 h1·p·button 찾기 → 여는 태그와 닫는 태그 짝 표시하기 → 제목 글자만 창고 센서 안내판으로 바꾸기 → 저장 후 어떤 내용이 바뀌었는지 확인하기

**설명할 질문.** h1과 CSS 글자 크기는 왜 같은 역할이 아닌가요?

**막혔을 때.** 태그 꺾쇠를 지웠다면 원본의 해당 줄과 비교합니다. 제목 문구와 title 탭 이름은 다른 위치입니다.

입력·답칸·확인 순서는 [실습지의 A02](practice-guide.md#a02)와 [활동 원문](examples/course/data/A02_input.md)에 있습니다.

### A03 · 속성·연결·접근성

**뜻과 비유.** 속성은 요소에 추가 정보를 붙이는 이름과 값입니다. lang은 문서 언어, id 는 특정 요소를 찾는 이름, type은 버튼 동작 종류를 설명합니다.

**왜 필요한가.** 사람이 보는 문구와 프로그램이 찾는 이름을 구분해야 버튼 연결을 끊지 않고 내용을 수정할 수 있습니다.

**예를 따라 읽기.** id ="check"는 JavaScript가 버튼을 찾는 기준이고 버튼 안 글자는 사용자에게 보이는 안내입니다.

**헷갈리는 반례.** id를 임의로 바꾸고 연결 코드를 그대로 두면 화면은 보여도 버튼 반응이 사라질 수 있습니다.

**직접 적용.** lang·id·type 속성 찾기 → 보이는 글자와 내부 이름 나누기 → 버튼 문구만 값 다시 확인으로 바꾸기 → Tab 키로 버튼에 이동해 테두리 보기

**설명할 질문.** 사용자에게 보이는 이름과 코드가 찾는 이름은 왜 구분하나요?

**막혔을 때.** 버튼 반응이 없으면 id와 선택자 #check가 같은지 봅니다. 화면 문구를 바꾸려면 태그 사이를 고칩니다.

입력·답칸·확인 순서는 [실습지의 A03](practice-guide.md#a03)와 [활동 원문](examples/course/data/A03_input.md)에 있습니다.

### A04 · CSS 선택자와 선언

<!-- enrichment:2026-10-21:P2 -->

#### 사례로 이해하기 · 선택자와 상자 모델로 읽기 편한 화면 만들기


#### 실무 상황

센서 카드의 글자가 테두리에 붙어 읽기 어렵습니다. 카드 사이 간격도 좁습니다. 글자만 띄우려다가 페이지 전체를 오른쪽으로 밀면 작은 화면에서 내용이 잘립니다. 어떤 상자의 어느 공간을 바꾸는지 먼저 그려 봅니다.

#### 쉬운 풀이

CSS는 문서의 모양을 정하는 규칙입니다. 선택자는 꾸밀 대상을 고르는 이름이고 선언은 속성과 값의 짝입니다. 중괄호 안의 `color: teal;`은 글자색을 청록으로 정합니다. 세미콜론은 선언의 끝입니다. 상자에서 content는 내용, padding은 내용과 테두리 사이, border는 테두리, margin은 다른 상자와의 바깥 간격입니다. 색과 여백은 온도 데이터의 의미를 바꾸지 않습니다.

#### 완성 예와 풀이

앞 문서의 head 안에 style 태그로 아래 규칙을 넣습니다.

```css
body { margin: 16px; font-family: sans-serif; }
h1 { color: teal; }
button { padding: 12px; margin-top: 8px; }
button:focus-visible { outline: 3px solid black; }
```

body 규칙은 전체 가장자리와 글꼴, h1 규칙은 제목만, button 규칙은 버튼 안팎 공간을 조절합니다. 마지막 규칙은 키보드로 이동할 때 초점을 표시합니다. 저장 후 새로고침하고 Tab 키로 버튼에 이동합니다. 초점은 지금 키보드로 조작할 대상이며 색 표시만으로 정상 상태를 전달하지 않듯 초점도 보이게 제공합니다. 별도 style.css를 쓰면 HTML의 link 경로가 같은 파일을 가리키는지도 확인합니다.

#### 독립 추가 복습 과제

버튼 글자 주변 공간만 늘리고 버튼과 제목 사이 공간은 유지하려면 어떤 속성을 바꾸나요? 다음으로 정상 상태를 녹색 원 하나로만 보여 주는 화면을 글자와 함께 표현하는 문장을 작성하세요.

#### 답과 대표 오답

안쪽 공간은 padding입니다. 상태 문장은 “정상: 제공된 가상 온도가 기준 미만입니다”처럼 뜻을 적습니다. margin을 늘리는 답은 바깥 공간을 바꿉니다. “색을 더 진하게 하면 의미가 전달된다”는 답은 색을 구별하기 어려운 상황을 해결하지 못합니다.

#### 확인 질문과 해설

① CSS 변경으로 센서값이 변하나요? 표시 모양만 달라집니다. ② 적용이 안 되면 무엇부터 보나요? 저장·경로·선택자·새로고침을 확인합니다. ③ 좁은 화면도 확인하는 이유는 무엇인가요? 읽기 폭과 넘침은 큰 화면에서 보이지 않을 수 있습니다.


**뜻과 비유.** CSS는 어떤 요소에 어떤 모양을 적용할지 쓰는 규칙입니다. 선택자는 대상을 고르고, 속성과 값은 색·크기·간격을 정합니다.

**왜 필요한가.** 내용과 모양을 나누면 같은 제목을 유지하면서 여러 화면 크기에 맞게 조정할 수 있습니다.

**예를 따라 읽기.** h1 { color: #126d65; }는 제목 글자의 색을 정합니다. #126d65는 색을 나타내는 표기입니다.

**헷갈리는 반례.** 색을 바꿔도 센서 온도의 데이터 값이 바뀌는 것은 아닙니다.

**직접 적용.** style.css에서 h1 규칙 찾기 → color와 값의 경계 표시하기 → 색을 #75421b로 바꾸기 → 같은 제목 내용이 유지되는지 비교하기

**설명할 질문.** CSS 값을 바꿨을 때 무엇이 유지돼야 하나요?

**막혔을 때.** CSS가 적용되지 않으면 HTML의 href와 파일 이름이 일치하는지 먼저 확인합니다.

입력·답칸·확인 순서는 [실습지의 A04](practice-guide.md#a04)와 [활동 원문](examples/course/data/A04_input.md)에 있습니다.

### A05 · 상자·여백·읽기 폭

**뜻과 비유.** 브라우저의 요소는 화면 공간을 차지하는 상자로 배치됩니다. padding은 안쪽 간격, margin 은 바깥 간격이며 max-width 는 너무 넓어지지 않게 제한합니다.

**왜 필요한가.** 문장이 화면 끝까지 길어지거나 요소가 붙어 있으면 내용을 읽기 어렵습니다. 간격도 정보 전달에 영향을 줍니다.

**예를 따라 읽기.** main의 padding:24px을 32px로 바꾸면 안내판 내용과 바깥 영역 사이의 안쪽 간격이 커집니다.

**헷갈리는 반례.** 글자를 작게 줄여 모든 것을 한 화면에 넣는 방식은 초심자의 읽기를 어렵게 할 수 있습니다.

**직접 적용.** main의 세 배치 규칙 찾기 → padding과 margin 을 그림으로 구분하기 → padding 한 값을 바꿔 비교하기 → 글자 크기와 읽기 폭의 영향을 설명하기

**설명할 질문.** 안쪽 여백과 바깥 여백은 어떻게 구분하나요?

**막혔을 때.** 차이가 안 보이면 같은 파일을 저장했는지와 브라우저 새로고침 여부를 확인합니다.

입력·답칸·확인 순서는 [실습지의 A05](practice-guide.md#a05)와 [활동 원문](examples/course/data/A05_input.md)에 있습니다.

### A06 · 작은 화면과 상태의 표시

**뜻과 비유.** 반응형 규칙은 화면 폭 같은 조건에 따라 모양을 조정하는 CSS입니다. 색만으로 의미를 전달하지 않고 글자와 구조도 함께 사용합니다.

**왜 필요한가.** 같은 자료를 좁은 화면과 키보드로도 읽을 수 있어야 업무 확인에 사용할 수 있습니다.

**예를 따라 읽기.** max-width:600px 조건에서는 main의 바깥 간격이 8px로 바뀝니다. focus-visible은 키보드 초점을 드러냅니다.

**헷갈리는 반례.** 초록색만 보고 정상이라고 판단하게 하면 색을 구분하기 어렵거나 상태가 바뀐 경우 설명이 부족합니다.

**직접 적용.** 브라우저 폭을 넓고 좁게 바꾸기 → 줄 바꿈과 가로 넘침 확인하기 → Tab으로 버튼에 이동하기 → 상태를 글자로도 알 수 있는 지 기록하기

**설명할 질문.** 정상 상태를 색만으로 표시하면 어떤 정보가 빠질까요?

### A07 · JavaScript와 이벤트

#### 사례로 이해하기 · 버튼 사건에서 데이터 표시까지 따라가기


#### 실무 상황

안내판은 처음에 22.5를 표시하지만 담당자가 data.js 값을 25로 바꾼 뒤에도 화면은 22.5입니다. 버튼을 누르자 25가 나타납니다. 오류라고 단정하기 전에 초기 문서와 버튼 동작의 데이터 흐름을 나누어 읽습니다.

#### 쉬운 풀이

JavaScript는 브라우저에서 동작을 수행하는 프로그램 언어입니다. 이벤트는 클릭처럼 일어난 사건이고 이벤트 처리 함수는 그 사건 때 실행할 행동입니다. querySelector는 이름에 맞는 문서 요소를 찾습니다. #은 id를 찾는 표시입니다. textContent는 요소의 글자 내용이며 이를 바꾸면 화면 글자가 달라집니다. 데이터 파일의 값, HTML의 처음 글자, 화면의 현재 글자는 같은 장소에 있지 않습니다.

#### 완성 예와 단계 풀이

제공 static/index.html은 data.js와 app.js를 연결합니다. data.js가 먼저 window.SENSOR에 가상 기록을 넣고 app.js가 #check·#temperature·#status를 찾습니다. 버튼 클릭 때 temperature 요소에 SENSOR.temperature_c를 넣고 상태에 장소 설명을 넣습니다. 처음 HTML의 22.5는 클릭 전의 표시이며 data.js에서 25를 저장한 뒤 새로고침하고 클릭하면 25가 보입니다. script 연결 순서와 같은 폴더의 파일 경로도 확인합니다. 실제 센서에서 받은 값이라는 의미는 없습니다.

#### 독립 추가 복습 과제

데이터는 26, 처음 HTML 글자는 22.5인 카드의 “열기 직후 / 클릭 뒤 / 데이터 파일 저장 여부” 세 칸을 작성하세요. 버튼 id만 read로 바꾼 경우 필요한 연결 수정을 결정하고 어떤 행동으로 복구를 확인할지 쓰세요.

처음은 22.5, 클릭 뒤는 26이며 클릭은 파일에 값을 저장하지 않습니다. id를 read로 바꾸면 JavaScript 선택자도 #read로 맞춰야 합니다. 수정 후 같은 버튼 클릭으로 결과를 확인합니다. “HTML 숫자만 고치면 이후 클릭도 바뀐다”는 답은 실제 데이터 출처를 놓쳤습니다.

① 버튼이 안 되면 무조건 데이터 문제인가요? 요소 이름이나 코드 로딩도 확인합니다. ② 새로고침과 클릭을 따로 기록하는 이유는 무엇인가요? 초기 표시와 사건 후 표시가 다릅니다. ③ 복구 후 파일 내용만 보면 충분한가요? 이전 실패 행동을 다시 수행하여 동작까지 확인해야 합니다.


**뜻과 비유.** JavaScript는 프로그램의 동작을 적는 언어입니다. 이 예제에서는 클릭이나 데이터 변화에 따라 화면을 바꿉니다. 이벤트는 버튼 클릭처럼 프로그램이 반응할 수 있는 사건입니다.

**왜 필요한가.** 정적인 문서 내용과 클릭 뒤 실행되는 동작을 나누면 화면이 왜 바뀌었는지 따라갈 수 있습니다.

### A10 · React와 컴포넌트

<!-- enrichment:2026-10-21:P4 -->

#### 사례로 이해하기 · React 부품과 브라우저가 실행하는 파일


#### 실무 상황

센서 카드를 여러 장소에 쓰려 합니다. 카드마다 제목과 온도를 직접 복사하면 한 곳을 고칠 때 다른 곳도 찾아야 합니다. 공통 화면 부품에 장소 값을 전달하면 구조를 재사용할 수 있습니다. 다만 소스 파일과 실제 실행 파일이 다르면 소스만 고치고 화면이 바뀌었다고 기대해서는 안 됩니다.

#### 쉬운 풀이

React 컴포넌트는 화면을 만드는 함수이며 props는 바깥에서 그 부품에 전달하는 값입니다. state는 화면 부품이 기억하고 바꾸는 현재 값입니다. JSX는 JavaScript 안에서 화면 구조를 적는 문법입니다. 일반 브라우저는 JSX가 들어 있는 .jsx 소스를 그대로 실행하지 못하며 변환 단계가 필요합니다. 번들은 변환된 코드와 필요한 라이브러리를 묶어 브라우저가 읽도록 만든 파일입니다. 제공 index.html은 app.bundle.js를 실행합니다.

#### 완성 예와 풀이

App.jsx의 `<SensorCard location={window.SENSOR.location} />`은 같은 부품에 장소를 전달합니다. SensorCard 안에서 useState는 SENSOR.temperature_c를 시작 값으로 기억합니다. 클릭은 setTemperature로 현재 값을 0.5 올립니다. 제공 데이터가 22.5라면 두 번 클릭 뒤 23.5가 보이며 새로고침하면 22.5로 돌아옵니다. 클릭이 data.js나 센서 장비에 저장한 것은 아닙니다. data.js는 HTML이 별도로 읽으므로 장소를 바꿔 저장·새로고침하면 반영됩니다. App.jsx의 문구나 증가량을 바꾸려면 번들을 다시 만드는 환경이 필요하고 오늘 필수 활동은 제공 번들을 사용합니다.

#### 독립 추가 복습 과제

“장소 이름 바꾸기”, “클릭한 현재 온도 올리기”, “증가량을 1로 바꾸기”를 데이터 파일·상태 변경·소스와 번들 재생성에 각각 연결하세요. 원래 값이 24라면 세 번 클릭과 새로고침 뒤의 값도 예상하세요.

#### 답과 대표 오답

장소는 data.js, 현재 값은 브라우저 state, 증가량은 App.jsx 수정과 빌드가 필요합니다. 세 번 뒤 25.5이고 새로고침 뒤 24입니다. “JSX는 HTML과 같아서 파일을 열면 된다”는 답은 변환을 빠뜨렸습니다. “클릭값이 저장됐다”는 답은 메모리와 파일을 혼동합니다.

#### 확인 질문과 해설

① props와 state는 같은가요? 전달 입력과 부품의 현재 기억입니다. ② 번들을 직접 고치나요? 생성 결과보다 소스를 수정하고 다시 만드는 경로가 기준입니다. ③ React가 MCP를 자동 호출하나요? 별도 연결 처리 없이는 호출하지 않습니다.


**뜻과 비유.** React는 데이터와 상태를 이용해 화면을 구성하는 JavaScript 라이브러리입니다. 컴포넌트는 내용과 동작을 함께 설명하는 재사용 가능한 화면 부품입니다.

**왜 필요한가.** 같은 센서 안내 형식을 여러 곳에 쓸 때 각 부품의 입력과 상태를 구분할 수 있습니다.

**예를 따라 읽기.** SensorCard는 장소와 온도를 보여 주는 제공된 완성 부품입니다. App은 제목과 이 부품을 화면에 배치합니다.

### A12 · 상태와 화면의 다시 그리기

**뜻과 비유.** 상태는 컴포넌트가 기억하는 값입니다. useState는 현재 값과 그 값을 바꾸는 함수를 제공하며 상태 변경에 따라 화면이 다시 계산됩니다.

**왜 필요한가.** 화면 글자를 직접 찾는 방식과 상태를 바꿔 화면을 설명하는 방식의 차이를 작은 클릭으로 관찰합니다.

### A13 · MCP의 호스트·클라이언트·서버

<!-- enrichment:2026-10-21:P5 -->

#### 사례로 이해하기 · 직접 연결과 MCP 연결을 비교한 뒤 권한 정하기


#### 실무 상황

온도 안내판이 기록을 보여 주는 방법에는 파일을 직접 읽는 경로, 서버 API를 호출하는 경로, AI 도구가 MCP 서버를 통해 기록을 조회하는 경로가 있습니다. 화면 모양은 비슷해도 중간 프로그램과 권한은 다릅니다. 연결을 그렸다는 사실만으로 실제 호출이 구현되었다고 보고하지 않습니다.

#### 쉬운 풀이

MCP는 AI 애플리케이션이 도구와 자료에 접근할 때 주고받는 메시지의 공통 약속입니다. 호스트는 AI 애플리케이션, 클라이언트는 서버와 통신하는 부분, 서버는 도구와 자료를 제공하는 프로그램입니다. 직접 파일 읽기는 공통 프로토콜 없이 해당 파일 구조를 알아야 합니다. MCP는 초기화·도구 목록·호출 같은 약속을 공유하지만 모든 서버가 같은 자료나 권한을 갖지는 않습니다. 연결 가능성과 쓰기 허용도 별개입니다.

#### 완성 예와 단계 풀이

오늘은 mcp_client.py가 로컬 mcp_server.py를 실행하여 표준 입력과 표준 출력으로 메시지를 주고받습니다. initialize 요청에 id 1이 있고 initialized 알림에는 id가 없습니다. tools/list가 get_reading의 입력 이름 sensor_id를 알려 줍니다. tools/call로 S01을 요청하면 22.5가 담긴 가상 기록이 돌아옵니다. S02는 존재하지만 미측정 null이며 S99는 Unknown sensor와 isError입니다. 이 서버는 읽기 도구만 제공하며 네트워크 요청, React 갱신, 실제 AI 추론을 수행하지 않습니다. 실제 호스트의 권한 통제 전체를 재현한 프로그램도 아닙니다.

#### 독립 추가 복습 과제

“HTML의 고정 숫자”, “data.js의 가상 값”, “MCP get_reading의 응답”을 자료 출처와 필요한 연결 단계로 비교하세요. 이어서 센서 조회에 계정 삭제 도구 권한까지 요구하는 서버가 있다면 허용 범위를 어떻게 판단할지 쓰세요.

#### 답과 대표 오답

고정 숫자는 HTML, 가상 값은 데이터 파일, MCP 응답은 서버 기록과 호출 연결입니다. 조회 목적에 필요하지 않은 삭제 권한은 제공하지 않고 필요한 범위를 확인합니다. “MCP가 연결되면 모든 작업이 자동 허용”은 오답입니다.

#### 확인 질문과 해설

① 알림에 응답 id가 있나요? 오늘 initialized 알림은 응답을 기대하지 않습니다. ② null은 도구 오류인가요? 존재하는 기록의 미측정 값일 수 있습니다. ③ 실제로 연결됐는지는 무엇을 보고 확인하나요? 실제 요청과 대응 응답, 실행 범위를 남겨야 합니다.


호스트는 사용자가 요청하는 AI 앱 전체이고, 클라이언트는 그 안에서 특정 서버와 메시지를 주고받는 연결 부분입니다. 서버는 도구와 입력 규칙을 제공하고 실행 결과를 돌려줍니다. 오늘 예제의 클라이언트는 미리 쓴 요청만 보내며 실제 AI 호스트나 모델이 판단하는 과정을 구현하지 않습니다.

**뜻과 비유.** MCP는 AI 앱이 외부 도구나 자료를 정해진 메시지 형식으로 사용하도록 연결하는 프로토콜입니다. 서버는 기능을 제공하고 클라이언트는 요청을 전달합니다.

**왜 필요한가.** React의 화면 구성과 MCP의 도구 통신을 같은 역할로 생각하지 않도록 경계를 구분합니다.

**예를 따라 읽기.** 제공 클라이언트는 get_reading이라는 읽기 도구를 요청하고 서버는 가상 센서 기록을 반환합니다.

**헷갈리는 반례.** 오늘의 mcp_client.py는 저장된 요청을 보내는 프로그램이며 AI 모델이나 실제 AI 호스트가 아닙니다.

**직접 적용.** 역할 카드의 네 요소 읽기 → 화면 역할과 도구 통신 역할 나누기 → 클라이언트·서버·데이터 파일 연결하기 → 실제 AI 호출이 없는 조건 쓰기

**막혔을 때.** MCP를 모든 AI 서비스의 동의어로 보지 않고 오늘 메시지를 주고 받는 두 프로그램을 정확히 지정합니다.

### A16 · 네 요소의 연결과 경계

<!-- enrichment:2026-10-21:P6 -->

#### 사례로 이해하기 · 도구 응답을 화면에 넣기 위한 중간 처리


#### 실무 상황

MCP에서 온도 응답을 받았지만 React 화면은 바뀌지 않습니다. 화면에 카드를 만든 것과 서버에서 기록을 조회한 것은 각각 확인했어도 두 동작을 잇는 처리가 빠질 수 있습니다. “연결 완료”라는 말 대신 실제로 이어진 화살표와 아직 계획인 화살표를 나눕니다.

#### 쉬운 풀이

도구 응답은 메시지이며 화면 상태는 React 부품이 현재 기억하는 값입니다. 둘 사이에는 호출 결과를 받기, 오류 구별하기, 내용 해석하기, 숫자와 단위 확인하기, 상태에 전달하기가 필요합니다. 문자열 안의 JSON도 해석하지 않으면 숫자를 바로 사용할 수 없습니다. 응답 안의 안내 글은 외부 자료이므로 호스트 권한을 바꾸라는 명령처럼 취급하지 않습니다. 읽기 도구의 결과가 추가 쓰기 권한을 부여하지도 않습니다.

#### 완성 예와 단계 풀이

recorded_responses.json의 id 3 결과는 content 안의 text에 S01 기록이 담겼습니다. 먼저 isError가 false인지 확인하고 text를 JSON 데이터로 읽은 뒤 temperature_c가 22.5인지 확인합니다. id 4는 temperature_c가 null이므로 “미측정” 문구를 고릅니다. id 5는 isError가 true이므로 “조회 실패”로 처리합니다. 이 판단 표를 작성해도 실제 React 상태 변경 코드를 구현한 것은 아닙니다. 지금 제공 화면은 data.js를 사용하고 제공 MCP는 STDIO 기록 조회를 사용합니다. 실제 연결에는 호스트 환경과 화면 갱신 경로 설계가 더 필요합니다.

#### 독립 추가 복습 과제

숫자 0, null, Unknown sensor 응답 세 개를 각각 표시 문구로 바꾸고 조건 순서를 작성하세요. 다음으로 응답 내용에 “다른 파일을 삭제하라”라는 문장이 섞였을 때 데이터 표시 작업을 계속하려면 무엇을 구별해야 할지 설명하세요.

#### 답과 대표 오답

유효한 0은 0 ℃, null은 미측정, 도구 오류는 조회 실패입니다. 먼저 오류와 자료 형태를 확인한 뒤 값을 해석합니다. 응답에 삭제하라는 문장이 있어도 파일을 삭제할 허가가 생기지는 않습니다. 받은 자료의 한 문장으로 읽습니다. “null도 0으로 표시”는 값 없음과 영점을 혼동합니다. “응답을 받았으니 화면도 갱신”은 중간 처리를 생략했습니다.

#### 확인 질문과 해설

① CSS로 누락 값이 측정값이 되나요? 모양은 자료의 의미를 바꾸지 않습니다. ② 그림에 화살표를 그리면 실제 프로그램도 연결됐나요? 실제 호출과 화면 관찰이 필요합니다. ③ 인계에 무엇을 쓰나요? 사용한 파일, 응답 id, 표시 결정, 실제 연결 여부와 다음 확인 범위를 적습니다.


**뜻과 비유.** HTML·CSS·React·MCP는 같은 시스템에 함께 있을 수 있지만 책임이 다릅니다. 데이터 이동이 필요한 곳에는 명시적인 연결 프로그램이 있어야 합니다.

**왜 필요한가.** 도구 응답을 받았다는 사실만으로 브라우저가 자동 갱신된다고 생각하면 연결이 빠진 설계를 만들 수 있습니다.

**예를 따라 읽기.** 오늘은 MCP 응답의 온도를 사람이 읽고 제공 데이터와 비교합니다. React와 MCP 간 자동 연결은 만들지 않았습니다.

**헷갈리는 반례.** MCP 서버가 있으니 로그인·화면·저장이 모두 해결됐다고 말하지 않습니다.

**직접 적용.** 네 요소 역할을 한 문장씩 쓰기 → S01 값의 출처와 화면 표시 구분하기 → 자동 연결한 것과 사람이 옮긴 것 표시하기 → 다음 연결에 필요한 프로그램 제안하기

**설명할 질문.** 도구 응답을 화면에 보이려면 무엇이 더 필요할까요?

**막혔을 때.** 그림의 화살표가 실제 동작인지 가정인지 따로 표시합니다.

입력·답칸·확인 순서는 [실습지의 A16](practice-guide.md#a16)와 [활동 원문](examples/course/data/A16_input.md)에 있습니다.

### A17 · 작은 변경의 동료 확인

**뜻과 비유.** 변경 검수는 입력한 값·바뀐 파일·예상 화면·실제 결과를 짝이 다시 확인하는 것입니다. 내용·모양·데이터·통신을 각기 다른 근거로 봅니다.

**왜 필요한가.** 화면의 모양이 좋아졌어도 도구에 올바른 입력을 보냈는지, 자료형을 유지했는지는 따로 확인해야 합니다.

**예를 따라 읽기.** HTML 제목,CSS 색,React 장소·온도,MCP sensor_id를 각각 한 줄의 변경 기록으로 남깁니다.

**헷갈리는 반례.** CSS 색 변경을 센서 상태로 기록하거나 모의 버튼을 실제 측정이라고 부르지 않습니다.

**직접 적용.** 작업 파일과 관찰 표 교환하기 → 네 역할 중 각 한 개 근거 확인하기 → 새로고침과 클릭 결과 구분하기 → 설명이 모호한 한 곳 보완하기

**설명할 질문.** 같은 화면에서 서로 다른 역할의 변경을 어떻게 확인하나요?

**막혔을 때.** 짝의 코드를 바로 수정하지 말고 대상 파일과 기대한 결과를 먼저 설명합니다.

입력·답칸·확인 순서는 [실습지의 A17](practice-guide.md#a17)와 [활동 원문](examples/course/data/A17_input.md)에 있습니다.

### A18 · 결과 설명과 선택 확장

**뜻과 비유.** 학습 결과는 수정한 작은 부분의 이유와 결과를 설명하는 것입니다. 전체 앱이나 MCP 서버를 독립 작성하는 능력을 오늘의 필수 목표로 삼지 않습니다.

**왜 필요한가.** 네 기술의 이름만 기억하는 것보다 어느 문제를 어떤 요소가 맡는지 말할 수 있어야 다음 대시보드로 연결됩니다.

**예를 따라 읽기.** 필수 결과는 제목·색·React 데이터 수정과 MCP 요청·응답 한 쌍의 설명입니다.

**헷갈리는 반례.** 패키지 설치를 못 했다고 개념 설명과 제공 번들 수정까지 실패로 판정하지 않습니다.

**직접 적용.** 수정한 파일 목록 정리하기 → 실제로 실행한 경로 쓰기 → 네 역할에 대한 새 질문 답하기 → 남은 환경·자동 연결 조건을 인계하기

**설명할 질문.** React 상태·CSS 색·MCP 응답은 각각 무엇을 바꾸나요?

**막혔을 때.** 설치나 외부 호스트 연결이 막히면 오프라인 번들과 저장된 응답으로 동일 개념을 확인하고 실행 범위를 명시합니다.

입력·답칸·확인 순서는 [실습지의 A18](practice-guide.md#a18)와 [활동 원문](examples/course/data/A18_input.md)에 있습니다.
