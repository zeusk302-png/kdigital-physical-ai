## 1구간 · 웹 문서의 내용



### A01 · 파일과 브라우저의 관계

**뜻과 비유.** 브라우저는 HTML 문서를 읽어 화면으로 보여 주는 프로그램입니다. 파일을 편집하는 창과 결과를 보는 창은 역할이 다릅니다.

**왜 필요한가.** 어디에 썼는지와 무엇을 열었는지를 구분해야 저장한 변경을 다시 확인할 수 있습니다.

**예를 따라 읽기.** work/static/index.html을 편집하고 같은 파일을 브라우저로 열면 제공 안내판을 볼 수 있습니다.

**헷갈리는 반례.** 코드 편집기에 글자를 바꾼 것만으로 이미 열린 화면이 자동 갱신되는 것은 아닙니다.

**직접 적용.** course 폴더를 압축 풀기 → work/static/index.html 경로 적기 → 브라우저에서 안내판 열기 → 편집·저장·새로고침 순서를 말하기

**설명할 질문.** 편집 창과 브라우저 화면은 어떻게 다른가요?

**막혔을 때.** 확장자가.txt로 붙었으면 파일 이름과 종류를 확인합니다. ZIP 안의 미리 보기에서 편집하지 않습니다.

입력·답칸·확인 순서는 [실습지의 A01](practice-guide.md#a01)와 [활동 원문](examples/course/data/A01_input.md)에 있습니다.

### A02 · HTML 태그와 문서 의미

**뜻과 비유.** HTML은 제목·문단·버튼 같은 내용의 의미를 표시하는 문서 형식입니다. 여는 태그와 닫는 태그 사이의 내용이 하나의 요소가 됩니다.

**왜 필요한가.** 보기에 큰 글자를 만드는 것과 문서의 제목이라는 의미를 주는 것을 구별해야 내용 구조를 읽을 수 있습니다.

**예를 따라 읽기.** `<h1>입구 센서 안내판</h1>`에서 h1은 주요 제목, 안의 글자는 화면 내용입니다.

**헷갈리는 반례.** 모든 글자를 h1으로 만들면 크기가 같아질 수 있어도 제목과 설명의 관계가 흐려집니다.

**직접 적용.** 전체 HTML에서 h1·p·button 찾기 → 여는 태그와 닫는 태그 짝 표시하기 → 제목 글자만 창고 센서 안내판으로 바꾸기 → 저장 후 어떤 내용이 바뀌었는지 확인하기

**설명할 질문.** h1과 CSS 글자 크기는 왜 같은 역할이 아닌가요?

**막혔을 때.** 태그 꺾쇠를 지웠다면 원본의 해당 줄과 비교합니다. 제목 문구와 title 탭 이름은 다른 위치입니다.

입력·답칸·확인 순서는 [실습지의 A02](practice-guide.md#a02)와 [활동 원문](examples/course/data/A02_input.md)에 있습니다.

### A03 · 속성·연결·접근성

**뜻과 비유.** 속성은 요소에 추가 정보를 붙이는 이름과 값입니다. lang은 문서 언어, id 는 특정 요소를 찾는 이름, type은 버튼 동작 종류를 설명합니다.

**왜 필요한가.** 사람이 보는 문구와 프로그램이 찾는 이름을 구분해야 버튼 연결을 끊지 않고 내용을 수정할 수 있습니다.

**예를 따라 읽기.** id ="check"는 JavaScript가 버튼을 찾는 기준이고 버튼 안 글자는 사용자에게 보이는 안내입니다.

**헷갈리는 반례.** id를 임의로 바꾸고 연결 코드를 그대로 두면 화면은 보여도 버튼 반응이 사라질 수 있습니다.

**직접 적용.** lang·id·type 속성 찾기 → 보이는 글자와 내부 이름 나누기 → 버튼 문구만 값 다시 확인으로 바꾸기 → Tab 키로 버튼에 이동해 테두리 보기

**설명할 질문.** 사용자에게 보이는 이름과 코드가 찾는 이름은 왜 구분하나요?

**막혔을 때.** 버튼 반응이 없으면 id와 선택자 #check가 같은지 봅니다. 화면 문구를 바꾸려면 태그 사이를 고칩니다.

입력·답칸·확인 순서는 [실습지의 A03](practice-guide.md#a03)와 [활동 원문](examples/course/data/A03_input.md)에 있습니다.

## 2구간 · CSS의 모양과 읽기



### A04 · CSS 선택자와 선언

**뜻과 비유.** CSS는 어떤 요소에 어떤 모양을 적용할지 쓰는 규칙입니다. 선택자는 대상을 고르고, 속성과 값은 색·크기·간격을 정합니다.

**왜 필요한가.** 내용과 모양을 나누면 같은 제목을 유지하면서 여러 화면 크기에 맞게 조정할 수 있습니다.

**예를 따라 읽기.** h1 { color: #126d65; }는 제목 글자의 색을 정합니다. #126d65는 색을 나타내는 표기입니다.

**헷갈리는 반례.** 색을 바꿔도 센서 온도의 데이터 값이 바뀌는 것은 아닙니다.

**직접 적용.** style.css에서 h1 규칙 찾기 → color와 값의 경계 표시하기 → 색을 #75421b로 바꾸기 → 같은 제목 내용이 유지되는지 비교하기

**설명할 질문.** CSS 값을 바꿨을 때 무엇이 유지돼야하나요?

**막혔을 때.** CSS가 적용되지 않으면 HTML의 href와 파일 이름이 일치하는지 먼저 확인합니다.

입력·답칸·확인 순서는 [실습지의 A04](practice-guide.md#a04)와 [활동 원문](examples/course/data/A04_input.md)에 있습니다.

### A05 · 상자·여백·읽기 폭

**뜻과 비유.** 브라우저의 요소는 화면 공간을 차지하는 상자로 배치됩니다. padding은 안쪽 간격, margin 은 바깥 간격이며 max-width 는 너무 넓어지지 않게 제한합니다.

**왜 필요한가.** 문장이 화면 끝까지 길어지거나 요소가 붙어 있으면 내용을 읽기 어렵습니다. 간격도 정보 전달에 영향을 줍니다.

**예를 따라 읽기.** main의 padding:24px을 32px로 바꾸면 안내판 내용과 바깥 영역 사이의 안쪽 간격이 커집니다.

**헷갈리는 반례.** 글자를 작게 줄여 모든 것을 한 화면에 넣는 방식은 초심자의 읽기를 어렵게 할 수 있습니다.

**직접 적용.** main의 세 배치 규칙 찾기 → padding과 margin 을 그림으로 구분하기 → padding 한 값을 바꿔 비교하기 → 글자 크기와 읽기 폭의 영향을 설명하기

**설명할 질문.** 안쪽 여백과 바깥 여백은 어떻게 구분하나요?

**막혔을 때.** 차이가 안 보이면 같은 파일을 저장했는지와 브라우저 새로고침 여부를 확인합니다.

입력·답칸·확인 순서는 [실습지의 A05](practice-guide.md#a05)와 [활동 원문](examples/course/data/A05_input.md)에 있습니다.

### A06 · 작은 화면과 상태의 표시

**뜻과 비유.** 반응형 규칙은 화면 폭 같은 조건에 따라 모양을 조정하는 CSS입니다. 색만으로 의미를 전달하지 않고 글자와 구조도 함께 사용합니다.

**왜 필요한가.** 같은 자료를 좁은 화면과 키보드로도 읽을 수 있어야 업무 확인에 사용할 수 있습니다.

**예를 따라 읽기.** max-width:600px 조건에서는 main의 바깥 간격이 8px로 바뀝니다. focus-visible은 키보드 초점을 드러냅니다.

**헷갈리는 반례.** 초록색만 보고 정상이라고 판단하게 하면 색을 구분하기 어렵거나 상태가 바뀐 경우 설명이 부족합니다.

**직접 적용.** 브라우저 폭을 넓고 좁게 바꾸기 → 줄 바꿈과 가로 넘침 확인하기 → Tab으로 버튼에 이동하기 → 상태를 글자로도 알 수 있는 지 기록하기

**설명할 질문.** 정상 상태를 색만으로 표시하면 어떤 정보가 빠질까요?

**막혔을 때.** 좁은 화면이 넘치면 고정 폭을 늘리지 말고 max-width와 여백 규칙부터 확인합니다.

입력·답칸·확인 순서는 [실습지의 A06](practice-guide.md#a06)와 [활동 원문](examples/course/data/A06_input.md)에 있습니다.

## 3구간 · 버튼과 데이터 변화



### A07 · JavaScript와 이벤트

**뜻과 비유.** JavaScript는 프로그램의 동작을 적는 언어입니다. 이 예제에서는 클릭이나 데이터 변화에 따라 화면을 바꿉니다. 이벤트는 버튼 클릭처럼 프로그램이 반응할 수 있는 사건입니다.

**왜 필요한가.** 정적인 문서 내용과 클릭 뒤 실행되는 동작을 나누면 화면이 왜 바뀌었는지 따라갈 수 있습니다.

**예를 따라 읽기.** addEventListener("click", ...)는 클릭 때 안쪽 코드를 실행하도록 연결합니다.

**헷갈리는 반례.** 버튼이 보인다는 사실만으로 클릭 동작이 연결됐다고 볼 수 없습니다.

**직접 적용.** app.js 전체 일곱 줄 읽기 → 버튼 선택과 클릭 연결 구간 나누기 → 누르기 전 상태 문구 예상하기 → 클릭 후 바뀐 문구를 비교하기

**설명할 질문.** 버튼 표시와 클릭 반응은 어떻게 다른가요?

**막혔을 때.** 선택한 요소가 없다는 오류면 HTML의 id와 querySelector 이름을 비교합니다.

입력·답칸·확인 순서는 [실습지의 A07](practice-guide.md#a07)와 [활동 원문](examples/course/data/A07_input.md)에 있습니다.

### A08 · 데이터와 화면 내용 연결

**뜻과 비유.** 데이터는 프로그램이 보여 줄 값이며 화면 요소는 그 값을 담는 자리입니다. textContent는 글자를 넣는 방법으로 오늘의 단순 숫자·문구 표시에 사용합니다.

**왜 필요한가.** 어느 파일의 값이 어느 화면 자리로 이동하는지 알면 작은 변경을 스스로 확인할 수 있습니다.

**예를 따라 읽기.** data.js의 temperature_c를 24.5로 바꾼 뒤 클릭하면 온도 자리에 24.5가 표시됩니다.

**헷갈리는 반례.** HTML에 처음 적힌 22.5와 클릭 후 data.js에서 읽은 값은 출처가 다르므로 수정 위치를 구분합니다.

**직접 적용.** data.js의 세 필드 읽기 → 온도 하나를 24.5로 바꾸기 → 새로고침 직후와 클릭 후 비교하기 → 초기 HTML 값과 동적 값의 출처 쓰기

**설명할 질문.** 새로고침 직후와 클릭 뒤 값이 다른 이유는 무엇인가요?

**막혔을 때.** 값이 그대로면 클릭까지 수행했는지 봅니다. 초기 HTML 값만 확인하고 변경 실패라고 판단하지 않습니다.

입력·답칸·확인 순서는 [실습지의 A08](practice-guide.md#a08)와 [활동 원문](examples/course/data/A08_input.md)에 있습니다.

### A09 · 오류 위치와 최소 복구

**뜻과 비유.** 오류를 찾을 때는 증상·실제 파일·가장 최근에 바꾼 부분을 순서대로 확인합니다. 코드 전체를 다시 쓰기보다 연결 하나를 비교합니다.

**왜 필요한가.** 작은 오타를 찾는 과정은 화면이 여러 파일의 연결로 만들어진다는 사실을 보여 줍니다.

**예를 따라 읽기.** 복사본의 id ="check"를 id ="checkx"로 바꾸면 #check 선택과 어긋납니다. 원복하면 클릭이 돌아옵니다.

**헷갈리는 반례.** 정상 원본까지 고치면 비교 기준을 잃으므로 의도적 오류는 작업 복사본에만 만듭니다.

**직접 적용.** 복사본에서 id 한 글자 바꾸기 → 클릭 반응이 없는 증상 관찰하기 → HTML과 JavaScript 이름 대조하기 → 원복 후 같은 행동으로 재확인하기

**설명할 질문.** 원복 후에도 같은 행동으로 확인해야 하는 이유는 무엇인가요?

**막혔을 때.** 개발자 도구가 익숙하지 않으면 먼저 원문 이름 비교로 찾고 강사가 콘솔 오류를 보여 줍니다.

입력·답칸·확인 순서는 [실습지의 A09](practice-guide.md#a09)와 [활동 원문](examples/course/data/A09_input.md)에 있습니다.

## 4구간 · React 완성 부품



### A10 · React와 컴포넌트

**뜻과 비유.** React는 데이터와 상태를 이용해 화면을 구성하는 JavaScript 라이브러리입니다. 컴포넌트는 내용과 동작을 함께 설명하는 재사용 가능한 화면 부품입니다.

**왜 필요한가.** 같은 센서 안내 형식을 여러 곳에 쓸 때 각 부품의 입력과 상태를 구분할 수 있습니다.

**예를 따라 읽기.** SensorCard는 장소와 온도를 보여 주는 제공된 완성 부품입니다. App은 제목과 이 부품을 화면에 배치합니다.

**헷갈리는 반례.** React는 HTML이나 CSS를 없애는 도구가 아니며 화면의 내용과 모양을 여전히 이해해야 합니다.

**직접 적용.** code/react/index.html 실행하기 → App.jsx에서 두 함수 이름 찾기 → 제목·SensorCard·안내문 위치 연결하기 → 정적 화면과 React 부품의 공통점 적기

**설명할 질문.** 컴포넌트는 표의 데이터 한 행과 같은 말인가요?

**막혔을 때.** 패키지 설치가 없어도 제공 app.bundle.js로 화면을 볼 수 있습니다. JSX를 브라우저가 그대로 읽는다고 가정하지 않습니다.

### A11 · props와 제공 데이터 수정

**뜻과 비유.** props는 부모가 부품에 전달하는 입력입니다. 오늘은 장소를 전달하고 온도의 첫 값을 제공 데이터에서 읽는 작은 완성 예제를 사용합니다.

**왜 필요한가.** 부품을 처음부터 새로 만들지 않아도 어떤 입력을 바꾸면 어느 화면이 달라지는지 확인할 수 있습니다.

**예를 따라 읽기.** work/react/data.js에서 location을 창고,temperature_c를 24.5로 바꾸고 새로고침하면 부품의 내용이 바뀝니다.

**헷갈리는 반례.** JSX의 중괄호는 여기서 JavaScript 값을 넣는 자리이며 CSS 규칙의 중괄호와 역할이 다릅니다.

**직접 적용.** 작업 React 폴더 열기 → data.js의 장소와 온도 수정하기 → 새로고침 해두 표시 비교하기 → props로 전달되는 장소 경로 쓰기

**설명할 질문.** 같은 부품을 다른 장소에 쓰려면 어떤 입력을 바꿀까요?

**막혔을 때.** 수정한 data.js가 code인지 work인지 확인합니다. 변경 값을 읽는 곳은 현재 열린 HTML 과 같은 폴더입니다.

입력·답칸·확인 순서는 [실습지의 A11](practice-guide.md#a11)와 [활동 원문](examples/course/data/A11_input.md)에 있습니다.

### A12 · 상태와 화면의 다시 그리기

**뜻과 비유.** 상태는 컴포넌트가 기억하는 값입니다. useState는 현재 값과 그 값을 바꾸는 함수를 제공하며 상태 변경에 따라 화면이 다시 계산됩니다.

**왜 필요한가.** 화면 글자를 직접 찾는 방식과 상태를 바꿔 화면을 설명하는 방식의 차이를 작은 클릭으로 관찰합니다.

**예를 따라 읽기.** 0.5 올린 모의값 버튼을 누르면 22.5 →23.0처럼 상태가 바뀝니다. 이것은 실제 센서 측정이 아닙니다.

**헷갈리는 반례.** 새로고침하면 서버에 저장한 값이 아니라 data.js의 초기 값으로 돌아갑니다.

**직접 적용.** useState와 setTemperature 위치 찾기 → 클릭 전후 숫자 예상하기 → 두 번 클릭한 값과 실제 비교하기 → 새로고침 뒤 초기화 이유 설명하기

**설명할 질문.** 상태 변경과 파일 저장은 어떤 차이가 있나요?

**막혔을 때.** 버튼을 누른 값이 파일에 저장됐다고 생각되면 data.js 원문을 다시 열어 비교합니다.

입력·답칸·확인 순서는 [실습지의 A12](practice-guide.md#a12)와 [활동 원문](examples/course/data/A12_input.md)에 있습니다.

## 5구간 · MCP 요청과 응답



### A13 · MCP의 호스트·클라이언트·서버

호스트는 사용자가 요청하는 AI 앱 전체이고, 클라이언트는 그 안에서 특정 서버와 메시지를 주고받는 연결 부분입니다. 서버는 도구와 입력 규칙을 제공하고 실행 결과를 돌려줍니다. 오늘 예제의 클라이언트는 미리 쓴 요청만 보내며 실제 AI 호스트나 모델이 판단하는 과정을 구현하지 않습니다.

**뜻과 비유.** MCP는 AI 앱이 외부 도구나 자료를 정해진 메시지 형식으로 사용하도록 연결하는 프로토콜입니다. 서버는 기능을 제공하고 클라이언트는 요청을 전달합니다.

**왜 필요한가.** React의 화면 구성과 MCP의 도구 통신을 같은 역할로 생각하지 않도록 경계를 구분합니다.

**예를 따라 읽기.** 제공 클라이언트는 get_reading이라는 읽기 도구를 요청하고 서버는 가상 센서 기록을 반환합니다.

**헷갈리는 반례.** 오늘의 mcp_client.py는 저장된 요청을 보내는 프로그램이며 AI 모델이나 실제 AI 호스트가 아닙니다.

**직접 적용.** 역할 카드의 네 요소 읽기 → 화면 역할과 도구 통신 역할 나누기 → 클라이언트·서버·데이터 파일 연결하기 → 실제 AI 호출이 없는 조건 쓰기

**설명할 질문.** MCP 서버가 웹 화면을 자동으로 만드는 것은 왜 아닌가요?

**막혔을 때.** MCP를 모든 AI 서비스의 동의어로 보지 않고 오늘 메시지를 주고 받는 두 프로그램을 정확히 지정합니다.

입력·답칸·확인 순서는 [실습지의 A13](practice-guide.md#a13)와 [활동 원문](examples/course/data/A13_input.md)에 있습니다.

### A14 · JSON-RPC 요청과 초기화

**뜻과 비유.** JSON-RPC 메시지는 method로 요청 종류를, id로 요청과 응답의 대응을 나타냅니다. 오늘의 MCP 예제는 2025-11-25규격 버전에 고정한 초기화 절차를 사용합니다.

**왜 필요한가.** 버전과 기능을 먼저 맞추면 어떤 도구 통신을 기대할지 확인할 수 있습니다. 최신 전체 규격 구현과 교육용 일부 구현을 구분합니다.

**예를 따라 읽기.** initialize 응답 뒤 notifications/initialized를 보내고 tools/list로 get_reading의 입력 규칙을 읽습니다.

**헷갈리는 반례.** id가 없는 알림은 일반 요청과 달리 같은 id의 결과 응답을 기다리는 메시지가 아닙니다.

**직접 적용.** requests.jsonl의 첫 세 메시지 읽기 → method·id·params 표시하기 → 초기화 요청과 알림 구별하기 → tools/list에서 입력 필드 찾기

**설명할 질문.** 초기화 알림과 도구 요청은 어떻게 구분하나요?

**막혔을 때.** JSONL은 메시지 한 개당 한 줄입니다. 예쁘게 여러 줄로 바꾸면 이 STDIO 입력 규칙과 맞지 않습니다.

입력·답칸·확인 순서는 [실습지의 A14](practice-guide.md#a14)와 [활동 원문](examples/course/data/A14_input.md)에 있습니다.

### A15 · 실제 STDIO 도구 호출

**뜻과 비유.** STDIO는 한 프로그램이 다른 프로그램의 표준 입력과 표준 출력으로 메시지를 교환하는 방법입니다. 네트워크 계정 없이 로컬 자식 프로세스를 실행할 수 있습니다.

**왜 필요한가.** 저장된 예시 문장을 읽는 것과 실제 서버가 응답한 기록을 구분하면서 작은 프로토콜을 관찰합니다.

**예를 따라 읽기.** python code/mcp_client.py는 서버를 실행해 S01의 22.5,S02의 null,S99의 도구 오류를 받습니다.

**헷갈리는 반례.** S02의 null은 통신 실패가 아닙니다. S99의 isError:true와 값 없음은 서로 다릅니다.

**직접 적용.** 완성 클라이언트와 서버 줄 해설 읽기 → 클라이언트 명령 실행 또는 강사 결과 비교하기 → id3·4·5의 값과 오류 표시 찾기 → 응답 예와 실제 실행 여부를 분리 기록하기

**설명할 질문.** null 응답과 도구 오류 응답은 무엇이 다른가요?

**막혔을 때.** 서버를 단독 실행하면 입력을 기다릴 수 있습니다. 기본 활동은 제공 클라이언트 명령으로 실행합니다.

### A16 · 네 요소의 연결과 경계

**뜻과 비유.** HTML·CSS·React·MCP는 같은 시스템에 함께 있을 수 있지만 책임이 다릅니다. 데이터 이동이 필요한 곳에는 명시적인 연결 프로그램이 있어야 합니다.

**왜 필요한가.** 도구 응답을 받았다는 사실만으로 브라우저가 자동 갱신된다고 생각하면 연결이 빠진 설계를 만들 수 있습니다.

**헷갈리는 반례.** MCP 서버가 있으니 로그인·화면·저장이 모두 해결됐다고 말하지 않습니다.

**직접 적용.** 네 요소 역할을 한 문장씩 쓰기 → S01 값의 출처와 화면 표시 구분하기 → 자동 연결한 것과 사람이 옮긴 것 표시하기 → 다음 연결에 필요한 프로그램 제안하기

**설명할 질문.** 도구 응답을 화면에 보이려면 무엇이 더 필요할까요?

**막혔을 때.** 그림의 화살표가 실제 동작인지 가정인지 따로 표시합니다.

### A17 · 작은 변경의 동료 확인

**뜻과 비유.** 변경 검수는 입력한 값·바뀐 파일·예상 화면·실제 결과를 짝이 다시 확인하는 것입니다. 내용·모양·데이터·통신을 각기 다른 근거로 봅니다.

**왜 필요한가.** 한 화면이 예뻐졌어도 도구 요청 입력이 맞거나 자료형이 보존됐다는 증거는 아닙니다.

**예를 따라 읽기.** HTML 제목,CSS 색,React 장소·온도,MCP sensor_id를 각각 한 줄의 변경 기록으로 남깁니다.

**헷갈리는 반례.** CSS 색 변경을 센서 상태로 기록하거나 모의 버튼을 실제 측정이라고 부르지 않습니다.

**직접 적용.** 작업 파일과 관찰 표 교환하기 → 네 역할 중 각 한 개 근거 확인하기 → 새로고침과 클릭 결과 구분하기 → 설명이 모호한 한 곳 보완하기

**설명할 질문.** 같은 화면에서 서로 다른 역할의 변경을 어떻게 확인하나요?

**막혔을 때.** 짝의 코드를 바로 수정하지 말고 대상 파일과 기대한 결과를 먼저 설명합니다.

### A18 · 결과 설명과 선택 확장

**뜻과 비유.** 학습 결과는 수정한 작은 부분의 이유와 결과를 설명하는 것입니다. 전체 앱이나 MCP 서버를 독립 작성하는 능력을 오늘의 필수 목표로 삼지 않습니다.
