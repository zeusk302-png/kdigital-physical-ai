# W12 팀 피드백을 읽고 수정 작업으로 바꾸기

## ‘예뻐요’ 대신 재현할 수 있는 의견

팀원은 작성자의 설명 없이 공개 URL을 엽니다. ‘별로다’보다 ‘390px에서 메뉴를 열면 제목을 가린다’처럼 실제 행동과 결과를 적어야 수정할 수 있습니다. 다른 학생의 파일을 대신 고치지 말고 관찰한 사실을 남깁니다. 먼저 개인 페이지 하나를 집중 검수하고 팀 안에서 차례로 돌아갑니다.

## 검수 순서

1. 첫 화면만 보고 누구를 위한 페이지인지와 주요 버튼의 목적을 말합니다.
2. PC와 휴대전화에서 제목·이미지·카드가 잘리지 않는지 확인합니다. 휴대전화가 없으면 개발자 도구의 기기 화면 모드를 사용하고 실제 휴대전화 확인과 구분합니다.
3. 메뉴·내부 링크·FAQ를 누릅니다. Tab으로 버튼을 이동하고 Enter 또는 Space로 실행합니다.
4. 문의 폼에 빈 값·잘못된 이메일·짧은 내용·정상 내용을 넣습니다. 실제 접수하지 않는 예제라면 전송 완료로 오해할 문구가 없는지 봅니다.
5. Notion 검수표에 대상 URL·재현 단계·기대 결과·실제 결과·우선순위를 적습니다. 각 학생에게 서로 다른 피드백을 두 개 이상 남깁니다.

예시 P01: ‘MY-REPO/ 페이지, 390px, 메뉴 버튼 클릭, 기대: 제목을 가리지 않고 탐색 항목 표시, 실제: 첫 줄을 덮음, 우선순위: 높음’. 캡처에는 계정 메뉴·토큰·개인 메일이 포함되지 않도록 화면 영역을 확인합니다.

## MCP로 의견 읽기

아래 요청의 URL과 내 페이지 이름을 실제 값으로 바꿉니다. 여러 학생의 의견이 섞여 있으므로 대상을 정확히 지정합니다. 실제 도구 호출에서 반환한 항목만 근거로 사용합니다.

```text
Notion MCP로 TEAM-PAGE-URL을 읽어.
그중 내 홈페이지 ‘내 페이지 이름’에 대한 피드백만 골라 줘.
피드백 ID, 원문, 문서 링크를 유지하고
화면 오류·기능 오류·콘텐츠 개선으로 구분해.
문서에 없는 의견을 만들지 마.
높은 우선순위 2개를 작업 후보로 정리해.
아직 문서나 코드는 바꾸지 마.
```

AI 정리와 원문을 비교하고 잘못된 요약을 고칩니다. 피드백이 실제 오류가 아니라 취향 차이라면 채택하지 않을 수 있습니다. 선택한 이유를 한 줄 적습니다. 홈페이지와 무관한 기능을 추가하는 의견은 오늘 범위에서 제외합니다.

## 작업 요청으로 바꾸기

```text
피드백 P01을 해결할 거야.
docs/brief.md, index.html, src/styles/layout.css를 읽어.
모바일 메뉴가 제목을 가리는 원인을 먼저 설명해.
기존 문구·이미지·데스크톱 배치는 유지해.
관련 파일만 수정하고, 불필요한 패키지를 추가하지 마.
390px·1280px와 키보드 메뉴 동작을 확인할 방법을 적어.
```

이후 수정 계획을 보고 진행합니다. 변경 파일을 비교하고 직접 실행합니다. React판 문제라면 index.html 대신 src/App.jsx와 관련 컴포넌트를 지정해야 합니다. 대상 화면의 원본을 잘못 고치면 파일은 바뀌어도 공개 페이지는 그대로입니다.

## 수정 결과를 팀 문서에 남기기

로컬 시험 뒤 W13의 재배포를 마칩니다. 아래 요청에서 정확한 문서와 내용을 지정합니다. AI가 실제로 수정하기 전 대상·추가 문장을 확인합니다. 이 수업에서는 기존 검수 내용을 지우거나 다른 학생 행을 바꾸지 않습니다.

```text
Notion 팀 문서 TEAM-PAGE-URL의 내 결과 영역에만 아래 기록을 추가해.
피드백: P01
수정 파일: src/styles/layout.css
확인 결과: 내가 실제로 확인한 결과를 여기에 작성
배포 URL: 내 공개 URL
커밋: 실제 커밋 ID
다른 학생의 내용과 기존 의견은 유지해.
추가할 문장을 먼저 보여 주고 내가 확인한 뒤 실행해.
```

추가 후 브라우저에서 실제 문서가 바뀌었는지 확인합니다. 쓰기 도구가 제공되지 않거나 권한이 없다면 직접 기록하고 수동 작성이라고 표시합니다. 성공 문구만 복사해 놓지 않습니다.

## 완료 기준

팀원에게 받은 재현 가능한 피드백, 원문과 비교한 MCP 요약, 내가 선택한 수정, 코드 변경, 다시 배포한 공개 URL이 이어져야 합니다. 발표는 ‘무엇을 만들었다’보다 ‘어떤 문제가 있었고 무엇을 확인해 고쳤는지’를 중심으로 1분 안에 설명합니다.
