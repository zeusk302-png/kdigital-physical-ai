# 2026-10-20 · AI 코드에이전트

AI에 맡길 일을 구체적으로 적고, 제안된 코드의 변경과 결과를 확인합니다. 제공 응답을 비교하며 요청과 검토를 연습합니다.

실제 AI 계정·모델·유료 API를 호출하지 않습니다. 제공 응답은 강사가 만든 비교 자료입니다. 합성 분류 규칙이며 실제 센서 안전 판단을 검증하지 않았습니다.

전체 코드와 모든 줄의 뜻·실행 방법은 [코드 해설](examples/course/code/line-guide.md)에 있습니다. 작성 소스와 생성된 번들·잠금 파일을 구분합니다.

## 1구간 · 작업을 맡기는 방법



### A01 · 에이전트와 사람의 역할

**뜻과 비유.** 코드에이전트는 요청을 해석하고 파일과 실행 도구를 사용해 작업을 이어 가는 AI 도구입니다. 대화 답변 한 번과 파일 변경·실행이 연결된 작업 흐름을 구분합니다.

**왜 필요한가.** 동료에게 일을 맡겨도 완료 기준은 함께 정합니다. 코드가 생겼다는 사실과 업무 요구가 충족됐다는 사실은 다릅니다.

**예를 따라 읽기.** 센서 온도 28을 주의로 분류해 달라는 요청은 입력·기준·출력·확인 방법을 포함할 수 있습니다.

**헷갈리는 반례.** “알아서 좋게 고쳐”는 유지해야할 함수 이름이나 28 ℃ 경계를 알려 주지 않습니다.

**직접 적용.** 요청서에서 목적을 한 문장으로 찾기 → AI가 제안할 일과 사람이 판단할 일 나누기 → 완료라고 부를 증거 두 가지 적기 → 짝에게 도구와 검토자의 역할 설명하기

**설명할 질문.** 코드가 생긴 것만으로 완료가 아닌 이유는 무엇인가요?

**막혔을 때.** 도구 이름과 능력을 혼동하면 읽기·변경·실행 중 실제로 허용한 행동을 따로 적습니다.

입력·답칸·확인 순서는 [실습지의 A01](practice-guide.md#a01)와 [활동 원문](examples/course/data/A01_input.md)에 있습니다.

### A02 · 작은 작업과 수정 범위

**뜻과 비유.** 작업 범위는 어떤 파일과 동작을 바꿀지 정한 경계입니다. 전체 프로그램을 한 번에 고치기보다 한 함수의 분류 규칙처럼 확인 가능한 단위로 나눕니다.

**왜 필요한가.** 범위를 알면 변경 비교가 짧아지고 잘못 바꾼 항목을 되돌리기 쉽습니다. 10/16의 변경 비교가 여기서 업무 검토 근거가 됩니다.

**예를 따라 읽기.** 오늘은 classifier.py의 classify 동작만 바꾸고 함수 이름과 threshold =28을 유지합니다.

**헷갈리는 반례.** 결과를 맞추려고 cases.json 기대 값을 변경하면 검사기준을 바꾼 것이므로 요청을 해결한 증거가 아닙니다.

**직접 적용.** 바꿀 파일 하나 적기 → 유지할 이름·기준·입출력 찾기 → 요청 밖 변경 예 두 가지 표시하기 → 작업 요청서에 범위 적기

**설명할 질문.** 테스트 기대 값을 바꾸면 왜 문제가 숨을 수 있나요?

**막혔을 때.** 파일을 못 찾으면 압축을 푼 course 폴더의 code·data·work 위치부터 확인합니다.

입력·답칸·확인 순서는 [실습지의 A02](practice-guide.md#a02)와 [활동 원문](examples/course/data/A02_input.md)에 있습니다.

### A03 · 컨텍스트와 관련 자료

**뜻과 비유.** 컨 텍스트는 이번 일을 이해하는 데 필요한 설명과 자료입니다. 파일 전체를 많이 넣는 것보다 어떤 입력이 어떤 문제를 만드는지 정확히 전달하는 것이 중요합니다.

**왜 필요한가.** 도구가 보지 못한 파일이나 숨은 업무 규칙을 저절로 안다고 가정하면 엉뚱한 수정이 나올 수 있습니다.

**예를 따라 읽기.** 원본 함수·가상 입력·기대 결과·실제 오류 마지막 줄은 문제를 재현하는 데 도움이 됩니다.

**헷갈리는 반례.** 관계없는 오래된 프로젝트와 실제 계정 비밀번호는 오늘의 분류 규칙을 설명하는 데 필요하지 않습니다.

**직접 적용.** 여섯 자료 카드 읽기 → 관련·무관·공유하지 않을 자료로 분류하기 → 선택한 자료의 필요성을 한 줄씩 쓰기 → 빠진 맥락 하나를 질문으로 남기기

**설명할 질문.** 자료가 많으면 항상 더 좋은 요청이 되나요?

**막혔을 때.** 출처와 사용 목적을 구분하지 못하면 각 자료가 어떤 질문에 답하는지 적어 봅니다.

입력·답칸·확인 순서는 [실습지의 A03](practice-guide.md#a03)와 [활동 원문](examples/course/data/A03_input.md)에 있습니다.

## 2구간 · 근거가 있는 요청서



### A04 · 입력과 출력 계약

**뜻과 비유.** 입출력 계약은 어떤 값을 받아 어떤 형태로 답할지 정한 약속입니다. 함수의 내부가 달라져도 호출하는 쪽이 기대하는 이름과 결과는 유지해야합니다.

**왜 필요한가.** 함수 이름을 바꾸거나 새 숫자 코드를 반환하면 기존 호출 자는 결과를 이해하지 못할 수 있습니다.

**예를 따라 읽기.** classify(28)는 주의, classify(None)는 미측정으로 답하도록 요청에 씁니다.

**헷갈리는 반례.** 미측정을 정상으로 부르면 측정하지 못한 상황이 정상 온도로 보입니다.

**직접 적용.** 요청서에서 허용 입력 추출하기 → 네 반환 문자열을 표로 쓰기 → 함수 호출 하나의 입력·출력 연결하기 → task.md에 계약 작성하기

**설명할 질문.** 함수 이름과 반환 문자열을 유지하는 이유는 무엇인가요?

**막혔을 때.** None과 문자열 "None"이 헷갈리면 10/8의 값 없음과 글자 차이를 다시 비교합니다.

입력·답칸·확인 순서는 [실습지의 A04](practice-guide.md#a04)와 [활동 원문](examples/course/data/A04_input.md)에 있습니다.

### A05 · 정상·경계·오류 사례

**뜻과 비유.** 검사 사례는 입력과 기대 결과를 한 쌍으로 적은 것입니다. 경계 사례는 규칙이 달라지는 바로 앞·같은 값·바로 뒤를 비교합니다.

**왜 필요한가.** 평범한 22.5 하나가 통과해도 28에서 비교 기호가 틀린 문제는 드러나지 않습니다.

**예를 따라 읽기.** 27.9는 정상, 28 과 28.1은 주의입니다. 0은 유효하며 None은 미측정입니다.

**헷갈리는 반례.** 글자 “뜨거움”을 0으로 바꿔 처리하면 오류 입력이 정상 기록으로 둔갑합니다.

**직접 적용.** cases.json 아홉 입력 읽기 → 실행 전에 기대 상태 써 보기 → 경계 세 사례를 묶기 → 결과가 틀릴 때의 업무 영향을 설명하기

**설명할 질문.** 왜 28만 확인하지 않고 27.9와 28.1도 보나요?

**막혔을 때.** 숫자와 불리 언을 혼동하면 type(True)가 bool임을 확인하고 온도 계약과 비교합니다.

입력·답칸·확인 순서는 [실습지의 A05](practice-guide.md#a05)와 [활동 원문](examples/course/data/A05_input.md)에 있습니다.

### A06 · 검증 가능한 프롬프트

**뜻과 비유.** 프롬프트는 도구에게 전달하는 요청 문장입니다. 목표·입력·범위·유지 조건·확인 사례를 짧게 연결하면 모호한 칭찬 대신 확인 가능한 결과를 요구할 수 있습니다.

**왜 필요한가.** 검사 방법을 먼저 적으면 도구가 스스로 완료라고 말해도 무엇이 확인됐는지 비교할 수 있습니다.

**예를 따라 읽기.** “28 이상은 주의로 고치고 None은 미측정으로 남기며 아홉 사례를 실행해 결과를 보고해 주세요.”

**헷갈리는 반례.** “완벽한 전문가 코드로 만들어”는 어떤 결과가 맞는지 판단할 기준이 없습니다.

**직접 적용.** work/task.md의 여섯 칸 채우기 → 모호한 형용사 한 개를 구체 조건으로 고치기 → 짝이 요청만 보고 예상 결과 말하기 → 해석이 갈린 문장 다시 쓰기

**설명할 질문.** 좋은 요청에 실행 전 기대 결과가 들어가는 이유는 무엇인가요?

**막혔을 때.** 요청이 길어지면 목적과 유지 조건을 분리하고 이번에 필요 없는 기능은 후속 요청으로 둡니다.

입력·답칸·확인 순서는 [실습지의 A06](practice-guide.md#a06)와 [활동 원문](examples/course/data/A06_input.md)에 있습니다.

## 3구간 · 변경된 코드 읽기



### A07 · 변경 비교의 기호 읽기

**뜻과 비유.** diff는 전후 코드에서 빠진 줄과 새 줄을 보여 주는 변경 비교입니다. -는 이전 줄, +는 새 줄이며 코드의 빼기·더하기 연산과 다릅니다.

**왜 필요한가.** 전체 파일을 외우지 않아도 요청이 어느 변경에 반영됐는지 확인할 수 있습니다.

**예를 따라 읽기.** >를 >=로 바꾼 줄은 경계 28을 포함하도록 동작을 바꿉니다.

**헷갈리는 반례.** 주석만 “28 이상”으로 바뀌고 실제 비교가 >이면 동작은 그대로입니다.

**직접 적용.** changes.diff에서 파일 이름 찾기 → 미측정·검사·경계 변경 줄 묶기 → 요청한 항목과 변경 한 곳 연결하기 → 문구 변경과 동작 변경 구분하기

**설명할 질문.** diff의 +와 Python의 +는 어떤 차이가 있나요?

**막혔을 때.** diff의 +를 원본 코드에 복사했다면 실제 소스 파일의 완성 줄을 참고해 제거합니다.

입력·답칸·확인 순서는 [실습지의 A07](practice-guide.md#a07)와 [활동 원문](examples/course/data/A07_input.md)에 있습니다.

### A08 · 설득력 있는 응답 검토

**뜻과 비유.** AI 응답은 설명이며 실행 증거 그 자체가 아닙니다. 코드를 바꿨다는 주장, 검사를 했다는 주장, 실제 결과를 각각 확인합니다.

**왜 필요한가.** 자신 있는 문장 때문에 범위 밖 수정이나 누락된 검사를 지나칠 수 있습니다.

**예를 따라 읽기.** 응답 A는 기준을 27로 바꾸고 None을 0으로 채웁니다. 요청의 28 유지와 미측정 보존에 어긋납니다.

**헷갈리는 반례.** “모든 문제 해결”이라는 문장이 있어도 어떤 입력으로 확인했는지 없으면 결론을 보류합니다.

**직접 적용.** 응답 A와 코드 나란히 읽기 → 기준 변경과 빈 값 처리 표시하기 → 요구 위반 두 개를 근거로 쓰기 → 승인 전 추가 확인 질문 작성하기

**설명할 질문.** 친절하고 자신 있는 응답도 왜 다시 확인하나요?

**막혔을 때.** 응답의 어조보다 실제 바뀐 값과 반환을 원문 요청에 대조합니다.

입력·답칸·확인 순서는 [실습지의 A08](practice-guide.md#a08)와 [활동 원문](examples/course/data/A08_input.md)에 있습니다.

### A09 · 작업 복사본과 되돌림

**뜻과 비유.** 작업 복사본은 원본을 남기고 수정 결과를 비교하기 위한 파일입니다. 저장한 파일과 실행한 파일의 경로가 같아야 변경의 효과를 볼 수 있습니다.

**왜 필요한가.** 같은 이름의 파일을 다른 폴더에서 실행하면 고쳤는데도 이전 결과가 나오는 것처럼 보입니다.

**예를 따라 읽기.** work/classifier.py는 원본과 같은 시작 코드입니다. code/baseline.py는 비교용으로 유지합니다.

**헷갈리는 반례.** 원본까지 덮어쓰고 이 전 동작을 기억만 하면 변경 근거와 되돌릴 기준을 잃습니다.

**직접 적용.** 세 폴더 역할 적기 → work/classifier.py를 열어 원본과 대조하기 → 실행할 정확 경로 기록하기 → 수정전 사본과 복구 방법 적기

**설명할 질문.** 파일 이름이 같은데 다른 결과가 나올 수 있는 이유는 무엇인가요?

**막혔을 때.** 파일 확장자 숨김이면 파일 속성을 확인하고 ZIP 목록 안에서 편집하지 않습니다.

입력·답칸·확인 순서는 [실습지의 A09](practice-guide.md#a09)와 [활동 원문](examples/course/data/A09_input.md)에 있습니다.

## 4구간 · 예상과 실제 결과



### A10 · 기준 코드의 실제 실패

**뜻과 비유.** 실패 검사는 실수로 망가진 수업이 아니라 요구와 현재 동작의 차이를 드러내는 관찰입니다. 검사 프로그램은 기대와 실제를 나란히 비교합니다.

**왜 필요한가.** 수정 전 실패를 재현해 두면 수정 후 무엇이 달라졌는지 확인할 기준이 생깁니다.

**예를 따라 읽기.** python code/check_cases.py code/baseline.py를 실행하면 경계와 미측정 등의 차이가 FAIL로 나옵니다.

**헷갈리는 반례.** 종료 코드 1을 보고 무조건 재설치하지 않습니다. 이 검사기는 실패 사례가 있으면 의도적으로 1을 반환합니다.

**직접 적용.** 전체 검사 코드와 줄 해설 읽기 → 원본 실행 명령 확인하기 → 아홉 줄 결과에서 FAIL의 입력 찾기 → 예상과 실제 차이를 표에 남기기

**설명할 질문.** 테스트가 실패한 것과 실행환경이 고장 난 것은 어떻게 구별하나요?

**막혔을 때.** 모듈 경로 오류면 course 폴더에서 명령을 실행하고 파일 경로 인수를 빠뜨리지 않았는지 봅니다.

입력·답칸·확인 순서는 [실습지의 A10](practice-guide.md#a10)와 [활동 원문](examples/course/data/A10_input.md)에 있습니다.

### A11 · 경계 비교 기호 수정

**뜻과 비유.** >는 기준보다 큰 값, >=는 기준과 같은 값까지 포함합니다. 말로 쓴 “이상”과 코드 비교 기호를 연결합니다.

**왜 필요한가.** 경계 한 글자는 업무 분류를 바꿉니다. 정상 값만 시험하면 이 차이를 놓칩니다.

**예를 따라 읽기.** 작업본의 value > threshold를 value >= threshold로 바꾸면 28의 결과가 정상에서 주의로 달라집니다.

**헷갈리는 반례.** 기본 threshold를 27로 내리는 것은 같은 수정이 아닙니다. 27.9까지 주의가 되어 규칙을 바꿉니다.

**직접 적용.** 수정 전 28결과 기록하기 → work의 비교 기호 한곳 수정하기 → 저장 후 같은 검사 다시 실행하기 → 27.9·28·28.1 변화 비교하기

**설명할 질문.** 기준값을 바꾸는 것과 비교 기호를 바꾸는 것은 왜 다른가요?

**막혔을 때.** 결과가 그대로면 저장 여부와 실행 경로를 먼저 확인합니다.

입력·답칸·확인 순서는 [실습지의 A11](practice-guide.md#a11)와 [활동 원문](examples/course/data/A11_input.md)에 있습니다.

### A12 · 누락과 잘못된 입력 처리

**뜻과 비유.** 입력 검사는 자료가 함수의 약속에 맞는지 살펴보는 것입니다. 값이 없는 경우와 종류가 틀린 경우, 범위를 벗어난 경우를 따로 처리합니다.

**왜 필요한가.** 없음을 0으로 채우면 실제 0 측정과 구분할 수 없고 문자에 비교 연산을 하면 실행 오류가 납니다.

**예를 따라 읽기.** reviewed.py는 None →미측정, 숫자 아님 →입력 오류, 범위 밖 →입력 오류를 먼저 검사합니다.

**헷갈리는 반례.** Python에서 bool은 숫자와 관련된 특성이 있지만 이 업무 계약은 온도로 받지 않으므로 type을 정확히 확인합니다.

**직접 적용.** 완성 검사 세 부분 줄별로 읽기 → 작업본에 제공된 검사 구간 반영하기 → 0·None·True·51결과 예상하기 → 검사기로 실제 결과 확인하기

**설명할 질문.** 값 검사를 비교보다 먼저 하는 이유는 무엇인가요?

**막혔을 때.** 들여 쓰기가 틀리면 원본 완성 예제의 블록 범위를 대조합니다. 조건 순서도 함께 확인합니다.

입력·답칸·확인 순서는 [실습지의 A12](practice-guide.md#a12)와 [활동 원문](examples/course/data/A12_input.md)에 있습니다.

## 5구간 · 오류 재현과 수정



### A13 · 재현 가능한 오류 보고

**뜻과 비유.** 오류 보고는 실제로 한 행동·입력·기대한 결과·실제 결과를 다른 사람이 다시 따라갈 수 있게 적은 문서입니다.

**왜 필요한가.** “안 돼요”보다 파일 경로와 입력 하나를 제시하면 재현 범위가 좁아지고 원인 추측을 줄입니다.

**예를 따라 읽기.** 입력 28, 기대 주의, 실제 정상,baseline.py 실행이라는 네 정보가 있으면 경계 문제를 재현할 수 있습니다.

**헷갈리는 반례.** 관찰하지 않은 원인을 확정해“AI가 고장 났다”고 쓰면 다음 확인 행동이 불명확합니다.

**직접 적용.** 실패한 사례 하나 고르기 → 파일·명령·입력·기대·실제 쓰기 → 추정 원인과 관찰 사실 분리하기 → 짝이 같은 문제를 재현할 수 있는 지 읽기

**설명할 질문.** 관찰 사실과 원인 추정은 왜 나누어 쓰나요?

**막혔을 때.** 실행 화면을 남기지 못 했으면 실제 출력 문구를 그대로 적고 확인하지 않은 내용은 비워 둡니다.

입력·답칸·확인 순서는 [실습지의 A13](practice-guide.md#a13)와 [활동 원문](examples/course/data/A13_input.md)에 있습니다.

### A14 · 수정 요청을 좁히기

**뜻과 비유.** 추가 요청은 실패한 조건과 유지할 조건을 함께 적는 것입니다. 문제가 하나 발견됐다고 전체 프로그램을 다시 만드는 요청으로 넓히지 않습니다.

**왜 필요한가.** 작은 수정은 이미 통과한 사례를 보존하는지 재확인하기 쉽습니다.

**예를 따라 읽기.** “28의 기대는 주의인데 정상입니다. 기준 28과 함수 이름을 유지하고 비교 조건만 검토해 주세요.”

**헷갈리는 반례.** “전부 새로 고쳐”는 빈 값 처리나 이름까지 바꾸어 새 문제를 만들 수 있습니다.

**직접 적용.** 이전 실패에서 추가 요청한 문단 쓰기 → 수정 대상과 유지 대상 분리하기 → 응답 B가 주장한 범위 읽기 → 실행으로 확인할 주장 표시하기

**설명할 질문.** 추가 요청에서도 유지할 조건을 다시 적는 이유는 무엇인가요?

**막혔을 때.** 응답에 없는 검증을 했다고 추측하지 말고 별도 확인 항목으로 남깁니다.

입력·답칸·확인 순서는 [실습지의 A14](practice-guide.md#a14)와 [활동 원문](examples/course/data/A14_input.md)에 있습니다.

### A15 · 회귀 확인과 증거

**뜻과 비유.** 회귀는 수정한 뒤 예전에 맞던 동작이 다시 틀리는 현상입니다. 수정한 사례 뿐 아니라 관련된 기존 사례도 함께 확인합니다.

**왜 필요한가.** 경계를 고치며 기준을 27로 바꾸면 28 은 맞아도 27.9가 틀려집니다.

**예를 따라 읽기.** baseline·proposal_a·reviewed의 아홉 결과를 같은 기대 값으로 비교합니다.

**헷갈리는 반례.** 검사를 새 코드에 유리하게 바꾸거나 통과 한 줄만 보고하면 근거가 사라집니다.

**직접 적용.** 세 후보에 같은 검사 실행하기 → 통과 수와 실패 입력 표로 비교하기 → 요구 위반과 실패의 연결 쓰기 → 원본 검사 파일이 유지됐는지 확인하기

**설명할 질문.** 통과 수만 같으면 같은 품질이라고 할 수 있나요?

**막혔을 때.** FAIL 수가 줄어도 새로운 실패가 입력되었는지 각 행을 확인합니다.

## 6구간 · 새 요청과 인수인계



### A16 · 새 조건의 영향 분석

**뜻과 비유.** 새 업무 조건은 기존 규칙과 독립인지 먼저 확인한 뒤 작은 사례로 설계합니다. 오늘은 추가 코드보다 변경이 영향 줄 입력을 설명하는 일에 집중합니다.

**왜 필요한가.** 특수 기준을 추가하면 조건 순서와 기존 계약을 함께 검토해야합니다.

**예를 따라 읽기.** 담당자가 기준을 30으로 바꿔 달라고 새로 요청했다면 29.9·30·30.1을 새 경계로 예상합니다.

**헷갈리는 반례.** 승인된 새 요청 없이 기준을 바꾸는 것과 업무 담당자가 조건을 변경한 것은 다릅니다.

**직접 적용.** 기준 30이라는 새 요청서 작성하기 → 영향 받을 기대 값 찾기 → 29.9·30·30.1의 예상 작성하기 → 기본 기준 28 을 유지할지 인수로 전달할지 설명하기

**설명할 질문.** 새 조건에서 어떤 기존 검사를 그대로 써야하나요?

**막혔을 때.** 기본 기준 변경과 함수 인수 전달을 혼동하면 classify(30,threshold =30)호출 예를 읽습니다.

입력·답칸·확인 순서는 [실습지의 A16](practice-guide.md#a16)와 [활동 원문](examples/course/data/A16_input.md)에 있습니다.

### A17 · 동료의 변경을 설명하기

**뜻과 비유.** 동료 검토는 작성자의 설명 없이도 요구·변경·검사 근거를 찾을 수 있는지 확인하는 과정입니다.

**왜 필요한가.** 다른 사람에게 설명할 수 없다면 어떤 줄을 왜 바꿨는지 자신도 놓친 부분이 있을 수 있습니다.

**예를 따라 읽기.** 짝은 None 처리와>=조건을 찾고 요청서 및 검사 입력을 한 곳씩 연결합니다.

**헷갈리는 반례.** “테스트됐음”한 줄만 있으면 실행한 대상과 입력이 불명확합니다.

**직접 적용.** 작업본과 검토 노트를 짝에게 전달하기 → 요구 두 개에 대응하는 줄 찾기 → 검사 결과 한 개를 재현하기 → 부족한 설명하나 보완하기

**설명할 질문.** 동료가 다시 확인하려면 어떤 정보가 있어야하나요?

**막혔을 때.** 짝의 작업본을 바로 덮어쓰지 말고 수정 제안을 먼저 기록합니다.

### A18 · 완료 범위와 다음 확인

**뜻과 비유.** 인수인계는 요청한 일, 실제 바뀐 것, 확인한 증거, 남은 조건을 다음 사람이 이해할 수 있게 남기는 일입니다.

**왜 필요한가.** 합성 데이터 검사와 실제 센서 운영은 다른 범위입니다. 확인하지 않은 서비스 호출이나 장비 연결을 완료라고 쓰지 않습니다.

**예를 따라 읽기.** 분류기 아홉 사례 통과·오프라인 응답 검토·실제 AI 호출 미 수행을 함께 적습니다.

**헷갈리는 반례.** AI가 코드를 썼다고 가정하거나 검사 통과만으로 실제 안전 시스템 완성이라고 표현하지 않습니다.

**직접 적용.** 세 문장 인계 작성하기 → 실제 AI 호출 여부 명시하기 → 미검증 조건 두 개 쓰기 → 새 질문:0과 None·기준과 경계·설명과 증거 답하기

**설명할 질문.** 자료 작성과 실제 운영 검증을 어떻게 구분하나요?

**막혔을 때.** 완료 문장이 추상적이면 파일·입력 수·실행 방법을 넣습니다.
