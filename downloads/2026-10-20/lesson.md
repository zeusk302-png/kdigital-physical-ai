# 2026-10-20 · AI 코드에이전트

이전 Python·Git 기초를 짧게 복습하며 준비된 작은 예제를 읽고 수정합니다. **최신 운영은 50분 × 6교시, 순수 수업 300분**입니다. 설명 보충은 필수 개념이며 독립 과제는 추가 복습입니다. 추가 문제는 수업 후 복습에 사용합니다.

실제 AI 계정·모델·유료 API를 호출하지 않습니다. 제공 응답은 강사가 만든 비교 자료입니다. 합성 분류 규칙이며 실제 센서 안전 판단을 검증하지 않았습니다.

전체 코드와 모든 줄의 뜻·실행 방법은 [코드 해설](examples/course/code/line-guide.md)에 있습니다. 작성 소스와 생성된 번들·잠금 파일을 구분합니다.

이 교시는 50분 운영이며 아래 세 개념을 연결합니다. 필수 경로를 먼저 진행하고 추가 복습은 수업 진행에 따라 배정합니다. 학생은 자신의 말로 확인 근거를 설명합니다.

### A01 · 에이전트와 사람의 역할

<!-- enrichment:2026-10-20:P1 -->

#### 사례로 이해하기 · 실행하는 AI와 책임을 갖는 사람


#### 실무 상황

센서 안내 프로그램을 고치려는 직원이 AI에게 “온도 분류를 개선해 줘”라고 보냅니다. AI는 파일 이름과 기준을 추측하고 새 코드를 제안할 수 있습니다. 직원이 기대한 것은 경계 오류 하나의 수정인데 프로그램 전체가 바뀌면 검토가 어려워집니다. 먼저 맡길 범위와 사람이 결정할 규칙을 구별합니다.

#### 쉬운 풀이

대화형 AI는 문장이나 코드를 답할 수 있습니다. 코드에이전트는 허용된 도구를 이용하여 파일을 읽고 고치거나 실행까지 이어갈 수 있습니다. 가능한 능력과 이번 작업에서 허용한 행동은 다릅니다. 프롬프트는 요청 글이고 컨텍스트는 그 요청을 이해하는 데 필요한 자료입니다. 사람은 업무 기준, 공유할 자료, 적용 승인, 실제 확인 범위를 결정합니다. 도구가 읽지 못한 숨은 규칙까지 안다고 추정하지 않습니다.

#### 완성 예와 풀이

요청의 목적을 “28 이상을 주의로 분류”로 적습니다. 대상은 work/classifier.py의 classify 함수이며 입력은 가상 온도, 출력은 정상·주의·미측정·입력 오류입니다. 관련 자료는 현재 함수와 cases.json, 실패 출력 마지막 부분입니다. 읽기와 수정은 이 연습 복사본에만 허용하고 외부 게시와 계정 접근은 허용하지 않습니다. 실제 토큰 대신 `DEMO_TOKEN`이라는 표시를 씁니다. 확인 근거는 변경 비교와 같은 검사 입력의 실행 결과입니다. 제공 AI 응답은 수업용 작성 자료이며 실제 모델 호출 증거가 아닙니다.

#### 독립 추가 복습 과제

파일 세 개, 고객 명단, 접속 암호, 가상 실패 로그 가운데 온도 경계 수정에 필요한 자료를 선택하세요. 이어서 “목적 / 바꿀 곳 / 유지할 것 / 금지할 행동 / 확인 근거” 다섯 줄 요청서를 작성하세요.

#### 답과 대표 오답

현재 함수·검사 입력·가상 실패 로그를 선택하고 고객 명단과 암호는 제외합니다. “자료를 전부 보내면 정확해진다”는 답은 관련성과 공유 범위를 검토하지 않았습니다. “AI가 썼으니 실행도 했다” 역시 생성과 실행의 차이를 놓칩니다.

#### 확인 질문과 해설

① 에이전트 이름이 능력을 보장하나요? 실제 연결 도구와 권한을 확인해야 합니다. ② 비밀이 필요한 상황은 어떻게 하나요? 그대로 공유하지 말고 담당 절차와 대체 데이터를 확인합니다. ③ 완료 판단은 누구의 일인가요? 요구와 증거를 대조하는 사람의 판단이 필요합니다.


**뜻과 비유.** 코드에이전트는 요청을 해석하고 파일과 실행 도구를 사용해 작업을 이어 가는 AI 도구입니다. 대화 답변 한 번과 파일 변경·실행이 연결된 작업 흐름을 구분합니다.

**왜 필요한가.** 동료에게 일을 맡겨도 완료 기준은 함께 정합니다. 코드가 생겼다는 사실과 업무 요구가 충족됐다는 사실은 다릅니다.

**예를 따라 읽기.** 센서 온도 28을 주의로 분류해 달라는 요청은 입력·기준·출력·확인 방법을 포함할 수 있습니다.

**헷갈리는 반례.** “알아서 좋게 고쳐”는 유지해야할 함수 이름이나 28 ℃ 경계를 알려 주지 않습니다.

**직접 적용.** 요청서에서 목적을 한 문장으로 찾기 → AI가 제안할 일과 사람이 판단할 일 나누기 → 완료라고 부를 증거 두 가지 적기 → 짝에게 도구와 검토자의 역할 설명하기

**설명할 질문.** 코드가 생긴 것만으로 완료가 아닌 이유는 무엇인가요?

**막혔을 때.** 도구 이름과 능력을 혼동하면 읽기·변경·실행 중 실제로 허용한 행동을 따로 적습니다.

입력·답칸·확인 순서는 [실습지의 A01](practice-guide.md#a01)와 [활동 원문](examples/course/data/A01_input.md)에 있습니다.

### A02 · 작은 작업과 수정 범위

**뜻과 비유.** 작업 범위는 어떤 파일과 동작을 바꿀지 정한 경계입니다. 전체 프로그램을 한 번에 고치기보다 한 함수의 분류 규칙처럼 확인 가능한 단위로 나눕니다.

**왜 필요한가.** 범위를 알면 변경 비교가 짧아지고 잘못 바꾼 항목을 되돌리기 쉽습니다. 10/16의 변경 비교가 여기서 업무 검토 근거가 됩니다.

**예를 따라 읽기.** 오늘은 classifier.py의 classify 동작만 바꾸고 함수 이름과 threshold =28을 유지합니다.

**헷갈리는 반례.** 결과를 맞추려고 cases.json 기대 값을 변경하면 검사기준을 바꾼 것이므로 요청을 해결한 증거가 아닙니다.

### A04 · 입력과 출력 계약

<!-- enrichment:2026-10-20:P2 -->

#### 사례로 이해하기 · 요청을 검사 가능한 약속으로 바꾸기


#### 실무 상황

동료가 “높은 온도를 주의로 표시”라고만 설명합니다. 28은 높은 값인가요? 값이 없으면 무엇을 표시하나요? 기계가 이해할 조건을 쓰기 전에 사람끼리 애매한 표현을 정확한 입출력 약속으로 바꿔야 합니다. 코드 한 줄의 차이가 사용자 안내를 바꾸기 때문입니다.

#### 쉬운 풀이

계약은 함수가 받을 값과 돌려줄 결과의 약속입니다. 정상 사례는 흔한 입력, 경계 사례는 규칙이 바뀌는 근처 입력, 오류 사례는 허용하지 않은 입력입니다. 온도 0은 측정값이고 None은 값이 없다는 표시입니다. 글자 "28"과 숫자 28은 화면에 비슷해 보여도 자료형이 다릅니다. 오늘 계약은 문자 숫자를 자동 변환하지 않고 입력 오류로 처리합니다. 업무 규칙이 달라지면 별도 승인이 필요합니다.

#### 완성 예와 풀이

함수 이름 classify와 기본 기준 28을 유지합니다. 유효한 수는 0~50이며 28 이상은 주의, 미만은 정상입니다. None은 미측정, 문자·불리언·범위 밖 값은 입력 오류입니다. `classify(27.9)`→정상, `classify(28)`→주의, `classify(28.1)`→주의, `classify(None)`→미측정으로 표를 작성합니다. `classify(0)`→정상을 별도 행으로 두면 None을 0으로 바꾼 후보의 문제를 찾을 수 있습니다. 기준을 27로 내리면 27.9의 약속이 깨집니다. 검사 파일의 기대 값을 바꾸어서 후보를 통과시키면 요구 검증이 되지 않습니다.

#### 독립 추가 복습 과제

냉장 보관 가상 규칙은 “5 초과이면 점검, 5 이하는 정상”입니다. 4.9·5·5.1의 기대를 직접 쓰고 온도 기준의 “이상” 규칙과 어떤 비교 기호가 다른지 설명하세요. 누락 값의 처리 약속도 한 문장 작성하세요.

#### 답과 대표 오답

4.9와 5는 정상, 5.1은 점검이며 초과는 >입니다. “5도 점검”은 초과와 이상을 혼동했습니다. 누락은 측정하지 못했음을 별도로 표시해야 하며 정상으로 채우는 답은 유효 측정과 누락을 합칩니다.

#### 확인 질문과 해설

① 함수 이름을 유지하는 이유는 무엇인가요? 기존 호출자가 같은 이름을 사용합니다. ② 경계 세 값을 두는 이유는 무엇인가요? 기준과 비교 기호의 오류를 구별합니다. ③ 출력 표만 맞으면 충분한가요? 실제 대상 함수의 실행과 유지 조건도 확인합니다.


**뜻과 비유.** 입출력 계약은 어떤 값을 받아 어떤 형태로 답할지 정한 약속입니다. 함수의 내부가 달라져도 호출하는 쪽이 기대하는 이름과 결과는 유지해야합니다.

**왜 필요한가.** 함수 이름을 바꾸거나 새 숫자 코드를 반환하면 기존 호출 자는 결과를 이해하지 못할 수 있습니다.

**예를 따라 읽기.** classify(28)는 주의, classify(None)는 미측정으로 답하도록 요청에 씁니다.

**헷갈리는 반례.** 미측정을 정상으로 부르면 측정하지 못한 상황이 정상 온도로 보입니다.

**직접 적용.** 요청서에서 허용 입력 추출하기 → 네 반환 문자열을 표로 쓰기 → 함수 호출 하나의 입력·출력 연결하기 → task.md에 계약 작성하기

**설명할 질문.** 함수 이름과 반환 문자열을 유지하는 이유는 무엇인가요?

**막혔을 때.** None과 문자열 "None"이 헷갈리면 10/8의 값 없음과 글자 차이를 다시 비교합니다.

입력·답칸·확인 순서는 [실습지의 A04](practice-guide.md#a04)와 [활동 원문](examples/course/data/A04_input.md)에 있습니다.

### A05 · 정상·경계·오류 사례

**뜻과 비유.** 검사 사례는 입력과 기대 결과를 한 쌍으로 적은 것입니다. 경계 사례는 규칙이 달라지는 바로 앞·같은 값·바로 뒤를 비교합니다.

**왜 필요한가.** 평범한 22.5 하나가 통과해도 28에서 비교 기호가 틀린 문제는 드러나지 않습니다.

**예를 따라 읽기.** 27.9는 정상, 28 과 28.1은 주의입니다. 0은 유효하며 None은 미측정입니다.

**헷갈리는 반례.** 글자 “뜨거움”을 0으로 바꿔 처리하면 오류 입력이 정상 기록으로 둔갑합니다.

**직접 적용.** cases.json 아홉 입력 읽기 → 실행 전에 기대 상태 써 보기 → 경계 세 사례를 묶기 → 결과가 틀릴 때의 업무 영향을 설명하기

**설명할 질문.** 왜 28만 확인하지 않고 27.9와 28.1도 보나요?

**막혔을 때.** 숫자와 불리 언을 혼동하면 type(True)가 bool임을 확인하고 온도 계약과 비교합니다.

입력·답칸·확인 순서는 [실습지의 A05](practice-guide.md#a05)와 [활동 원문](examples/course/data/A05_input.md)에 있습니다.

### A06 · 검증 가능한 프롬프트

**뜻과 비유.** 프롬프트는 도구에게 전달하는 요청 문장입니다. 목표·입력·범위·유지 조건·확인 사례를 짧게 연결하면 모호한 칭찬 대신 확인 가능한 결과를 요구할 수 있습니다.

**왜 필요한가.** 검사 방법을 먼저 적으면 도구가 스스로 완료라고 말해도 무엇이 확인됐는지 비교할 수 있습니다.

**예를 따라 읽기.** “28 이상은 주의로 고치고 None은 미측정으로 남기며 아홉 사례를 실행해 결과를 보고해 주세요.”

**설명할 질문.** 좋은 요청에 실행 전 기대 결과가 들어가는 이유는 무엇인가요?

**막혔을 때.** 요청이 길어지면 목적과 유지 조건을 분리하고 이번에 필요 없는 기능은 후속 요청으로 둡니다.

### A07 · 변경 비교의 기호 읽기

<!-- enrichment:2026-10-20:P3 -->

#### 사례로 이해하기 · 그럴듯한 완료 문장에서 근거 찾기


#### 실무 상황

제공 응답 A는 “모든 문제를 해결했습니다”라고 말합니다. 하지만 코드에서 기본 기준을 27로 낮추고 None을 0으로 바꿨습니다. 친절하고 자신 있는 문장은 업무 규칙을 충족했다는 증거가 아닙니다. 검토자는 주장, 실제 변경, 실행 기록을 각각 찾아 연결해야 합니다.

#### 쉬운 풀이

변경 비교는 이전과 이후의 차이를 보여 줍니다. 삭제 표시 -와 추가 표시 +는 파일 내용에 넣는 기호가 아닙니다. 주장에는 “고쳤다”, “검사했다”, “운영 가능하다”처럼 서로 다른 범위가 있습니다. 첫 주장은 코드 차이로, 둘째는 대상과 명령과 출력으로, 셋째는 실제 환경 증거로 확인합니다. 증거가 없으면 거짓으로 단정하기보다 확인하지 못했다고 적고 다음 검사 질문을 만듭니다.

#### 완성 예와 풀이

code/proposal_a.py를 읽으면 `threshold=27`과 None을 0으로 바꾸는 줄이 보입니다. 요청의 유지 조건은 threshold=28이고 None은 미측정입니다. 먼저 두 차이를 표시한 뒤 같은 code/check_cases.py로 실행합니다. 응답의 말과 실제 함수 동작은 별도로 기록합니다. 실행 경로가 proposal_a.py인지도 확인합니다. work/classifier.py를 고쳤는데 baseline.py를 실행했다면 고친 내용에 대한 증거가 아닙니다. 복구할 때는 원본 baseline.py를 보존한 채 작업 복사본만 다시 가져옵니다.

#### 독립 추가 복습 과제

“수정 완료, 오류 없음, 실제 장비에서도 안정적”이라는 세 주장 옆에 필요한 증거를 한 종류씩 적으세요. 주어진 자료가 코드 비교와 로컬 가상 검사 출력뿐일 때 어느 문장까지 보고할 수 있는지도 결정하세요.

#### 답과 대표 오답

변경 완료에는 diff, 오류 검사는 사례별 실행 결과, 장비 안정성에는 실제 장비와 운영 조건의 관찰이 필요합니다. 현재는 가상 검사 범위만 보고하고 장비 부분은 미확인으로 남깁니다. “AI의 자신감이 높아서 승인”은 검증 근거가 없습니다. “검사 결과가 없으니 코드는 반드시 틀렸다”도 증거 부족과 실패를 혼동합니다.

#### 확인 질문과 해설

① 코드 차이만으로 실행 성공을 아나요? 실행 증거가 필요합니다. ② 통과 화면에 대상 경로가 필요한 이유는 무엇인가요? 어느 복사본을 확인했는지 식별합니다. ③ 불확실성을 어떻게 쓰나요? 관찰 사실과 아직 확인하지 않은 조건을 나누어 구체적으로 적습니다.


**뜻과 비유.** diff는 전후 코드에서 빠진 줄과 새 줄을 보여 주는 변경 비교입니다. -는 이전 줄, +는 새 줄이며 코드의 빼기·더하기 연산과 다릅니다.

**왜 필요한가.** 전체 파일을 외우지 않아도 요청이 어느 변경에 반영됐는지 확인할 수 있습니다.

**예를 따라 읽기.** >를 >=로 바꾼 줄은 경계 28을 포함하도록 동작을 바꿉니다.

**헷갈리는 반례.** 주석만 “28 이상”으로 바뀌고 실제 비교가 >이면 동작은 그대로입니다.

**직접 적용.** changes.diff에서 파일 이름 찾기 → 미측정·검사·경계 변경 줄 묶기 → 요청한 항목과 변경 한 곳 연결하기 → 문구 변경과 동작 변경 구분하기

**설명할 질문.** diff의 +와 Python의 +는 어떤 차이가 있나요?

**막혔을 때.** diff의 +를 원본 코드에 복사했다면 실제 소스 파일의 완성 줄을 참고해 제거합니다.

### A10 · 기준 코드의 실제 실패

<!-- enrichment:2026-10-20:P4 -->

#### 사례로 이해하기 · 실패 결과를 요구와 연결하는 검사


#### 실무 상황

프로그램이 실행되었는데 검사 결과에 FAIL이 보입니다. 비전공자는 설치가 잘못됐다고 생각하기 쉽습니다. 하지만 이 검사기는 요구와 다른 출력이 나오면 의도적으로 실패 상태를 남깁니다. 실패를 읽을 수 있으면 재설치보다 수정할 규칙을 먼저 찾을 수 있습니다.

#### 쉬운 풀이

예상은 실행 전에 규칙으로 정한 답이고 실제는 실행으로 관찰한 답입니다. 종료 코드 0은 이 검사에서 모든 사례가 맞았다는 뜻이며 1은 적어도 하나가 달랐다는 뜻입니다. 이 의미는 프로그램마다 다릅니다. TypeError가 출력에 보이면 값 종류에 맞지 않는 비교가 발생했을 수 있습니다. 누락과 종류와 범위를 먼저 확인한 뒤 경계를 비교하면 오류 상황을 정상 온도로 착각하지 않습니다.

#### 완성 예와 풀이

압축을 푼 course에서 `python code/check_cases.py code/baseline.py`를 실행합니다. baseline은 28을 정상, None을 정상으로 반환하고 문자 비교에서는 예외가 발생합니다. 따라서 성공적인 수업 시연에서도 종료 코드가 1입니다. reviewed.py는 None을 먼저 미측정으로 처리하고 정확한 숫자 종류와 0~50 범위를 확인한 뒤 >=28을 적용합니다. `python code/check_cases.py code/reviewed.py`는 제공 아홉 사례에서 9/9입니다. 예상 목록이 같고 실행 대상만 달라졌음을 확인해야 변화의 원인을 설명할 수 있습니다.

#### 독립 추가 복습 과제

입력 0, None, True, "28", 50, 51의 출력을 먼저 표로 작성하세요. 이후 제공 완성 함수의 조건을 위에서 아래로 따라가며 각 입력이 어느 줄에서 반환되는지 설명하세요. 조건 순서를 바꾸면 문자 비교가 어떻게 달라지는지도 판단하세요.

#### 답과 대표 오답

0은 정상, None은 미측정, True와 "28"과 51은 입력 오류, 50은 주의입니다. “True는 1과 같으니 정상”은 오늘의 계약이 허용한 정확한 종류를 놓쳤습니다. “None은 0”은 값 없음과 유효한 영점을 혼동합니다.

#### 확인 질문과 해설

① FAIL이면 파이썬이 실행되지 않았나요? 실행된 뒤 기대와 달랐을 수 있습니다. ② 기준만 낮추면 해결되나요? 기존 정상 경계를 깨뜨립니다. ③ 아홉 통과로 모든 입력을 보장하나요? 제공된 검사 범위만 확인한 것이므로 새로운 입력 조건은 별도로 검토합니다.


**뜻과 비유.** 실패 검사는 실수로 망가진 수업이 아니라 요구와 현재 동작의 차이를 드러내는 관찰입니다. 검사 프로그램은 기대와 실제를 나란히 비교합니다.

**왜 필요한가.** 수정 전 실패를 재현해 두면 수정 후 무엇이 달라졌는지 확인할 기준이 생깁니다.

**예를 따라 읽기.** python code/check_cases.py code/baseline.py를 실행하면 경계와 미측정 등의 차이가 FAIL로 나옵니다.

**직접 적용.** 전체 검사 코드와 줄 해설 읽기 → 원본 실행 명령 확인하기 → 아홉 줄 결과에서 FAIL의 입력 찾기 → 예상과 실제 차이를 표에 남기기

**설명할 질문.** 테스트가 실패한 것과 실행환경이 고장 난 것은 어떻게 구별하나요?

**막혔을 때.** 모듈 경로 오류면 course 폴더에서 명령을 실행하고 파일 경로 인수를 빠뜨리지 않았는지 봅니다.

### A12 · 누락과 잘못된 입력 처리

**뜻과 비유.** 입력 검사는 자료가 함수의 약속에 맞는지 살펴보는 것입니다. 값이 없는 경우와 종류가 틀린 경우, 범위를 벗어난 경우를 따로 처리합니다.

**왜 필요한가.** 없음을 0으로 채우면 실제 0 측정과 구분할 수 없고 문자에 비교 연산을 하면 실행 오류가 납니다.

**예를 따라 읽기.** reviewed.py는 None →미측정, 숫자 아님 →입력 오류, 범위 밖 →입력 오류를 먼저 검사합니다.

**헷갈리는 반례.** Python에서 bool은 숫자와 관련된 특성이 있지만 이 업무 계약은 온도로 받지 않으므로 type을 정확히 확인합니다.

### A13 · 재현 가능한 오류 보고

<!-- enrichment:2026-10-20:P5 -->

#### 사례로 이해하기 · 다른 사람이 재현할 수 있는 오류 보고


#### 실무 상황

#### 쉬운 풀이

재현은 같은 조건에서 같은 현상을 다시 보는 일입니다. 회귀는 새 변경 때문에 이전에 맞던 동작이 다시 틀리는 현상입니다. 오류 보고에는 현재 폴더, 대상 파일, 실행 명령, 입력, 기대, 실제, 관찰 방식이 들어갑니다. 추정 원인은 별도 칸에 씁니다. 학생이 강사 시연을 봤다면 개인 실행으로 적지 않고 관찰이라고 표시합니다. 제공 결과를 읽기만 했다면 기록 읽기로 구분합니다.

#### 독립 추가 복습 과제

“검사에서 text 행이 TypeError”인 상황의 재현 보고 다섯 줄을 쓰세요. 확정 사실 하나와 추정 하나를 표시하고, 고친 뒤에도 반드시 다시 확인할 다른 입력을 두 개 골라 이유를 설명하세요.

① 통과 수만 기록하면 충분한가요? 같은 수라도 실패 입력이 다를 수 있습니다. ② 재검사에 기존 사례가 필요한 이유는 무엇인가요? 회귀를 찾습니다. ③ 원인을 확정하는 시점은 언제인가요? 코드와 재현 결과가 가설을 뒷받침할 때입니다.


**뜻과 비유.** 오류 보고는 실제로 한 행동·입력·기대한 결과·실제 결과를 다른 사람이 다시 따라갈 수 있게 적은 문서입니다.

### A16 · 새 조건의 영향 분석

<!-- enrichment:2026-10-20:P6 -->

#### 사례로 이해하기 · 새 기준과 완료 범위를 인계하기


#### 실무 상황

담당자가 새 장소에는 기준 30을 적용해 달라고 승인했습니다. 기존 모든 장소의 기본값을 30으로 바꾸면 이전 업무가 달라집니다. 새 요청이 특정 장소만의 조건인지 전체 기본값 변경인지 먼저 확인하고 영향 받는 호출과 검사를 찾습니다.

#### 쉬운 풀이

함수 인수는 호출할 때 전달하는 입력입니다. 기본값은 그 인수를 생략했을 때 사용하는 값입니다. `classify(29.9, threshold=30)`과 `classify(29.9)`는 같은 입력 온도지만 기준이 다르므로 결과가 다를 수 있습니다. 요구 변경은 검사의 기대를 바꿀 수 있으나 어떤 승인된 요구에 따른 변경인지 근거를 남겨야 합니다. 기존 실패를 숨기려고 기대를 바꾼 상황과 구별합니다.

#### 완성 예와 풀이

새 장소 요청서에 기준 30, 기본 계약 28 유지, 유효 범위 0~50 유지라고 씁니다. 새 호출의 29.9는 정상, 30과 30.1은 주의입니다. 기본 호출의 28은 여전히 주의입니다. None은 두 호출 모두 미측정이고 범위 밖은 입력 오류입니다. 인계에는 수정한 파일, 변경 조건, 기본 아홉 사례 결과, 새 경계 세 사례 결과, 실제 AI 호출 여부를 씁니다. 오늘은 제공 응답을 검토한 오프라인 활동이며 실제 센서 안전 판단과 실제 AI 서비스 연결은 확인하지 않았다고 기록합니다.

#### 독립 추가 복습 과제

기준 30을 특정 장소에만 적용하는 요청과 전체 기본값을 30으로 바꾸는 요청을 각각 한 문장으로 작성하세요. 두 요청에서 기대가 달라질 기본 호출 한 개를 고르고, 동료가 다시 확인할 명령과 자료 위치를 인계문에 넣으세요.

#### 답과 대표 오답

특정 장소에는 threshold 인수를 명시하고 전체 변경에는 기본값 변경 승인을 명시합니다. 기본 classify(28)은 전자에서 주의, 후자에서 정상입니다. “새 검사가 통과했으니 모든 서비스 운영 완료”는 검증 범위를 넘었습니다. “새 요청은 절대 기대를 바꾸면 안 된다”도 승인된 요구 변경을 무시합니다.

#### 확인 질문과 해설

① 기본값과 인수는 왜 구별하나요? 영향 받는 호출 범위가 다릅니다. ② 동료가 같은 결과를 보려면 무엇이 필요한가요? 대상 파일·실행 위치·입력·기대를 연결한 기록입니다. ③ 아직 모르는 사항은 어떻게 전달하나요? 실제 환경, 장비, 계정 등 미확인 항목과 다음 확인 담당을 구체적으로 남깁니다.


**뜻과 비유.** 새 업무 조건은 기존 규칙과 독립인지 먼저 확인한 뒤 작은 사례로 설계합니다. 오늘은 추가 코드보다 변경이 영향 줄 입력을 설명하는 일에 집중합니다.

**왜 필요한가.** 특수 기준을 추가하면 조건 순서와 기존 계약을 함께 검토해야합니다.

**예를 따라 읽기.** 담당자가 기준을 30으로 바꿔 달라고 새로 요청했다면 29.9·30·30.1을 새 경계로 예상합니다.

**헷갈리는 반례.** 승인된 새 요청 없이 기준을 바꾸는 것과 업무 담당자가 조건을 변경한 것은 다릅니다.

**직접 적용.** 기준 30이라는 새 요청서 작성하기 → 영향 받을 기대 값 찾기 → 29.9·30·30.1의 예상 작성하기 → 기본 기준 28 을 유지할지 인수로 전달할지 설명하기

**설명할 질문.** 새 조건에서 어떤 기존 검사를 그대로 써야하나요?

**막혔을 때.** 기본 기준 변경과 함수 인수 전달을 혼동하면 classify(30,threshold =30)호출 예를 읽습니다.

**왜 필요한가.** 합성 데이터 검사와 실제 센서 운영은 다른 범위입니다. 확인하지 않은 서비스 호출이나 장비 연결을 완료라고 쓰지 않습니다.

**예를 따라 읽기.** 분류기 아홉 사례 통과·오프라인 응답 검토·실제 AI 호출 미 수행을 함께 적습니다.

**헷갈리는 반례.** AI가 코드를 썼다고 가정하거나 검사 통과만으로 실제 안전 시스템 완성이라고 표현하지 않습니다.

**직접 적용.** 세 문장 인계 작성하기 → 실제 AI 호출 여부 명시하기 → 미검증 조건 두 개 쓰기 → 새 질문:0과 None·기준과 경계·설명과 증거 답하기

**설명할 질문.** 자료 작성과 실제 운영 검증을 어떻게 구분하나요?

**막혔을 때.** 완료 문장이 추상적이면 파일·입력 수·실행 방법을 넣습니다.

입력·답칸·확인 순서는 [실습지의 A18](practice-guide.md#a18)와 [활동 원문](examples/course/data/A18_input.md)에 있습니다.
