# E07 · 화면·데이터·함수를 함께 설계하기

무엇을 보여 주고, 어떤 값을 저장하고, 어디서 계산할지 연결합니다.

## 화면의 흐름

```text
장비 목록 선택
      ↓
대여 또는 반납 버튼
      ↓
장비 번호·수량 검사
      ↓
수량 변경 → 파일 저장 → 목록 새로 표시
실패하면 안내하고 수량 유지
```

버튼을 예쁘게 만드는 것만으로 기능이 완성되지는 않습니다. 화면에 보이는 값과 파일에 저장된 값이 같아야 합니다.

## 데이터 예시

```json
[
  {"id": "CAM01", "name": "카메라", "total": 2, "available": 1},
  {"id": "MIC01", "name": "마이크", "total": 3, "available": 3}
]
```

`id`는 이름이 바뀌어도 같은 장비를 찾는 식별자입니다. `total`은 전체 수량, `available`은 지금 빌릴 수 있는 수량입니다. 항상 `0 ≤ available ≤ total`이어야 합니다. 이름을 화면에 보여 주되 내부 처리는 번호로 구별합니다.

## 파일의 책임 나누기

| 파일 | 맡는 일 | 섞지 않을 일 |
|---|---|---|
| app.py | 창·선택·버튼·메시지 | 파일 형식의 세부 처리 |
| inventory.py | 수량 검사·대여·반납·저장 | 버튼 배치 |
| data/equipment.json | 장비 자료 | Python 실행 코드 |
| test_inventory.py | 조건별 결과 확인 | 실제 수업 원본 자료 변경 |

파일을 무조건 많이 나누는 것이 목적은 아닙니다. 화면을 고쳤을 때 수량 계산까지 다시 만들지 않게 책임을 분리합니다.

## 설계 요청

```text
docs/requirements.md와 현재 코드를 읽어.
화면·대여 계산·JSON 저장을 어느 파일이 맡는지 설명해.
각 함수의 입력, 반환값, 실패 시 동작을 표로 제안해.
새 라이브러리 없이 현재 파일 구조를 유지하는 설계를 우선해.
아직 구현하지 마.
```

## 직접 바꿔 보기

장비명 검색을 추가한다면 JSON 필드가 반드시 늘어나야 할까요? 기존 `name`을 이용해 화면에 보일 목록만 거르면 됩니다. 검색 때문에 전체 장비 파일을 덮어쓰지 않도록 설명해 보세요.

## 확인

선택한 장비가 없을 때 UI가 먼저 안내하는지, 없는 번호가 함수에 직접 들어와도 계산 함수가 거부하는지 나눠 봅니다. 화면 검사만으로 계산 함수까지 보호되는 것은 아닙니다.
