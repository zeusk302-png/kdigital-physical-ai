# E08 · 잘 수행할 수 있는 작업 요청 만들기

길이보다 필요한 정보와 확인 가능한 완료 조건이 중요합니다.

## 여덟 항목으로 나누기

목적 → 현재 상태 → 참고 파일 → 수정 범위 → 유지 조건 → 완료 조건 → 시험 방법 → 결과 보고를 적습니다. 작은 질문마다 전부 채울 필요는 없지만 파일을 바꾸는 작업에는 범위와 완료 조건을 꼭 넣습니다.

## 모호한 요청을 고쳐 보기

“대여 프로그램 완벽하게 만들어 줘”에는 수정 범위와 실패 조건이 없습니다. 아래 요청과 비교하세요.

```text
목적: 장비 대여 버튼이 실제로 작동하게 한다.
현재: 목록과 버튼은 있고 checkout 함수는 아직 연결 전이다.
참고: README.md, docs/requirements.md, inventory.py, app.py.
범위: checkout 함수와 꼭 필요한 버튼 연결만 수정한다.
유지: JSON 필드 이름·기존 화면·Python 표준 라이브러리.
완료: 재고가 있으면1 감소, 재고0·없는 번호는 안내하고 그대로 유지.
시험: 정상 대여·재고0·없는 번호의 전후 수량을 비교한다.
보고: 바꾼 파일, 실행한 명령, 결과, 남은 문제를 적는다.
먼저 계획을 제시하고, 불명확한 조건이 있으면 질문해.
```

## 오류 수정 요청은 재현 자료와 함께

```text
예상: 남은 수량0에서 대여하면 안내 후0 유지.
실제: 대여 버튼을 누르면 -1이 됨.
재현: CAM01의 available을0으로 설정 → 실행 → CAM01 선택 → 대여.
관련: inventory.py의 checkout, app.py의 버튼 처리.
원인을 설명하고 최소한으로 수정해.
같은 문제가 다시 생기는지 확인할 시험도 추가해.
```

## 직접 작성

반납 기능을 위 틀로 작성하세요. “대여와 똑같이 해”라고만 쓰지 말고 전체 수량을 초과하는 경우를 넣습니다.

## 풀이의 핵심

반납은 `available + 1`이 아니라 먼저 `available < total`을 확인해야 합니다. 에이전트가 규칙을 추측하게 두지 말고 요구사항에서 정합니다.

## 요청 뒤에 할 일

답변의 계획에서 요구사항과 다른 점을 짚습니다. 질문을 잘했다고 모든 출력이 맞아지는 것은 아닙니다. 실제 diff와 시험 결과를 확인하고 조건에서 벗어난 수정은 다시 요청합니다.
