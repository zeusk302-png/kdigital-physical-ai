# E06 · 만들기 전에 요구사항 정하기

필요한 기능을 적고, 어떤 상태면 완성인지 먼저 정합니다.

## 요구사항은 기능 이름보다 구체적입니다

“대여 프로그램”만으로는 누구에게 어떤 기능이 필요한지 알 수 없습니다. 사용자가 실제로 하는 일을 한 문장으로 적습니다.

> 실습실 담당자가 남은 장비를 보고 한 개를 대여·반납하며, 프로그램을 다시 열어도 수량이 유지되게 한다.

여기서 로그인·결제·예약 알림은 이번 필수 범위에 없습니다. 기능을 덜 만드는 이유는 수업 안에서 완성하고 시험할 범위를 정하기 위해서입니다.

## 필수 요구사항

| 번호 | 필요한 동작 | 완료 조건 |
|---|---|---|
| R01 | 장비 목록 표시 | 이름·전체 수량·남은 수량을 볼 수 있다 |
| R02 | 장비 대여 | 남은 수량이 1 줄고 화면에 반영된다 |
| R03 | 잘못된 대여 방지 | 재고0·미선택·없는 번호는 자료를 바꾸지 않는다 |
| R04 | 장비 반납 | 전체 수량을 초과하지 않고 1 늘어난다 |
| R05 | 저장과 복원 | 재실행 후 마지막 저장 상태가 나타난다 |

## 사례를 먼저 적기

```text
조건: 카메라 전체2개, 남은1개
행동: 카메라를 선택하고 대여
예상: 남은0개로 바뀌고 저장됨

조건: 같은 카메라의 남은0개
행동: 다시 대여
예상: 재고 부족 안내, 남은0개 유지
```

이렇게 조건·행동·예상 결과로 나눈 문장을 수용 기준이라고 부릅니다. 받아들일 수 있는 결과의 기준이라는 뜻입니다.

## 함께 작성하기

```text
실습실 담당자가 쓰는 장비 대여 프로그램을 설계하려고 해.
로그인·결제·온라인 서버는 이번 범위에서 제외해.
대여·반납·JSON 저장에 대해 사용자 행동과 완료 조건을 작성해.
정상 사례와 실패 사례를 각각 넣어 줘.
확정되지 않은 점은 별도 질문으로 남기고 아직 코드는 바꾸지 마.
```

## 직접 작성

`docs/requirements.md`에서 R04의 전체 수량 초과 반납 사례를 완성하세요. “잘 처리한다” 대신 수량이 몇 개로 유지되는지 적습니다.

## 풀이 확인

전체2·남은2인 장비를 반납하면 이미 모두 반납됐다는 안내를 하고 남은2를 유지합니다. 남은3으로 바뀌면 실패입니다. 화면 문구가 달라도 이 조건은 같아야 합니다.
