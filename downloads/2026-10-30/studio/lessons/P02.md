# P02 · 기존 대안과 MVP 선택

멋진 기술보다 실제 필요·구현 가능·시험 가능 기준으로 범위를 정합니다.

## 대안은 경쟁 서비스만이 아닙니다

엑셀·전화·수작업·기존 장비·문제를 해결하지 않는 선택도 현재 대안입니다. 사용자가
새 프로그램으로 바꾸려면 무엇이 나아져야 하는지 비교합니다. 공개 서비스의 기능은
실제 페이지에서 확인하고 URL·확인 날짜를 남깁니다. 광고 문구를 실제 성능이나 사용자
검증 결과로 옮겨 적지 않습니다.

## 비교 기준 정하기

필요성·데이터 확보·장비·계정·정확도·응답시간·제작 기간·시험 가능성을 사용 목적에
맞게 고릅니다. 점수를 붙였다면 근거를 한 줄씩 적습니다. 세밀한 소수 점수를 만들어
객관적으로 보이게 하기보다 어떤 판단 때문에 선택이 바뀌는지 설명합니다.

## 최소 범위

MVP는 기능을 무조건 적게 만드는 것이 아니라 핵심 가치를 시험할 수 있는 범위입니다.
로그인 없이도 확인할 수 있는 기능에 계정 시스템부터 붙이지 않습니다. 위험한 연결이
있다면 그 기능을 먼저 검증하고, 안 될 때의 대체 경로를 정합니다.

## 직접 작성

필수 기능3개 안팎, 이번 제외 기능, 범위가 늘어나는 요청을 판단할 기준을 적습니다.
예를 들어 영상 인식이면 “모든 위험 감지” 대신 어떤 객체·장소·사건을 다루는지 정합니다.
웹이면 누가 어떤 행동을 완료하는지 적습니다. 제어면 어떤 입력과 출력의 관계를 시험할지
정합니다. 공통 점수표로 모두 같은 아이디어를 고르게 하지는 않습니다.

## 확인

필수 기능이 없어도 핵심 가치를 확인할 수 있다면 그 기능의 우선순위를 다시 봅니다.
제외 범위는 포기 목록이 아니라 기간과 검증을 지키는 약속입니다.

## 실제 파일과 연결해서 읽기

[전체 파일 받기](../kit/docs/research.md)

아래는 파일 앞부분입니다. 실행은 전체 파일로 합니다. 생략한 코드를 그대로 실행하지 마세요.

```python
# 대안 조사와 범위

|---|---|---|---|

## 이번 필수와 제외 범위
[작성] MVP와 추가 요청 판단 기준.
```

## 실습을 끝내기 전에

먼저 실행 위치와 파일 이름을 확인합니다. 코드를 바꾸기 전 출력이나 화면을 예상하고,
실행 후 실제 결과를 비교합니다. 에이전트가 수정했다면 git diff에서 이번 요구와 무관한
변경이 섞이지 않았는지 봅니다. 다음 단계가 막힐 때는 현재 작업을 보존하고 실행 가능한
기준본과 비교하되, 기준본을 실행한 결과와 내가 구현한 결과를 구분합니다.

결과 기록에는 내가 바꾼 파일, 입력과 조건, 실제 결과, 실패한 것과 다음 확인을 적습니다.
설명문을 길게 쓰는 대신 코드·실행 명령·짧은 화면 또는 출력으로 확인할 수 있게 남깁니다.
