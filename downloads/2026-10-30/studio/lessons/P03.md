# P03 · 요구사항과 수용 기준 작성

기획의 표현을 개발자가 구현하고 시험할 수 있는 문장으로 바꿉니다.

## 기능과 품질

요구사항은 사용자가 할 일과 시스템이 지킬 조건을 다룹니다. “빠르고 정확하게”만 적으면
완료를 판단하기 어렵습니다. 어떤 입력·환경·자료에서 어떤 결과를 어떻게 측정할지
정합니다. 수치를 정했다면 근거와 측정 방법을 붙이고 확인하지 않은 목표를 성능 결과로
표시하지 않습니다.

## 작은 형식

요구번호 R01, 사용자 행동, 입력 조건, 처리, 출력, 실패 동작을 적습니다. 수용 기준은
그 요구를 받아들일 수 있는지 확인하는 시험 가능한 조건입니다. 정상 사례 하나 외에
입력 누락·취소·반복·장치 또는 네트워크 중단 중 해당하는 실패를 포함합니다.

## 실습

docs/requirements.md의 요구를 작성하고 docs/validation.md에서 T01 같은 시험번호에
연결합니다. 기대 결과는 실행 전에 적습니다. 아직 못 실행한 것은 미실행으로 두고
실제 결과를 미리 채우지 않습니다. 요구 하나가 화면·시험·작업에서 같은 뜻으로 사용되는지
확인합니다.

## 나쁜 문장 고치기

“센서를 실시간으로 잘 보여 준다”를 고칩니다. 실제 갱신 주기, 마지막 수신 시각,
새 자료가 오지 않을 때의 표시, 관찰할 실행 조건을 나눕니다. “사용자가 요청하면
조회가 시작되고 연결 실패가 문구로 나타난다”처럼 실제 동작부터 구체화합니다.

## 에이전트 검토

요구를 임의로 바꾸게 하지 말고 모호한 말·빠진 실패·서로 충돌한 조건을 찾아 설명하게
합니다. 의사결정은 학생이 하고 변경 이유를 남깁니다.

## 실제 파일과 연결해서 읽기

[전체 파일 받기](../kit/docs/requirements.md)

아래는 파일 앞부분입니다. 실행은 전체 파일로 합니다. 생략한 코드를 그대로 실행하지 마세요.

```python
# 요구사항
| 요구번호 | 사용자 행동 | 입력·조건 | 결과 | 실패 처리 | 우선순위 |
|---|---|---|---|---|---|
| R01 | [작성] | [작성] | [작성] | [작성] | 필수 |
## 품질 조건
[작성] 목표·환경·측정 방법. 확인 결과와 목표를 구분.
```

## 실습을 끝내기 전에

먼저 실행 위치와 파일 이름을 확인합니다. 코드를 바꾸기 전 출력이나 화면을 예상하고,
실행 후 실제 결과를 비교합니다. 에이전트가 수정했다면 git diff에서 이번 요구와 무관한
변경이 섞이지 않았는지 봅니다. 다음 단계가 막힐 때는 현재 작업을 보존하고 실행 가능한
기준본과 비교하되, 기준본을 실행한 결과와 내가 구현한 결과를 구분합니다.

결과 기록에는 내가 바꾼 파일, 입력과 조건, 실제 결과, 실패한 것과 다음 확인을 적습니다.
설명문을 길게 쓰는 대신 코드·실행 명령·짧은 화면 또는 출력으로 확인할 수 있게 남깁니다.
