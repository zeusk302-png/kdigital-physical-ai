# P01 · 문제와 사용자 상황을 검증하기

AI가 만든 그럴듯한 문제 설명을 실제로 확인할 질문과 근거로 바꿉니다.

## 해결할 문제부터

“YOLO를 사용한다”는 기술 선택이지 사용자 문제가 아닙니다. 누가 어느 상황에서 어떤
일을 하다가 무엇 때문에 막히는지 적습니다. 현재 어떤 방식으로 해결하고 있고 실패하면
어떤 영향이 있는지 구분합니다. 프로젝트는 학생 개인 또는 팀이 선택하며 이전 실습과
같은 주제일 필요는 없습니다.

## 사실·해석·가정

직접 관찰, 공개 문서, 인터뷰 메모처럼 확인한 것은 출처와 날짜를 적습니다. 몇 명이
겪었다는 자료를 전체 사용자가 그렇다는 결론으로 확대하지 않습니다. 아직 확인하지
못한 것은 가정으로 두고 질문을 만듭니다. 실제로 만나지 않은 사용자의 인터뷰를 AI로
생성해 근거로 적지 않습니다.

## 실습

docs/problem.md의 사용자·상황·현재 방법·불편·바라는 결과를 작성합니다. 기능 이름을
적기 전에 사용자가 실제로 할 행동을 한 문장으로 씁니다. 옆 학생이 질문 세 개를 만들고
답에 없는 조건을 찾아 봅니다. 확인이 어려운 주장은 필요 자료와 확인 방법을 붙입니다.

## 에이전트 요청

```text
docs/problem.md에서 관찰한 사실과 추정을 나눠 줘.
자료에 없는 통계나 인터뷰는 만들지 마.
이 문제가 실제인지 확인할 질문5개를 제안하고 이유를 설명해.
지금은 기능이나 기술을 확정하지 마.
```

## 완료 기준

사용자·문제 상황·기존 방법·개선 결과가 연결되고 확인된 근거와 가정이 구분돼야 합니다.
“모두를 위한 편리한 AI”처럼 대상과 상황이 없는 문장은 다시 씁니다.

## 실제 파일과 연결해서 읽기

[전체 파일 받기](../kit/docs/problem.md)

아래는 파일 앞부분입니다. 실행은 전체 파일로 합니다. 생략한 코드를 그대로 실행하지 마세요.

```python
# 문제와 사용자
## 사용자와 사용 상황
[작성] 누가 언제 어떤 일을 하는가?
## 현재 방법과 불편
[작성] 지금 해결 방법과 실패 시 영향.
## 근거와 가정
[작성] 실제 확인한 출처·날짜 / 아직 확인하지 못한 조건.
## 개선할 행동
[작성] 기술 이름이 아니라 사용자가 완료할 행동 한 문장.
```

## 실습을 끝내기 전에

먼저 실행 위치와 파일 이름을 확인합니다. 코드를 바꾸기 전 출력이나 화면을 예상하고,
실행 후 실제 결과를 비교합니다. 에이전트가 수정했다면 git diff에서 이번 요구와 무관한
변경이 섞이지 않았는지 봅니다. 다음 단계가 막힐 때는 현재 작업을 보존하고 실행 가능한
기준본과 비교하되, 기준본을 실행한 결과와 내가 구현한 결과를 구분합니다.

결과 기록에는 내가 바꾼 파일, 입력과 조건, 실제 결과, 실패한 것과 다음 확인을 적습니다.
설명문을 길게 쓰는 대신 코드·실행 명령·짧은 화면 또는 출력으로 확인할 수 있게 남깁니다.
