# P07 · AI를 조사자·설계자·검토자로 쓰기

AI의 역할을 바꾸어도 판단 근거와 실제 실행은 사람이 확인합니다.

## 역할을 나누기

조사 단계에서는 출처와 질문을, 설계 단계에서는 대안과 선택 이유를, 검토 단계에서는
빠진 조건과 충돌을 요청합니다. 같은 대화에서 전체 기획을 한 번에 쓰게 하면 앞에서
확정한 가정이 사실처럼 굳을 수 있습니다. 확정 결정과 미확인 조건을 docs에 나눠 남깁니다.

## 검토 요청

```text
docs/problem.md, requirements.md, architecture.md, validation.md를 읽어.
문제→기능→화면/데이터→시험→작업 사이에 빠진 연결을 찾아.
자료에 없는 사용자 인터뷰·통계·비용·성능은 만들지 마.
문제 위치, 왜 문제인지, 확인할 질문을 먼저 보고해.
기획 내용은 아직 수정하지 마.
```

## 첫 개발 지시

검토 후 선택한 요구 하나를 목적·현재 상태·참고 파일·수정 범위·유지 조건·완료 기준·시험으로
작성합니다. “기획서대로 모두 만들어 줘” 대신 가장 작은 성공 경로를 지정합니다. 계획을
검토하고 구현을 진행한 뒤 실제 파일과 시험 결과를 확인합니다.

## 파일 구조와 컨텍스트

AGENTS.md에는 읽을 문서와 공통 작업 원칙, README에는 실행과 자료 안내를 둡니다.
요구·구조·검증·일정은 역할별 docs로 나눕니다. 파일명만 적으면 모든 도구가 자동으로
읽는다고 가정하지 말고 실제 읽은 파일을 확인합니다. 새 대화에서는 현재 결정과 다음
작업을 함께 전달합니다.

## 직접 수행

자기 기획을 다른 에이전트 또는 다른 학생에게 검토받고 수용한 의견과 수용하지 않은
의견의 이유를 남깁니다. 검토 의견을 모두 따라야 하는 것이 아니라 근거로 선택합니다.

## 실제 파일과 연결해서 읽기

[전체 파일 받기](../kit/AGENTS.md)

아래는 파일 앞부분입니다. 실행은 전체 파일로 합니다. 생략한 코드를 그대로 실행하지 마세요.

```python
# 작업 지침
README와 현재 단계의 docs를 읽고 문서·코드와 맞춰 작업한다.
없는 인터뷰·통계·가격·성능·실행 결과를 만들지 않는다.
확인한 근거와 미확인 가정을 나눈다.
요구 변경은 화면·데이터·시험·작업에 함께 반영한다.
첫 개발 지시는 파일·범위·완료·시험으로 좁힌다.
```

## 실습을 끝내기 전에

먼저 실행 위치와 파일 이름을 확인합니다. 코드를 바꾸기 전 출력이나 화면을 예상하고,
실행 후 실제 결과를 비교합니다. 에이전트가 수정했다면 git diff에서 이번 요구와 무관한
변경이 섞이지 않았는지 봅니다. 다음 단계가 막힐 때는 현재 작업을 보존하고 실행 가능한
기준본과 비교하되, 기준본을 실행한 결과와 내가 구현한 결과를 구분합니다.

결과 기록에는 내가 바꾼 파일, 입력과 조건, 실제 결과, 실패한 것과 다음 확인을 적습니다.
설명문을 길게 쓰는 대신 코드·실행 명령·짧은 화면 또는 출력으로 확인할 수 있게 남깁니다.
