# P11 Notion·GitHub·AI 작업 지시로 개발 넘기기


기획서는 개발자가 첫 작업을 시작할 수 있어야 합니다. Notion에는 논의·결정·진행 상태, GitHub에는 코드·설계·시험·변경 이력을 남깁니다. 문서만 두 군데 복제하고 서로 다른 버전이 되지 않도록 최신 원본의 링크를 지정합니다.

## 작업을 나누기

기능 하나를 요구번호 R01, 확인할 시험 T01, 구현 작업 W01로 연결합니다. ‘프런트 전부’보다 ‘수신 중단 상태를 마지막 값과 함께 표시’처럼 검토 가능한 단위로 자릅니다. 담당자·수정 파일·선행 작업·완료 조건·검토자를 적고, 기간은 실제 남은 일정과 준비 작업을 근거로 정합니다.

## 첫 개발 요청

```text
AGENTS.md와 docs/requirements.md, architecture.md, validation.md를 읽어.
이번에는 R01만 구현해. 수정 범위는 frontend의 연결 상태 표시야.
API 계약과 센서 펌웨어는 바꾸지 마.
먼저 현재 구조·수정 계획·확인할 파일을 설명해.
빈 기록·수신 중단·서버 중단·복구 시험을 함께 제안해.
없는 자료·실행 결과를 만들지 말고 실제 확인과 미실행을 나눠 보고해.
```

## 리뷰 방식

다른 팀은 문제→기능→입력→화면→구조→시험→작업이 연결되는지 질문합니다. 준비 안 된 장비·요금제·외부 서비스·권한이 필수 경로에 숨어 있지 않은지 봅니다. 문서 점검 도구는 빠진 파일과 참조를 찾을 뿐 사업성이나 사실성을 판정하지 않습니다.

## 팀 제출과 개인 설명

팀 기획과 기술 검증을 제출하되 각자는 본인이 정한 요구·시험·작업 하나를 설명합니다. 발표는 문제 1분, 실제 검증 2분, 설계·다음 작업 2분 정도로 구성하고 팀 수에 맞춰 발표 시간을 운영합니다. 모두 발표할 시간이 부족하면 두 팀씩 교차 리뷰 후 대표 사례를 공유합니다. 다음 개발자가 README와 첫 작업 지시만으로 실행·검토할 수 있는지 확인합니다.
