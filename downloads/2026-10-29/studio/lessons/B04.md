# B04 · React 요청·상태·필터

화면에 같은 수치를 붙여 넣는 대신 응답과 상태를 연결합니다.

## 프런트와 서버의 주소

이 프로젝트는 FastAPI가 web 폴더를 같은 주소에서 제공합니다. 따라서 /api/events처럼
상대 주소로 요청합니다. frontend/src가 원본이고 web/app.js는 생성된 결과입니다.
JSX를 바꿨는데 화면이 같다면 npm run dev의 감시 상태·파일 저장·새로고침을 확인합니다.
package-lock.json과 npm ci로 설치 버전을 맞춥니다.

## 화면이 기억할 것

minutes와 device는 조회 조건이고 data는 마지막 성공 응답입니다. error와 loading은
서로 다른 화면 상태입니다. 응답이200이어도 아직 기록이 없으면 빈 결과입니다. 서버가
끊기면 마지막 자료를 유지하되 연결 실패라고 표시합니다. 에러가 났다고0으로 채우면
실제 값0과 구분할 수 없습니다.

## 주기적 요청

setInterval로 무조건 요청을 쌓기보다 앞 요청이 끝난 뒤 다음 요청을 예약합니다.
필터가 바뀌거나 컴포넌트가 끝나면 타이머와 요청을 정리합니다. 제공 코드는 AbortController와
정리 함수를 사용합니다. 이 줄을 지웠을 때 오래된 요청이 화면을 덮을 수 있는지 설명해
보세요. 자동 새로고침과 실시간 스트리밍은 같은 방식이 아닙니다.

## 직접 구현

주의 사건만 보기 토글을 추가합니다. 표만 거르고 지표는 전체를 계산하는 오류를 피하세요.
필터된 rows를 하나의 기준으로 쓰고 지표·차트·표가 그 범위를 사용하는지 확인합니다.
버튼만 노랗게 변하는 것은 필터가 동작한 것이 아닙니다.

## 오류 해결

개발자 도구 Network에서 주소·상태·응답 본문을 확인하고 Console 오류 위치를 엽니다.
CSS 문제와 데이터 요청 실패를 한꺼번에 에이전트에게 맡기지 말고 재현 조건과 파일을
정해 하나씩 수정합니다.

[Fetch 응답과 오류](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch)

## 실제 파일과 연결해서 읽기

[전체 파일 받기](../kit/frontend/src/api.js)

아래는 파일 앞부분입니다. 실행은 전체 파일로 합니다. 생략한 코드를 그대로 실행하지 마세요.

```javascript
// HTTP 오류 응답도 fetch 자체는 성공할 수 있으므로 response.ok를 따로 검사합니다.
export async function readEvents(minutes,device,signal){
  const query=new URLSearchParams({minutes:String(minutes),device});
  const response=await fetch('/api/events?'+query,{signal,cache:'no-store'});
  if(!response.ok)throw Error('조회 실패: HTTP '+response.status);
  return response.json();
}
```

## 실습을 끝내기 전에

먼저 실행 위치와 파일 이름을 확인합니다. 코드를 바꾸기 전 출력이나 화면을 예상하고,
실행 후 실제 결과를 비교합니다. 에이전트가 수정했다면 git diff에서 이번 요구와 무관한
변경이 섞이지 않았는지 봅니다. 다음 단계가 막힐 때는 현재 작업을 보존하고 실행 가능한
기준본과 비교하되, 기준본을 실행한 결과와 내가 구현한 결과를 구분합니다.

결과 기록에는 내가 바꾼 파일, 입력과 조건, 실제 결과, 실패한 것과 다음 확인을 적습니다.
설명문을 길게 쓰는 대신 코드·실행 명령·짧은 화면 또는 출력으로 확인할 수 있게 남깁니다.
