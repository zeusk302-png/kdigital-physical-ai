# B08 · AI 작업 지시·파일 구조·Git 인수인계

하루 동안 만든 결과를 다른 사람이 다시 실행할 수 있도록 정리합니다.

## 파일을 나누는 기준

frontend/src/api.js는 요청, main.jsx는 표시·상태, backend/app/models.py는 입력 계약,
store.py는 DB, main.py는 경로 연결, adapters는 외부 원천의 변환입니다. 파일을 많이
만드는 것이 아니라 바뀌는 이유가 다른 부분을 나누는 것입니다. 실제 리팩터링에서는
먼저 통과하던 시험을 남기고 한 책임씩 옮깁니다.

## 에이전트 요청 예

```text
README.md, docs/api.md, frontend/src/api.js와 main.jsx를 읽어.
서버가 멈춘 뒤에도 정상처럼 보이는 문제를 재현해.
API 계약과 DB 구조는 유지하고 화면 상태 처리만 고쳐.
중단·복구·빈 이력·새 수신 중단을 각각 시험해.
수정 파일, 실제 실행 결과, 확인하지 못한 장치 연결을 나눠 보고해.
```

## Git에 남기기

코드·requirements·package-lock·DB 테이블 생성 코드·설정 예·설계·시험·실행 안내를
올립니다. 실제 DB·수집 로그·가상환경·node_modules·비밀값은 제외합니다. 이미 추적한
파일은 .gitignore만 적어도 과거 기록에서 사라지지 않으므로 커밋 전 상태를 확인합니다.
운영 비밀을 시험 자료에 복사하지 않습니다.

## 직접 수행

git status → git diff로 확인한 뒤 이번 기능의 파일만 git add합니다. git diff --cached를
읽고 한 기능을 설명하는 커밋을 만듭니다. README만 보고 다른 사람이 서버와 화면을
열 수 있는지 확인하고 빠진 명령·폴더·주소를 보완합니다.

## 마지막 변경 요구

자기 사용자에게 필요한 지표나 필터 하나를 추가하고 기존 수신·저장·복구가 유지되는지
시험합니다. 에이전트가 만든 변경 중 어떤 부분을 직접 확인했는지 설명하세요.

## 실제 파일과 연결해서 읽기

[전체 파일 받기](../kit/AGENTS.md)

아래는 파일 앞부분입니다. 실행은 전체 파일로 합니다. 생략한 코드를 그대로 실행하지 마세요.

```python
# 작업 지침
README.md와 docs/api.md, docs/challenges.md를 먼저 읽는다.
요청한 기능만 수정하고 API 필드·기존 자료의 의미를 유지한다.
DB SQL은 파라미터를 사용한다. 비밀값·운영 DB는 커밋하지 않는다.
시험과 실제 장치 연결은 구분해 보고한다.
```

## 실습을 끝내기 전에

먼저 실행 위치와 파일 이름을 확인합니다. 코드를 바꾸기 전 출력이나 화면을 예상하고,
실행 후 실제 결과를 비교합니다. 에이전트가 수정했다면 git diff에서 이번 요구와 무관한
변경이 섞이지 않았는지 봅니다. 다음 단계가 막힐 때는 현재 작업을 보존하고 실행 가능한
기준본과 비교하되, 기준본을 실행한 결과와 내가 구현한 결과를 구분합니다.

결과 기록에는 내가 바꾼 파일, 입력과 조건, 실제 결과, 실패한 것과 다음 확인을 적습니다.
설명문을 길게 쓰는 대신 코드·실행 명령·짧은 화면 또는 출력으로 확인할 수 있게 남깁니다.
