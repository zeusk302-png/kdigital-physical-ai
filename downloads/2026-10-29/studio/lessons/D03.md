# 국제표준을 내 대시보드의 판단 기준으로 적용하기

## 목적과 읽는 순서

학생이 설명할 것은 ‘ISO 번호를 알고 있다’가 아니라 **사용자에게 필요한 이유 → 나쁜 화면의 문제 → 개선 방법 → 실제 확인 결과**입니다. 35분 동안 다섯 기준의 역할을 구별하고 자신의 스케치에 적용할 규칙을 만듭니다. [표준 적용 실습실](../kit/uno-dashboard/standards-lab.html)과 [적용표 MD](../kit/uno-dashboard/STANDARDS-CHECKLIST.md)를 함께 엽니다.

ISO 9241은 사람과 시스템의 상호작용을 다루는 표준군입니다. 모든 화면의 위치·색·글자 크기를 하나로 정한 ‘대시보드 ISO 양식’처럼 쓰지 않습니다. WCAG는 W3C의 웹 접근성 기준으로 ISO와 발행 기관·적용 범위가 다릅니다. 아래 ISO 설명은 공식 공개 설명을 바탕으로 범위를 정리한 것이며, 화면 규칙·과제·시간 목표는 이 교재의 **수업용 적용 예**입니다. 유료 본문 전체의 조항별 적합성 심사나 제품 인증을 수행한 것은 아닙니다.

## 0~4분 · 다섯 기준이 맡는 일

| 기준 | 무엇을 다루나 | 오늘 남길 결과 |
| --- | --- | --- |
| [ISO 9241-11:2018](https://www.iso.org/standard/63500.html) | 사용성과 사용 맥락 | 사용자·상황·과업·완료 조건 |
| [ISO 9241-210:2019](https://www.iso.org/standard/77520.html) | 사람 중심 설계 원칙·활동 | 요구→스케치→확인→수정 기록 |
| [ISO 9241-110:2020](https://www.iso.org/standard/75258.html) | 사람과 시스템의 상호작용 원칙 | 예측·상태·제어·복구 문구 |
| [ISO 9241-112:2025](https://www.iso.org/standard/87518.html) | 제시된 정보의 지각·이해 | 값·이름·단위·시간·출처 구별 |
| [WCAG 2.2](https://www.w3.org/TR/WCAG22/) | 웹 콘텐츠 접근성 성공 기준 | 색·대비·키보드·초점 확인 근거 |

‘실제 화면이 예쁘다’는 관찰과 ‘표준 전체에 적합하다’는 판정은 다릅니다. 20개 사례는 앞의 관찰을 연습하는 자료입니다. 관련 기준을 붙인 것은 읽는 관점이며, 제공자의 적합성·부적합성을 판정한 것이 아닙니다.

## 4~9분 · S11 사용성: 누구의 일을 돕는가

사용성은 특정 사용자·목표·사용 맥락과 함께 생각합니다. 단순히 ‘쉬운 화면’이라는 취향 판단에서 벗어나 어떤 일이 제대로 완료되는지, 얼마나 노력해야 하는지, 사용자가 어떻게 느끼는지 나누어 봅니다. 효과성·효율성·만족도라는 개념은 이 세 관점을 구별하는 데 쓰입니다. 여기서 제안하는 시간·성공 조건은 교재의 예이며 ISO가 정한 합격 시간이 아닙니다.

**나쁜 출발:** ‘누구나 쓰는 스마트 대시보드. 센서 카드20개를 놓는다.’ 사용자와 해야 할 일이 없어서 어떤 정보가 우선인지 결정하기 어렵습니다.

**개선 출발:** ‘집에서 공부하는 내가 책상이 어두운지 확인하고 LED로 조명 제어를 표현한다.’ 첫 정보는 밝기·연결 상태, 행동은 LED 제어, 완료 근거는 값의 출처와 명령 응답·실제 점등의 구별입니다.

| 볼 관점 | 교재의 P01 확인 예 | 구별할 것 |
| --- | --- | --- |
| 원하는 일을 제대로 했나 | 현재 밝기와 오래된 값을 구별하고 올바른 제어를 선택했나 | 클릭했다는 사실과 과업 완료 |
| 불필요한 노력이 많나 | 핵심 정보와 제어를 찾느라 여러 화면을 오가지 않나 | 작업 시간·탐색 과정과 보드 통신 속도 |
| 사용자는 어떻게 느끼나 | 직접 사용 후 헷갈린 이름·불편한 조작을 자기 말로 적었나 | 작성자의 추측과 실제 사용 후 의견 |

**개인 수행:** ‘사용자 / 환경 / 해야 할 일 / 완료라고 볼 근거’를 각 한 줄 적습니다. `10초 안에 최신값 찾기` 같은 목표를 쓰면 교재의 시험 목표라고 표시하고, 실제 잰 시간과 구별합니다. 장치·사용자 확인을 못 했으면 아직 미확인으로 둡니다.

## 9~14분 · S210 사람 중심 설계: 무엇을 먼저 정하는가

ISO 9241-210은 시스템을 설계하는 과정에서 사람과 사용 맥락을 고려하는 원칙·활동을 다룹니다. 오늘은 그 범위를 **상황 이해 → 요구 정의 → 설계안 → 확인과 수정**이라는 수업 활동으로 연결합니다. 이 네 칸이 표준의 전체 절차나 인증 체크리스트를 대신하지는 않습니다.

**나쁜 과정:** AI에게 ‘예쁘게’ 요청 → 랜덤 숫자가 있는 화면을 받아 제출. **개선 과정:** 사용할 상황을 먼저 적고, 필요한 입력·출력·실패 상태를 정한 뒤, 두 스케치를 비교하고 한 번 수정합니다.

| 단계 | 학생이 쓸 한 문장 | 확인 질문 |
| --- | --- | --- |
| 상황 이해 | 집에서 USB 키트로 작업하며 값의 출처를 확인한다 | 같은 화면을 공장 관제용이라고 해도 될까? |
| 요구 정의 | 밝기·LED·USB 상태가 먼저 보여야 한다 | 어떤 입력과 출력이 실제로 있는가? |
| 설계안 | 상단 연결, 중앙 밝기, 아래 제어·이력 | 스케치와 요구가 연결되는가? |
| 확인·수정 | 중단 표시가 묻혀 상단으로 옮겼다 | 무엇을 관찰해서 왜 바꿨는가? |

**개인 수행:** 자신의 스케치에서 한 구역을 바꾸고 ‘바꾸기 전 / 관찰한 문제 / 바꾼 뒤 / 다시 확인’을 적습니다. Zoom 개인 수업이므로 자기 점검과 강사 피드백을 사용합니다. 실제 사용자 조사를 하지 않았다면 했다고 기록하지 않습니다.

## 14~20분 · S110 상호작용: 예상·응답·복구

ISO 9241-110의 범위는 사람과 시스템의 상호작용입니다. P01에서는 버튼의 이름으로 결과를 예상할 수 있는지, 요청 뒤 상태를 이해하는지, 오류 후 다음 행동이 있는지 살핍니다. 아래 명령 설계는 교재의 구체적 적용입니다.

| 나쁜 화면 | 개선 화면 | 직접 확인 |
| --- | --- | --- |
| 버튼이 ‘실행’뿐 | ‘LED 켜기’, ‘자동 해제·LED 끄기’ | 누르기 전에 예상 결과를 말한다 |
| 누르자마자 ‘성공’ | 전송 중→해당 요청 응답→보드 보고 상태 | 요청번호와 실제 LED를 따로 본다 |
| 응답 없는데 ‘실패’로 단정 | ‘적용 여부 미확인’과 연결 점검 안내 | 응답 유실과 실제 출력을 구별한다 |
| 기준500·400을 보내 버림 | 잘못된 순서를 안내하고 전송 거절 | `켜짐 < 꺼짐`으로 고쳐 다시 수행한다 |

[실습실](../kit/uno-dashboard/standards-lab.html)의 명령 상황을 ‘대기 / 적용 응답 / 시간 초과 / 명령 거절’로 바꿉니다. 화면 문구만 시연하는 연습이며 USB 명령을 전송하지 않습니다. 각 상황에서 사용자가 할 다음 행동을 적습니다. 특히 실제 P01은 USB 연결 해제가 STOP 명령이 아니므로 두 동작을 같은 뜻으로 표시하지 않습니다.

## 20~26분 · S112 정보 제시: 값이 무엇을 뜻하는가

ISO 9241-112는 인터페이스가 제시하는 정보를 지각하고 이해하는 원칙을 다룹니다. 2025판을 기준으로 범위를 안내하며 2017판을 최신이라고 쓰지 않습니다. 오늘의 화면 점검은 이름·단위·시각·출처·관계를 구별하는 수업용 적용입니다.

| 같은 자료를 잘못 표시 | 의미를 보존한 표시 | 이유 |
| --- | --- | --- |
| 밝기320 lux | CdS 원시값320/1023 | 교정된 조도 단위가 아니다 |
| 센서 실패를 온도0으로 표시 | 온도 — / 값 없음 | 측정된0과 값을 못 얻음은 다르다 |
| USB 중단 후320을 큰 현재값으로 유지 | 현재값 —, 마지막 정상 시각과 과거 그래프 유지 | 과거값을 현재로 오해하지 않게 한다 |
| 모든 숫자 하나로 평균 | 온도·습도·밝기를 별도 표시 | 단위와 의미가 다른 값을 섞지 않는다 |

**개인 수행:** 실습실에서 정상·온습도 실패·전체 수신 중단을 바꿉니다. 어느 항목은 남고 어느 항목은 숨기는지 예상한 뒤 비교합니다. 카드 이름·단위·시각을 자기 스케치에 붙입니다. 현재값과 그래프가 서로 다른 기간을 뜻한다면 각각 범위를 적습니다.

## 26~35분 · W22 웹 접근성: 직접 검사할 조건

WCAG의 성공 기준과 W3C의 Understanding 해설은 역할이 다릅니다. 성공 기준은 WCAG 본문에서, 이해를 돕는 설명·예시는 공식 해설에서 확인합니다. 수업은 다음 일부 항목을 적용하며 사이트 전체의 WCAG 적합성을 판정하지 않습니다.

### 색만으로 상태를 말하지 않기 · 1.4.1

빨강·초록만 상태 의미를 담당하면 색을 구별하기 어려운 사람에게 정보가 사라질 수 있습니다. 빨간 점과 함께 ‘USB 중단’, 초록 점과 함께 ‘정상 수신’을 씁니다. [공식 기준](https://www.w3.org/TR/WCAG22/#use-of-color) · [공식 해설](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html).

**확인:** 색을 가리고도 글자·모양으로 같은 상태를 구별할 수 있는지 읽어 봅니다. 특정 제품 사진의 색만 보고 적합·부적합을 단정하지 않습니다.

### 글자와 배경의 대비 · 1.4.3, AA

일반 텍스트는 최소4.5:1, 큰 텍스트는 최소3:1의 대비 조건이 있으며 로고·비활성 요소·순수 장식 등 예외가 있습니다. 큰 텍스트는 단순히 ‘커 보인다’가 아니라 대략18pt 이상 또는 굵은14pt 이상이라는 정의를 확인합니다. [공식 기준](https://www.w3.org/TR/WCAG22/#contrast-minimum) · [공식 해설](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).

**확인:** 실습실에서 흰 바탕과 회색 `#777777`을 고릅니다. 일반 본문 대비는 약4.48:1로4.5에 못 미칩니다. 숫자를 반올림해 합격 처리하지 않습니다. 검정/흰색은21:1, 같은 색끼리는1:1로 계산되는지도 비교합니다. 이 도구는 불투명한 두 색의 대비만 계산하며 사진·투명도·글자 크기·전체 사이트 적합성을 자동 판정하지 않습니다.

### 키보드 조작과 초점 · 2.1.1, 2.4.7

마우스 없이 기능을 조작할 수 있는지, 지금 키보드가 어느 요소를 선택했는지 보이는지 확인합니다. [키보드 공식 해설](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html) · [초점 공식 해설](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html).

**확인:** Tab·Shift+Tab으로 이동해 버튼·입력을 찾고 Enter 또는 Space 등 해당 조작으로 실행합니다. 핵심 기능에 도달했는지, 초점 테두리가 보이는지, 창을 닫고 돌아갈 수 있는지 적습니다. 자유 손그림처럼 경로에 의존하는 입력의 예외를 모든 기능에 넓혀 적용하지 않습니다.

### 눌리는 영역과 간격 · 2.5.8, AA · 추가 읽기

기본 크기24×24 CSS px와 간격·동등 기능·문장 안 링크·브라우저 제어·필수 표현의 예외를 함께 읽습니다. ‘모든 버튼은 무조건44px가 WCAG AA 규칙’이라고 설명하지 않습니다. 교재가 편한 조작을 위해 더 큰 버튼을 권할 수는 있지만 규범과 권고를 구별해야 합니다. [공식 해설과 예외](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html).
