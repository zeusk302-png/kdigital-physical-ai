# 2026-10-29 · 웹 대시보드

센서 기록을 현황판에 표시하고 최신값과 이력을 읽습니다. 값이 없거나 통신이 끊겼을 때의 화면도 확인합니다.

기본 화면은 고정 fixture와 고정 확인시각을 사용하는 모의 경로입니다. 로컬 API는 별도 실행하며 메모리에만 저장합니다. 실물ESP32·센서·외부망·인증·지속저장·공개배포는 검증 범위가 아닙니다.

전체 코드와 모든 줄의 뜻·실행 방법은 [코드 해설](examples/course/code/line-guide.md)에 있습니다. 작성 소스와 생성된 번들·잠금 파일을 구분합니다.

## 1구간 · 업무 질문과 표시 규칙



### A01 · 현황판이 답할 업무 질문

**뜻과 비유.** 대시보드는 여러 기록을 모아 현재 상황과 변화를 확인하는 업무 화면입니다. 먼저 누가 어떤 결정을 위해 보는지 정합니다.

**왜 필요한가.** 많은 숫자를 한 화면에 놓아도 사용자의 질문에 답하지 못하면 확인 부담만 커집니다.

**예를 따라 읽기.** 점검 담당자는 장소별 마지막 온도와 그 값이 언제 들어왔는지, 미측정인지 알고 싶어합니다.

**헷갈리는 반례.** 큰 숫자 22.8만 보여 주면 단위와 장소, 기록 시각을 알 수 없습니다.

**직접 적용.** 화면을 열어 보이는 항목 찾기 → 사용자와 확인할 질문 세 개 쓰기 → 질문에 필요한 필드 연결하기 → 필요 없는 장식과 정보 구별하기

**설명할 질문.** 보기 좋은 화면과 업무에 필요한 화면은 어떻게 다를까요?

**막혔을 때.** 화면을 열 수 없으면 제공 index.html 원문과 초기 시나리오를 먼저 대조합니다.

입력·답칸·확인 순서는 [실습지의 A01](practice-guide.md#a01)와 [활동 원문](examples/course/data/A01_input.md)에 있습니다.

### A02 · 관찰 단위와 최신 기록

**뜻과 비유.** 한 행은 센서의 한 시점 관찰입니다. 최신 기록은 배열의 마지막 줄이라는 뜻이 아니라 측정 시각을 비교해 정한 기록입니다.

**왜 필요한가.** 같은 센서가 여러 번 나오거나 늦게 도착한 기록이 있으면 입력 순서만 믿어서는 현재 상태를 잘못 보여 줄 수 있습니다.

**예를 따라 읽기.** 입구 S01은 22.5와 22.8의 두 기록이 있으며 10:10의 22.8이 마지막 기록입니다.

**헷갈리는 반례.** 다른 센서의 마지막 행을 전체 공간의 최신값이라고 부르면 장치별 상태가 사라집니다.

**직접 적용.** readings.json의 다섯 건 읽기 → 장치 수와 관찰 수 따로 세기 → S01 두 시각 비교하기 → 최신 선택 기준을 한 문장으로 쓰기

**설명할 질문.** 파일의 마지막 줄과 센서별 최신값은 왜 다를 수 있나요?

**막혔을 때.** 시각 문자열의 표기와 시간대를 확인합니다. 이 예제는 +09:00을 명시합니다.

입력·답칸·확인 순서는 [실습지의 A02](practice-guide.md#a02)와 [활동 원문](examples/course/data/A02_input.md)에 있습니다.

### A03 · 단위·시각·상태의 약속

**뜻과 비유.** 표시 규칙은 값의 뜻과 화면 문구를 연결한 약속입니다. 단위와 누락, 오래된 값의 기준을 먼저 정합니다.

**왜 필요한가.** 상태가 무엇을 뜻하는지 합의하지 않으면 같은 값에 서로 다른 판단을 붙일 수 있습니다.

**예를 따라 읽기.** 이 수업은 28 ℃ 이상 주의, 60초 초과 오래됨, 온도 null은 미측정이라고 표시합니다. 입력에는 시간대가 있는 ISO 시각을 쓰고 화면은 한국 시각으로 통일해 표시합니다.

**헷갈리는 반례.** 이 숫자는 실제 장비의 안전 한계가 아니라 합성 데이터의 표시 연습 규칙입니다.

**직접 적용.** rules.md의 기준 읽기 → 28과 60초 경계의 예상 쓰기 → 0·null·false의 표시 구별하기 → 상태 우선순위를 표로 옮기기

**설명할 질문.** 여러 상태가 동시에 맞을 때 어떤 문구를 보여 줄까요?

**막혔을 때.** 정지이면서 오래된 값의 문구가 궁금하면 우선순위를 확인합니다. 현재는 정지가 먼저입니다.

입력·답칸·확인 순서는 [실습지의 A03](practice-guide.md#a03)와 [활동 원문](examples/course/data/A03_input.md)에 있습니다.

## 2구간 · 데이터의 이동 경로



### A04 · 정적 파일로 여는 모의 화면

**뜻과 비유.** 정적 화면은 제공된 파일을 읽어 브라우저 안에서 표시합니다. 서버에서 실시간 데이터를 받는 기능과 별개로 미리 준비한 자료를 사용할 수 있습니다.

**왜 필요한가.** GitHub Pages나 오프라인 파일만으로도 화면 구조와 필터를 배울 수 있게 합니다.

**예를 따라 읽기.** code/index.html은 fixture.js의 가상 기록을 읽어 처음 화면을 표시합니다. 인터넷과 실제 센서는 필요 없습니다.

**헷갈리는 반례.** 화면이 움직여도 실제 네트워크나 하드웨어 측정이 연결되었다고 말하지 않습니다.

**직접 적용.** code/index.html 열기 → 고정 가상 자료 안내문 읽기 → 초기 표의 네 상태 확인하기 → 정적 파일 경로를 실행 노트에 쓰기

**설명할 질문.** 브라우저에서 화면이 갱신되면 항상 서버가 있는 건가요?

**막혔을 때.** 브라우저가 파일 열기를 막으면 강사의 로컬 정적 서버 경로를 사용합니다. 외부 계정은 만들지 않습니다.

입력·답칸·확인 순서는 [실습지의 A04](practice-guide.md#a04)와 [활동 원문](examples/course/data/A04_input.md)에 있습니다.

### A05 · 서버와 API의 요청·응답

**뜻과 비유.** 서버는 요청을 받아 결과를 보내는 프로그램입니다. API는 프로그램들이 어떤 주소와 자료형식으로 요청할지 정한 창구입니다.

**왜 필요한가.** 보낸 값과 수신한 값, 보여 준 값을 각각 확인하려면 어느 프로그램이 어느 역할을 하는지 구분해야 합니다.

**예를 따라 읽기.** GET /api/readings는 기록 목록을 읽고 POST /api/readings는 검사한 새 관찰을 추가합니다.

**헷갈리는 반례.** GET과 POST라는 이름을 외우는 것만으로 입력 계약이나 성공 여부가 확인되지는 않습니다.

**직접 적용.** 서버·송신자·브라우저 역할 쓰기 → GET과 POST의 목적 구분하기 → 응답 상태 200·201·400 비교하기 → 한 값의 이동 경로 설명하기

**설명할 질문.** 수신 성공과 화면 표시 성공은 왜 별도 확인인가요?

**막혔을 때.** 주소가 같아도 메서드가 다르면 역할이 다릅니다. 실습은 로컬 127.0.0.1에서만 엽니다.

입력·답칸·확인 순서는 [실습지의 A05](practice-guide.md#a05)와 [활동 원문](examples/course/data/A05_input.md)에 있습니다.

### A06 · 로컬 서버 실행과 종료

**뜻과 비유.** 로컬 실행은 자기 PC의 프로그램이 정해진 포트에서 요청을 기다리는 상태입니다. 주소·포트·실행 중인 창을 함께 기록합니다.

**왜 필요한가.** 서버를 껐는데 화면만 남아 있으면 마지막 값을 새로운 수신값으로 오해할 수 있습니다.

**예를 따라 읽기.** python code/server.py를 실행한 뒤 http://127.0.0.1:8780/?source=api를 열고 Ctrl+C로 종료합니다.

**헷갈리는 반례.** 파일을 더블 클릭해 열었다고 API 서버까지 실행된 것은 아닙니다.

**직접 적용.** 실행 폴더와 명령 확인하기 → 서버 주소를 브라우저로 열기 → API 읽기 성공 문구 확인하기 → 종료 방법과 다시 시작 순서 기록하기

**설명할 질문.** 서버를 종료한 뒤 기존 화면 값은 무엇을 뜻하나요?

**막혔을 때.** 8780 포트 사용 중이면 다른 수업 서버를 확인하고 강사 도움으로 정리합니다. 무관한 프로세스를 종료하지 않습니다.

입력·답칸·확인 순서는 [실습지의 A06](practice-guide.md#a06)와 [활동 원문](examples/course/data/A06_input.md)에 있습니다.

## 3구간 · 모의 입력과 값 추적



### A07 · 입력 필드와 수신 계약

**뜻과 비유.** 수신 계약은 필수 항목·종류·단위·시각을 검사한 뒤 기록을 받아들이는 규칙입니다. 통신에 성공한 글자가 곧 유효한 측정값은 아닙니다.

**왜 필요한가.** 잘못된 문자열이나 범위 밖 숫자가 들어와도 그대로 평균과 상태 계산에 섞지 않도록합니다.

**예를 따라 읽기.** new_reading.json은 S01·입구·24.2·10:10+09:00·true의 다섯 항목입니다.

**헷갈리는 반례.** 온도"24.2"는 문자열이고 24.2는 숫자입니다. 표면 모양이 비슷해도 수신 계약에서는 다릅니다.

**직접 적용.** 입력 JSON의 다섯 키 찾기 → 종류와 시각 시간대 표시하기 → 예상 응답 201 과 건수 증가 쓰기 → 보낼 값과 표시할 값을 기록하기

**설명할 질문.** API가 받은 글자를 왜 다시 검사하나요?

**막혔을 때.** JSON 기호 오류와 업무 규칙 오류를 구분합니다. 큰따옴표가 읽혀도 숫자 형식이 틀릴 수 있습니다.

입력·답칸·확인 순서는 [실습지의 A07](practice-guide.md#a07)와 [활동 원문](examples/course/data/A07_input.md)에 있습니다.

### A08 · 한 값을 보내고 끝까지 찾기

**뜻과 비유.** 추적은 같은 입력값이 송신·수신·화면의 어느 위치에 나타났는지 차례로 확인하는 것입니다.

**왜 필요한가.** 성공 문구 하나만 보고 값이 맞다고 판단하지 않고 경로 전체의 의미 보존을 확인합니다.

**예를 따라 읽기.** 서버를 실행한 뒤 send_sample.py를 실행하면 201과 count6이 출력됩니다. API 다시 읽기 뒤 S01 최신값은 24.2입니다.

**헷갈리는 반례.** 모의 기록 추가 버튼은 화면 메모리에만 추가하므로 서버 저장 확인의 대체가 아닙니다.

**직접 적용.** 서버 실행 확인하기 → 송신 명령으로 24.2 보내기 → 응답 상태와 count 기록하기 → 브라우저 API 다시 읽기로 같은 값 찾기

**설명할 질문.** 화면 버튼과 송신 프로그램은 저장 위치가 어떻게 다른가요?

**막혔을 때.** 같은 시각 기록이 추가되면 이 예제는 뒤에 받은 기록을 선택합니다. 중복 정책을 실 서비스 기준으로 일반화하지 않습니다.

입력·답칸·확인 순서는 [실습지의 A08](practice-guide.md#a08)와 [활동 원문](examples/course/data/A08_input.md)에 있습니다.

### A09 · 입력값 수정과 원본 보존

**뜻과 비유.** 작업 복사본에서 한 값을 바꾸면 다른 조건을 유지하며 변화의 원인을 확인할 수 있습니다.

**왜 필요한가.** 여러 필드와 기준을 동시에 바꾸면 어떤 변경이 어떤 결과를 만들었는지 설명하기 어렵습니다.

**예를 따라 읽기.** work/fixture.js의 첫 22.5 만 25.0으로 바꾸면 입구 이력 평균은 23.90이며 최신 22.8은 유지됩니다.

**헷갈리는 반례.** 과거 값을 고쳤다고 항상 최신값도 바뀌는 것은 아닙니다.

**직접 적용.** 작업 fixture에서 첫 온도 찾기 → 25.0으로 한 곳만 수정하기 → 작업 index.html 열어 입구 필터 선택하기 → 평균과 최신값의 다른 변화 기록하기

**설명할 질문.** 이력 평균만 바뀌고 최신값이 같은 이유는 무엇인가요?

**막혔을 때.** 다른 폴더의 HTML 을 열었으면 수정이 안 보입니다. 작업본의 세 파일 상대 위치를 유지합니다.

## 4구간 · 필터와 이력 해석



### A10 · 필터와 선택한 범위

**뜻과 비유.** 필터는 조건에 맞는 기록만 보여 주는 선택입니다. 원본을 삭제하는 것이 아니라 현재 화면에서 보는 범위를 바꿉니다.

**왜 필요한가.** 필터가 적용된 평균과 전체 평균을 혼동하면 다른 장소의 상태를 잘못 설명할 수 있습니다.

**예를 따라 읽기.** 입구 필터는 두 이력과 한 센서를 보여 주며 원본 전체는 다섯 기록입니다.

**헷갈리는 반례.** 필터를 선택해 행이 줄었다고 원본 데이터가 삭제된 것은 아닙니다.

**직접 적용.** 전체와 입구의 건수 예상하기 → 장소 필터 두 번 바꾸기 → 이력·최신·평균이 함께 바뀌는지 보기 → 원본 보존 여부 설명하기

**설명할 질문.** 필터된 평균을 전체 평균이라고 부르면 어떤 문제가 있나요?

**막혔을 때.** 화면 일부만 필터되면 서로 다른 범위의 값이 섞입니다. 제목과 선택 장소를 함께 읽습니다.

입력·답칸·확인 순서는 [실습지의 A10](practice-guide.md#a10)와 [활동 원문](examples/course/data/A10_input.md)에 있습니다.

### A11 · 평균과 미측정의 처리

**뜻과 비유.** 평균은 더한 값과 나눈 개수가 무엇인지 함께 설명해야하는 요약 값입니다. 오늘은 선택 이력의 유효한 숫자만 계산합니다.

**왜 필요한가.** null을 0으로 바꾸면 측정되지 않은 값이 실제 0으로 계산에 섞여 평균이 낮아집니다.

**예를 따라 읽기.** 전체 유효 온도 22.5·29.0·0·22.8의 평균은 18.575이며 소수 둘째 자리 표시는 18.58입니다.

**헷갈리는 반례.** 정지된 센서의 0도 유효 측정 이력에는 포함합니다. 운영 목적에 따른 다른 평균을 원하면 별도 규칙이 필요합니다.

**직접 적용.** 숫자인 온도와 null 나누기 → 합계와 나눌 개수 직접 쓰기 → 표시 값과 계산 정의 비교하기 → 창고만 고르면 계산 안 함인지 확인하기

**설명할 질문.** 0을 포함하고 null을 제외하는 이유는 무엇인가요?

**막혔을 때.** 반올림 표시와 원 계산 값이 달라 보이면 소수 둘째 자리 표시 규칙을 확인합니다.

입력·답칸·확인 순서는 [실습지의 A11](practice-guide.md#a11)와 [활동 원문](examples/course/data/A11_input.md)에 있습니다.

### 평균에 포함하는 기록의 범위

현재 선택된 이력 중 센서·장소·시각·온도의 기본 형식이 맞고, 기준 시각보다 미래가 아닌 숫자 기록을 유효 집계에 포함합니다. 미측정 null, 잘못된 자료형, 미래 시각은 평균에서 제외합니다. 기본 형식을 만족하는 과거 기록·정지 센서의 기록·실제 수치 0은 이력 평균에 포함합니다. 이력 평균과 현재 연결 상태·최신값은 의미가 다릅니다. 다른 운영 목적의 평균은 별도 규칙을 정해야 합니다.

### A12 · 이력 막대와 원문 표

**뜻과 비유.** 그래프는 값을 빠르게 비교하게하지만 축·단위·누락 표시를 읽어야합니다. 오늘의 막대는 각 기록의 온도 높이를 보여 주며 간격 이 시간 간격을 뜻하지 않습니다.

**왜 필요한가.** 표를 함께 두면 작은 막대나 미측정 표시의 정확한 값과 시각을 다시 확인할 수 있습니다.

**예를 따라 읽기.** 0은 최소 높이로 표시하되 글자 0을 남기고 null은 미측정 문구로 보여 줍니다.

**헷갈리는 반례.** 막대 사이 간격이 같다고 측정 시간 간격까지 같았다고 해석하지 않습니다.

**직접 적용.** 막대 하나와 표 한 행 연결하기 → 0과 미측정의 표시 비교하기 → S01 이력 두 점의 시각 읽기 → 그래프만으로 알 수 없는 것 쓰기

**설명할 질문.** 그래프 옆에 원문 표를 함께 두는 이유는 무엇인가요?

**막혔을 때.** 막대만 보고 정확한 소수를 추측하지 않고 표의 값을 확인합니다.

입력·답칸·확인 순서는 [실습지의 A12](practice-guide.md#a12)와 [활동 원문](examples/course/data/A12_input.md)에 있습니다.

## 5구간 · 멈춤·누락·오류 상태



### A13 · 새 값이 멈춘 상태

**뜻과 비유.** 오래된 값은 값 자체가 사라진 것이 아니라 마지막 기록 이후 시간이 지났다는 상태입니다. 마지막 관찰과 확인 시각을 함께 봅니다.

**왜 필요한가.** 오래된 수치를 계속 큰 글자로 보여 주면 지금도 새 측정이 들어오는 것처럼 오해할 수 있습니다.

**예를 따라 읽기.** 70초 수신 멈춤 버튼은 새 자료를 추가하지 않고 고정 확인 시각만 70초 이동합니다. 입구 정상은 오래됨으로 바뀝니다.

**헷갈리는 반례.** 실제로 네트워크 송신을 중단한 것이 아니라 멈춤 상황을 재현하는 모의 시각 변경입니다.

**직접 적용.** 멈춤 전 입구 상태 기록하기 → 70초 버튼 누르기 → 값 유지와 상태 변화 구분하기 → 고정 시각 모의라는 한계 쓰기

**설명할 질문.** 값이 남아 있는데도 정상이라고 부를 수 없는 이유는 무엇인가요?

**막혔을 때.** 상태가 미측정이나 정지인 행은 우선 순위 때문에 그 문구가 유지됩니다. 모든 행이 오래됨이어야한다고 가정하지 않습니다.

입력·답칸·확인 순서는 [실습지의 A13](practice-guide.md#a13)와 [활동 원문](examples/course/data/A13_input.md)에 있습니다.

### A14 · 누락·정지·통신 실패

**뜻과 비유.** 미측정은 값이 없다는 데이터 상태, 정지는 장치의 상태, 통신 실패는 요청 결과를 받지 못한 상황입니다. 각각 다른 증거와 안내가 필요합니다.

**왜 필요한가.** 서로 다른 원인을 모두 0으로 보여 주면 사용자가 무엇을 확인해야할지 알 수 없습니다.

**예를 따라 읽기.** S02는 null이라 미측정,S04는 0과 false라 정지입니다. 서버를 끈 뒤 API 읽기는 수신 실패 문구를 보여 줍니다.

**헷갈리는 반례.** 수신 실패 때 이전 값을 유지하더라도 새로 받았다고 표시하면 안 됩니다.

**직접 적용.** 세 상태의 근거 필드 찾기 → 서버 종료 후 API 다시 읽기 → 이전 표와 실패 안내 동시 확인하기 → 상태별 다음 확인 행동 쓰기

**설명할 질문.** 미측정과 수신 실패는 어떻게 구분하나요?

**막혔을 때.** 로컬 서버가 없다면 실패 상황을 강사가 시연하고 개인 실행 여부를 구분해 기록합니다.

입력·답칸·확인 순서는 [실습지의 A14](practice-guide.md#a14)와 [활동 원문](examples/course/data/A14_input.md)에 있습니다.

### A15 · 잘못된 입력의 거절

**뜻과 비유.** 입력을 거절하는 것은 전체 프로그램을 멈추는 것과 다릅니다. 오류 이유를 반환하고 기존 기록을 유지해야 다음 정상 요청을 처리할 수 있습니다.

**왜 필요한가.** 잘못된 값 한 개가 전체 이력에 섞이거나 검증 없이 화면에 나타나지 않도록 수신 단계와 화면 단계를 구분합니다.

**예를 따라 읽기.** 온도 51이나 문자열은 POST400이며 기록 수는 늘지 않습니다. 0이나 null은 계약에 맞으면 받습니다.

**헷갈리는 반례.** 에러가 났다는 이유로 서버 기록 전체를 비우면 정상 기록까지 잃습니다.

**직접 적용.** 정상 수신 건수 적기 → 제공 오류 입력의 예상 400 쓰기 → 강사 검증 결과와 건수 비교하기 → 정상 입력 다시 보내기 절차 설명하기

**설명할 질문.** 오류 응답 뒤 어떤 기존 상태가 유지돼야하나요?

**막혔을 때.** 검사기준과 실제 장비 범위를 혼동하지 않습니다. 이 과제의 0~50 은 입력 규칙입니다.

## 6구간 · 동료 검수와 인계



### A16 · 표시 문구와 사용자 설명

**뜻과 비유.** 상태 문구는 사용자에게 현재 사실과 필요한 행동을 알려 주는 내용입니다. 내부 오류 이름만 노출하기보다 확인 범위를 설명합니다.

**왜 필요한가.** “실패”한 단어보다 이전 값인지 새 값인지와 다시 읽을 방법을 함께 알려 주면 오해를 줄일 수 있습니다.

**예를 따라 읽기.** 수신 실패 문구에“이전 화면 값을 유지합니다”라는 설명이 있습니다. 모의 기록 추가도 서버 저장이 아님을 알립니다.

**헷갈리는 반례.** 모의 데이터를 실시간 센서로 표시하거나 단위 없이 숫자만 바꾸면 정확한 화면이라도 잘못 해석됩니다.

**직접 적용.** 현재 안내문 두개 읽기 → 더 명확한 문장 한 개 제안하기 → work/app.js의 문구 한곳 수정하기 → 동작과 데이터는 유지되는지 확인하기

**설명할 질문.** 사용자가 마지막 값을 새 값으로 오해하지 않게 어떻게 말할까요?

**막혔을 때.** 문구를 고칠 때 따옴표와 문장 밖 코드를 지우지 않습니다. 원본과 변경 한 줄만 대조합니다.

입력·답칸·확인 순서는 [실습지의 A16](practice-guide.md#a16)와 [활동 원문](examples/course/data/A16_input.md)에 있습니다.

### A17 · 동료가 다시 실행하는 검수

**뜻과 비유.** 재현 검수는 다른 사람이 문서만 보고 같은 입력과 화면을 확인할 수 있는지 살펴보는 것입니다.

**왜 필요한가.** 작성자의 기억에만 의존한 실행 순서는 강의실이나 다른 PC에서 쉽게 빠집니다.

**예를 따라 읽기.** 정적 기본 경로와 서버·송신·API 다시 읽기 경로를 분리해서 짝에게 전달합니다.

**헷갈리는 반례.** 화면 스크린 샷 한 장만으로 서버가 정상 수신했거나 오류를 거절했다는 것까지 증명하지 않습니다.

**직접 적용.** 실행 순서와 입력 파일 쓰기 → 짝이 입구 필터 결과 대조하기 → 한 수정 값을 입력부터 표까지 찾기 → 빠진 준비와 종료 방법 보완하기

**설명할 질문.** 같은 결과를 비교하려면 어떤 시작 상태를 맞춰야하나요?

**막혔을 때.** 서로 다른 상태에서 비교하면 브라우저 새로고침이나 서버 재시작으로 기준 조건을 맞춥니다.

입력·답칸·확인 순서는 [실습지의 A17](practice-guide.md#a17)와 [활동 원문](examples/course/data/A17_input.md)에 있습니다.

### A18 · 운영 한계와 다음 연결

**뜻과 비유.** 제작 완료는 제공 파일과 모의 동작을 확인했다는 뜻입니다. 실제 장비·지속 저장·인증·배포까지 확인했다는 뜻은 아닙니다.

**왜 필요한가.** 실무로 넘어갈 때 새로 확인해야할 조건을 분명히 남겨야 교재 예제를 바로 운영 시스템으로 오해하지 않습니다.

**예를 따라 읽기.** 서버 기록은 메모리에 있어 재시작 하면 초기 자료로 돌아갑니다. GitHub Pages는 정적 화면을 제공하며 Python 서버는 별도입니다.

**헷갈리는 반례.** 모의 센서의 성공을 ESP32 연결 성공이나 공개 배포 완료라고 보고하지 않습니다.

**설명할 질문.** 실제 현장에 연결하기 전에 무엇을 더 확인해야하나요?

**막혔을 때.** 완료 문장에 모의·로컬·실제 실행 범위를 명시합니다. 실측 강의 시간은 별도 기록합니다.
