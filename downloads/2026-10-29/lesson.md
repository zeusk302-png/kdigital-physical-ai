#### 실무 상황과 원리

### A04 · 정적 파일로 여는 모의 화면

<!-- enrichment:2026-10-29:P2 -->

#### 2교시 필수 개념 보충 · 브라우저와 HTTP 서버가 하는 일

#### 실무 상황과 원리

동료가 index.html을 열었는데 API 버튼에서 실패가 났습니다. 화면 파일이 열렸다고 API 서버까지 켜진 것은 아닙니다. 브라우저는 HTML, CSS, JavaScript를 읽어 화면을 만들고, 서버는 주소로 온 요청을 받아 응답하는 별도 프로그램입니다. 같은 PC 안에서도 두 역할과 실행 위치를 나눠 이해해야 합니다.

고정 fixture 경로는 파일 속 가상 기록을 화면 메모리에 읽습니다. 모의 추가 버튼은 그 메모리를 바꾸며 서버에 저장하지 않습니다. 로컬 API 경로는 Python server.py를 실행해야 합니다. GET /api/readings는 목록을 요청하고 POST /api/readings는 검사할 새 기록을 보냅니다. GET은 읽기, POST는 제공된 서버에서 추가 요청이라는 약속입니다. HTTP 상태 200은 읽기 성공, 201은 새 기록 수락, 400은 내용 오류, 404는 없는 경로를 뜻합니다.

완성 실행 흐름은 예제 course 폴더의 터미널에서 python -X utf8 code/server.py 입력 → 터미널을 열린 채 유지 → 브라우저에서 http://127.0.0.1:8780/?source=api 열기입니다. 127.0.0.1은 현재 PC, 8780은 해당 프로그램을 찾는 포트입니다. 다른 PC나 인터넷에 공개된 주소가 아닙니다. 서버 터미널에서 Ctrl+C로 종료하면 이후 요청은 실패할 수 있습니다. 주소의 ?source=api는 시작할 때 API 읽기를 선택하는 매개변수입니다. Python의 단순 정적 서버는 파일을 제공할 뿐 이번 GET·POST 처리 코드를 대신 만들지 않습니다. 서버 기록은 메모리에만 있어 재시작하면 제공 초기 데이터로 돌아갑니다. 저장 파일이나 데이터베이스가 있는 운영 서비스와 구분합니다.

#### 새로운 입력에 직접 적용 · 복습 또는 도전

복습 문제: HTML은 보이는데 API 읽기만 실패합니다. 확인할 프로그램, 주소, 포트, 터미널 상태를 순서대로 작성하세요. python -m http.server만 켜면 POST 추가가 되는지도 판단하세요.

#### 정답과 오답의 이유

server.py 실행 여부와 주소의 127.0.0.1:8780을 먼저 확인하고 종료·오류 로그를 봅니다. 기본 정적 서버는 제공 API 추가 동작을 구현하지 않습니다. 화면 표시 성공과 API 수신 성공을 같은 결과로 적으면 오답입니다.

#### 확인 질문과 답

1. 서버를 켠 창은 닫아도 되나요? → 수신 중에는 유지합니다.
2. 127.0.0.1의 범위는? → 현재 PC입니다.
3. 현재 서버는 영구 저장인가요? → 메모리 저장입니다.

### A05 · 서버와 API의 요청·응답

**뜻과 비유.** 서버는 요청을 받아 결과를 보내는 프로그램입니다. API는 프로그램들이 어떤 주소와 자료형식으로 요청할지 정한 창구입니다.

**왜 필요한가.** 보낸 값과 수신한 값, 보여 준 값을 각각 확인하려면 어느 프로그램이 어느 역할을 하는지 구분해야 합니다.

**예를 따라 읽기.** GET /api/readings는 기록 목록을 읽고 POST /api/readings는 검사한 새 관찰을 추가합니다.

**헷갈리는 반례.** GET과 POST라는 이름을 외우는 것만으로 입력 규칙이나 성공 여부가 확인되지는 않습니다.

**직접 적용.** 서버·송신자·브라우저 역할 쓰기 → GET과 POST의 목적 구분하기 → 응답 상태 200·201·400 비교하기 → 한 값의 이동 경로 설명하기

**설명할 질문.** 수신 성공과 화면 표시 성공은 왜 별도 확인인가요?

**막혔을 때.** 주소가 같아도 메서드가 다르면 역할이 다릅니다. 실습은 로컬 127.0.0.1에서만 엽니다.

### A06 · 로컬 서버 실행과 종료

**뜻과 비유.** 로컬 실행은 자기 PC의 프로그램이 정해진 포트에서 요청을 기다리는 상태입니다. 주소·포트·실행 중인 창을 함께 기록합니다.

**왜 필요한가.** 서버를 껐는데 화면만 남아 있으면 마지막 값을 새로운 수신값으로 오해할 수 있습니다.

#### 3교시 필수 개념 보충 · CSV 빈칸과 JSON null의 처리 규칙

#### 실무 상황과 원리

센서 업체가 CSV를 보내왔습니다. 한 행의 온도는 0, 다른 행은 빈칸입니다. 이를 모두 숫자 0으로 바꾸면 실제 영도와 미측정을 구별하지 못합니다. 입력 규칙은 필드 이름, 자료형, 단위, 허용 범위와 누락 처리의 약속입니다. 파일 문법을 읽는 파싱과 값이 업무 약속을 지키는 검사는 별도 단계입니다.

CSV의 셀은 우선 문자열로 읽습니다. temperature_c 셀이 "22.5"이면 숫자 변환을 하고, 빈 문자열이면 합의한 규칙에 따라 None으로 옮깁니다. JSON에서는 None을 null로 씁니다. CSV 문자 "null"은 자동으로 JSON null이 되는 특별 문법이 아니므로 빈칸과 같은 것으로 처리할지 처리 규칙이 필요합니다. 이번 보충 예는 빈칸만 미측정으로 인정하고 문자 null은 형식 오류로 남깁니다. active의 true와 false도 문자열을 그대로 두지 않고 정한 불리언 값으로 변환해야 합니다.

완성 추적 예는 CSV 입력 S05,창고,0 → 문자열 "0" → 숫자 0.0 → 유효 범위 0~50 확인 → JSON temperature_c:0.0입니다. 다음 행 S06,창고,빈칸은 None → JSON null → 미측정 표시입니다. "abc"나 51은 거절하고 원문과 이유를 기록합니다. 서버의 입력 규칙은 temperature_c 숫자 또는 null, active 불리언, 시간대가 있는 measured_at을 요구합니다. 보낸 본문, HTTP 응답, 다시 읽은 기록, 화면의 같은 sensor_id를 연결해 한 값의 이동을 확인합니다. 수락만 보았다고 최신 표가 바뀐다고 단정하지 않습니다. 과거 시각으로 보낸 행은 이력에는 추가되어도 최신값에서 선택되지 않을 수 있습니다.

#### 새로운 입력에 직접 적용 · 복습 또는 도전

#### 정답과 오답의 이유

0.0, null, 거절, 거절, 24.0입니다. 문자 null은 합의 없이 특별 값으로 해석하지 않습니다. 최신 표는 도착 순서가 아니라 측정 시각을 비교하므로 과거 행을 보내도 최신값이 유지될 수 있습니다.

#### 확인 질문과 답

1. CSV 빈칸은 자동 0인가요? → 아닙니다.
2. JSON null은 문자열인가요? → 따옴표 없는 누락 값입니다.
3. 201만 보면 최신값 변경인가요? → 재조회와 시각 비교도 필요합니다.

#### 짧은 완성 코드로 추적하기

제공 참고 파일 [code/csv_value_trace.py](examples/course/code/csv_value_trace.py)은 보존합니다. 예제 `course` 폴더에서 이 파일을 `work/csv_value_trace.py`에 복사하고 학생 수정본은 work에 저장합니다. 아래는 완결된 전체 코드입니다. 파일·폴더·확장자를 확인한 뒤 같은 course 폴더의 터미널에서 `python -X utf8 work/csv_value_trace.py`을 실행합니다. 저장과 실행은 별도 행동입니다.

```python
import csv
import io
import json
import math
source = "sensor_id,temperature_c\nS05,0\nS06,\nS07,24.0\n"
rows = []
for row in csv.DictReader(io.StringIO(source)):
    text = row["temperature_c"].strip()
    value = None if text == "" else float(text)
    if value is not None and (not math.isfinite(value) or not 0 <= value <= 50):
        raise ValueError("온도 범위 오류")
    rows.append({"sensor_id": row["sensor_id"], "temperature_c": value})
print(json.dumps(rows, ensure_ascii=False))
```

예상 출력:

```text
[{"sensor_id": "S05", "temperature_c": 0.0}, {"sensor_id": "S06", "temperature_c": null}, {"sensor_id": "S07", "temperature_c": 24.0}]
```

#### 4교시 필수 개념 보충 · 필터와 평균의 분모를 먼저 결정하기

#### 실무 상황과 원리

관리자가 장소 필터를 창고로 바꾸면 평균 숫자도 달라집니다. 평균은 센서 이름의 장식 숫자가 아니라 선택한 자료의 합계를 개수로 나눈 계산입니다. 어떤 행을 포함했는지 설명하지 않으면 같은 기록에서 서로 다른 평균이 나옵니다. 현재 예제는 센서별 최신값 평균이 아니라 선택한 장소의 유효 숫자 이력 평균입니다.

완성 예의 이력 온도는 [22,24,null,0]입니다. 모두 입력 규칙에 맞고 확인 시각 이전이라고 가정합니다. null을 제외하고 0은 포함하면 합계 46, 분모 3, 평균 15.33℃입니다. null을 0으로 바꾸면 분모가 4가 되어 11.5℃라는 다른 결과가 나옵니다. 0을 거짓 값이라 제외하면 23℃가 되어 역시 틀립니다. 같은 센서의 두 기록도 이력 평균에서는 각각 포함합니다. 최신값 평균이 필요한 업무라면 자료 선택 규칙부터 새로 정해야 합니다.

기본 코드의 평균은 입력 형식·범위가 유효하고 미래 시각이 아닌 행의 숫자만 사용합니다. 오래된 값과 정지 센서의 숫자도 현재 규칙에서는 포함하므로 “현재 가동 센서 평균”이라고 이름 붙이지 않습니다. 장소 필터는 이력과 최신 표 모두에 적용합니다. 그래프의 막대 높이는 온도이며 막대 간격은 시간 간격을 뜻하지 않습니다. 10초 간격과 1시간 간격의 기록이 같은 간격으로 그려질 수 있습니다. 표의 sensor_id, 값, 시각을 그래프와 대조해야 해석할 수 있습니다. 숫자가 한 건도 없을 때 평균은 null이고 화면은 계산 안 함으로 표시합니다.

2. 정지 센서 0은 포함되나요? → 현재 이력 평균에는 포함됩니다.
3. 막대 간격이 시간인가요? → 현재 그래프에서는 아닙니다.

### A11 · 평균과 미측정의 처리

**뜻과 비유.** 평균은 더한 값과 나눈 개수가 무엇인지 함께 설명해야 하는 요약 값입니다. 오늘은 선택 이력의 유효한 숫자만 계산합니다.

**왜 필요한가.** null을 0으로 바꾸면 측정되지 않은 값이 실제 0으로 계산에 섞여 평균이 낮아집니다.

**예를 따라 읽기.** 전체 유효 온도 22.5·29.0·0·22.8의 평균은 18.575이며 소수 둘째 자리 표시는 18.58입니다.

**헷갈리는 반례.** 정지된 센서의 0도 유효 측정 이력에는 포함합니다. 운영 목적에 따른 다른 평균을 원하면 별도 규칙이 필요합니다.

**직접 적용.** 숫자인 온도와 null 나누기 → 합계와 나눌 개수 직접 쓰기 → 표시 값과 계산 정의 비교하기 → 창고만 고르면 계산 안 함인지 확인하기

**설명할 질문.** 0을 포함하고 null을 제외하는 이유는 무엇인가요?

**막혔을 때.** 반올림 표시와 원 계산 값이 달라 보이면 소수 둘째 자리 표시 규칙을 확인합니다.

### 평균에 포함하는 기록의 범위

현재 선택된 이력 중 센서·장소·시각·온도의 기본 형식이 맞고, 기준 시각보다 미래가 아닌 숫자 기록을 유효 집계에 포함합니다. 미측정 null, 잘못된 자료형, 미래 시각은 평균에서 제외합니다. 기본 형식을 만족하는 과거 기록·정지 센서의 기록·실제 수치 0은 이력 평균에 포함합니다. 이력 평균과 현재 연결 상태·최신값은 의미가 다릅니다. 다른 운영 목적의 평균은 별도 규칙을 정해야 합니다.

**왜 필요한가.** “실패”한 단어보다 이전 값인지 새 값인지와 다시 읽을 방법을 함께 알려 주면 오해를 줄일 수 있습니다.

**예를 따라 읽기.** 수신 실패 문구에“이전 화면 값을 유지합니다”라는 설명이 있습니다. 모의 기록 추가도 서버 저장이 아님을 알립니다.

**헷갈리는 반례.** 모의 데이터를 실시간 센서로 표시하거나 단위 없이 숫자만 바꾸면 정확한 화면이라도 잘못 해석됩니다.

**직접 적용.** 현재 안내문 두 개 읽기 → 더 명확한 문장 한 개 제안하기 → work/app.js의 문구 한 곳 수정하기 → 동작과 데이터는 유지되는지 확인하기

**설명할 질문.** 사용자가 마지막 값을 새 값으로 오해하지 않게 어떻게 말할까요?

**막혔을 때.** 문구를 고칠 때 따옴표와 문장 밖 코드를 지우지 않습니다. 원본과 변경 한 줄만 대조합니다.

### A17 · 동료가 다시 실행하는 검수

**뜻과 비유.** 재현 검수는 다른 사람이 문서만 보고 같은 입력과 화면을 확인할 수 있는지 살펴보는 것입니다.

**왜 필요한가.** 작성자의 기억에만 의존한 실행 순서는 강의실이나 다른 PC에서 쉽게 빠집니다.

**예를 따라 읽기.** 정적 기본 경로와 서버·송신·API 다시 읽기 경로를 분리해서 짝에게 전달합니다.

**헷갈리는 반례.** 화면 스크린 샷 한 장만으로 서버가 정상 수신했거나 오류를 거절했다는 것까지 증명하지 않습니다.

**직접 적용.** 실행 순서와 입력 파일 쓰기 → 짝이 입구 필터 결과 대조하기 → 한 수정 값을 입력부터 표까지 찾기 → 빠진 준비와 종료 방법 보완하기

**설명할 질문.** 같은 결과를 비교하려면 어떤 시작 상태를 맞춰야 하나요?

**막혔을 때.** 서로 다른 상태에서 비교하면 브라우저 새로고침이나 서버 재시작으로 기준 조건을 맞춥니다.

입력·답칸·확인 순서는 [실습지의 A17](practice-guide.md#a17)와 [활동 원문](examples/course/data/A17_input.md)에 있습니다.

### A18 · 운영 한계와 다음 연결

**뜻과 비유.** 제작 완료는 제공 파일과 모의 동작을 확인했다는 뜻입니다. 실제 장비·지속 저장·인증·배포까지 확인했다는 뜻은 아닙니다.

**왜 필요한가.** 실무로 넘어갈 때 새로 확인해야 할 조건을 분명히 남겨야 교재 예제를 바로 운영 시스템으로 오해하지 않습니다.

**예를 따라 읽기.** 서버 기록은 메모리에 있어 재시작하면 초기 자료로 돌아갑니다. GitHub Pages는 정적 화면을 제공하며 Python 서버는 별도입니다.

**헷갈리는 반례.** 모의 센서의 성공을 ESP32 연결 성공이나 공개 배포 완료라고 보고하지 않습니다.

**직접 적용.** 세 문장 인계 작성하기 → 정적·API 검증 범위 구분하기 → 미검증 조건 세 개 기록하기 → 다음날 프로젝트 기획 질문 한 개 쓰기

**설명할 질문.** 실제 현장에 연결하기 전에 무엇을 더 확인해야하나요?

**막혔을 때.** 완료 문장에 모의·로컬·실제 실행 범위를 명시합니다. 실측 강의 시간은 별도 기록합니다.

입력·답칸·확인 순서는 [실습지의 A18](practice-guide.md#a18)와 [활동 원문](examples/course/data/A18_input.md)에 있습니다.
