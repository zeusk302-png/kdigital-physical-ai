# V07 · 인식 실패와 처리 속도를 공정하게 비교하기

같은 입력에서 하나의 설정만 바꾸어 근거 남기기


프로그램 창이 매끄럽게 보여도 객체를 놓치거나 사건을 반복하면 목적을 달성하지 못합니다. 반대로 박스가 잘 맞아도 실시간 판단이 너무 늦으면 웹캠 경보에는 적합하지 않을 수 있습니다. 인식 품질과 처리 속도는 각각 확인해야 합니다. 오늘은 같은 짧은 입력 영상에서 기준 설정 A와 비교 설정 B를 실행하고, 사람이 직접 확인한 장면 수와 처리 시간을 함께 기록합니다. 사전학습 모델의 전체 정확도 평가를 작은 영상 한 개로 대체하지 않습니다.

먼저 configs/default.json을 baseline.json과 fast.json으로 복사합니다. baseline은 imgsz=640, fast는 imgsz=320으로 두고 conf·클래스·추적기·입력 영상은 같게 유지합니다. imgsz는 내부 모델 입력의 목표 크기이지 원본 영상 파일을 영구 축소하는 기능이 아닙니다. 작게 하면 계산량이 줄 수 있지만 작은 객체가 사라질 수 있습니다. 속도가 반드시 절반이 되거나 정확도가 정해진 만큼 줄어든다고 미리 단정하지 않습니다.
```powershell
.\.venv\Scripts\python.exe -m src.main --source runtime/input/clip.mp4 --config configs/baseline.json --output runtime/results/baseline
.\.venv\Scripts\python.exe -m src.main --source runtime/input/clip.mp4 --config configs/fast.json --output runtime/results/fast
```
결과 폴더를 다르게 해야 이전 실험을 덮어쓰지 않습니다. GUI 표시 유무도 두 실험에서 같게 맞춥니다. 모델 최초 실행의 준비 비용이 크므로 짧은 사전 실행 후 본 측정을 반복하고 각 회차를 기록합니다. 기록에서 마음에 드는 수치만 고르지 않습니다.

metrics.json의 processing_fps는 읽기·추론·그리기·저장을 포함한 전체 프레임 수를 경과 시간으로 나눈 값입니다. mean_pipeline_ms는 프레임을 읽은 뒤 추론부터 저장까지의 평균이며 모델 내부 inference 시간과 다릅니다. source_fps는 입력 영상의 재생률입니다. 영상이 30FPS이고 처리 10FPS라면 저장 결과는 원래 30FPS로 재생될 수 있지만 생성에 세 배가량 걸릴 수 있습니다. 카메라의 지연은 이 수치 하나로 정확히 측정되지 않으므로 촬영 시각과 표시 시각을 별도로 비교해야 합니다.

품질 기록에는 10개 이상 고정 프레임을 사람이 표시한 정답표를 만듭니다. 예를 들어 프레임 20에는 사람 두 명이 보이며 A는 둘, B는 한 명을 잡았다고 기록합니다. 작은 표본에서는 '이 장면에서 누락 1건'이라고 씁니다. 모든 장소의 정확도 90%라고 쓰지 않습니다. 가림·어두운 장면·빠른 이동 세 조건 중 가능한 두 조건 이상을 비교합니다. 촬영 조건을 통제할 수 없으면 어떤 조건을 확인하지 못했는지 남깁니다.

필수 제출은 입력 식별 정보·설정 두 개·측정 표·오류 장면 근거·선택 이유입니다. 현재 제작 검증은 공식 bus 사진에서 CPU 추론이 실제로 실행됐고 320에서 사람 3개, 640에서 4개가 나왔습니다. 이는 해당 사진·해당 설정 결과이며 수업 PC나 자기 영상 결과로 옮겨 쓰지 않습니다. 한 장의 첫 실행 시간을 근거로 크기별 속도 우열을 주장하지도 않습니다. 학생은 직접 측정한 값만 자기 실험 표에 넣습니다. 추가 도전은 conf만 바꾼 별도 비교를 수행하고 해상도 효과와 점수 기준 효과를 따로 설명하는 것입니다.
